# 基本词性目录对齐产品原型与"基础词性"规则 需求评估

## 背景与目标

产品给出了"基本词性"管理表的原型：列为 序号 / 正式中文 / 简洁显示 / 正式英文 / 英文缩写 /
英文全称 / 创建人 / 创建时间 / 操作（修改、删除）。与现有实现相比：

- 「正式中文」「正式英文」「英文缩写」对应现有 `name_zh` / `name_en` / `abbreviation`，只是叫法不同；
- 「简洁显示」「英文全称」是**新字段**，后端 `PartOfSpeechConfig` 目前没有；
- 现有表格里的「稳定编码」列原型没有；「细分词性」「引用」两列产品要求保留。

同时产品补充了一条一直没有落地的基础规则：**只有名词、动词、代词、形容词、副词这五个
"基础词性"可以扩展细分词性，其他基本词性不能挂细分词性。** 现状是后端种子给全部 11 个
基本词性都配了细分词性（介词下 PREP、冠词下 ART 等），创建细分词性时对父级也没有任何限制，
本地库里已经出现"非基础词性挂了细分词性、词条又引用了它"的数据（2026-09-06 已清空本地
词条与词性数据，备份在会话 scratchpad）。

目标：管理后台的基本词性目录按原型呈现并可维护两个新字段；细分词性只能挂在五个基础词性下，
前后端一致地约束这条规则。

## 目标端

- admin（`apps/admin`，antd v6）——词性配置页、V3 词条创建向导中的细分词性选择。
- 后端 tsz-rust 契约变更（新增字段、新增规则与错误码、种子与数据迁移）——见 design.md
  「后端对接」；已拍板由本会话直接落地。
- 不涉及 web 端（`apps/web` 未消费词性目录）。

## 用户故事 / 使用场景

1. **查看基本词性列表**：超级管理员进入「系统设置 → 词性配置」，表格按原型展示
   序号、正式中文、简洁显示、正式英文、英文缩写、英文全称、细分词性、引用、创建人、创建时间、
   操作。能在同一行看出这个词性是否允许扩展细分词性。
2. **新增 / 修改基本词性**：弹窗里除现有字段外还要填写「简洁显示」「英文全称」，两者必填；
   留空或超长时前端即时提示，服务端也拒绝。修改时稳定编码仍不可改。
3. **维护细分词性**：在「细分词性」Tab 里，「所属基本词性」下拉只列出五个基础词性；
   对非基础词性无法新增细分词性。若通过其他途径（旧版本前端、直接调接口）尝试，
   服务端返回稳定错误码，页面给出"该基本词性不支持细分词性"的提示。
4. **词条创编选择细分词性**：V3 向导词义步里，只有基础词性的释义才出现细分词性选择；
   非基础词性的释义不展示该字段（等价于"不指定子词性"）。历史数据若已带子词性，
   继续以只读方式显示，不静默丢弃。
5. **管理员自建的其他基本词性**：管理员可以照常新增诸如"小品词"这类非基础词性，
   它们能被词条引用，但不能扩展细分词性。

## 功能范围

### 本次包含

- 基本词性表按原型调整列与操作按钮（已完成：列名改为正式中文/正式英文、去掉稳定编码列、
  行操作按钮去图标；细分词性、引用两列保留）。
- 新增「简洁显示」「英文全称」两个必填字段：列表展示、新增/修改表单、目录 wire 类型。
- 细分词性同样按原型对齐（评审后追加）：新增「简洁显示」「英文缩写」「英文全称」三个必填字段；表格列为 序号 / 正式中文 / 简洁显示 / 正式英文 / 英文缩写 / 英文全称 / 所属基本词性 / 引用 / 创建人 / 创建时间 / 操作，去掉稳定编码与排序列。
- "基础词性可扩展细分词性"规则：后端按固定编码集合判定并在创建细分词性时拦截；
  前端根据后端下发的标记过滤父级选项、在表格中标注、在向导中隐藏字段。
- 后端种子与迁移：新字段回填、五个基础词性以外的种子基本词性及其细分词性下线、幂等重建种子
  （本地库已清空，迁移必须能在空目录上重新种入）。
- 契约同步（`sync:openapi`）、类型镜像、契约测试、单测与手测清单。

### 明确不包含

- 不改稳定编码规则，不重命名现有 wire 字段（`name_zh` 等保持不变，只改界面文案）。稳定编码仍是接口层标识，但不再让管理员填写或查看：新建时由英文全称派生，创建后不可修改（评审后追加）。
- 不把「简洁显示」推广到词库列表、向导标签等业务页面（见开放问题 2）。
- 不改 web 端；不动内置词典导入（`dictionary.*`）数据。
- 不为测试服 / 生产的存量数据做自动修复：存在"非基础词性下的细分词性被词条引用"时，
  迁移直接失败并要求先人工清理（见约束）。
- 不改细分词性自身的字段。

## 约束与边界

- 权限沿用现状：catalog 任意有效管理员可读；管理列表与全部写操作仅 `super_admin`。
- `@tsz/types` 全 snake_case 1:1 镜像后端；前端不得硬编码"哪五个是基础词性"，
  必须使用后端下发的布尔标记（与 `allowed_form_types` 由后端派生下发同一路数）。
- 「简洁显示」：去首尾空白后 1–16 个字符，全局唯一（与 `name_zh` 同级约束）；
  「英文全称」：去首尾空白后 1–64 个字符，忽略大小写唯一。以上为本评估默认，见开放问题 3。
- 两个新字段为**必填**（用户 2026-09-06 拍板）。请求体缺字段时服务端返回 422
  `invalid_request_body`；这意味着后端上线后旧前端无法再新增/修改基本词性，
  前后端必须同批部署（见 design.md「部署顺序」）。
- 词性响应不在 admin-word-v3 的严格运行时 schema 范围内，后端先加响应字段不会打坏前端。
- 非基础词性下若仍有细分词性且被词条引用，删除会被外键 RESTRICT 拦住：迁移不得静默跳过，
  应明确失败并提示先清理。本地已清空；测试服部署前需确认（开放问题 4）。
- admin 继续使用 antd v6，不引入 tailwind / `@tsz/ui`；时间格式沿用全站 `YYYY-MM-DD HH:mm`。

## 验收标准

- [ ] 词性配置表列顺序为：序号、正式中文、简洁显示、正式英文、英文缩写、英文全称、细分词性、引用、创建人、创建时间、操作；无「稳定编码」列。
- [ ] 非基础词性所在行的「细分词性」列显示"不可扩展"，基础词性显示现有的"N 项"。
- [ ] 基本词性下仍有细分词性时「删除」禁用并提示先删细分词性；直接调接口删除返回 409 `part_of_speech_has_sub_parts`（评审后追加）。
- [ ] 新增 / 修改弹窗包含「简洁显示」「英文全称」，留空时不能提交；保存后列表与目录立即刷新并显示新值。
- [ ] 「细分词性」Tab 的「所属基本词性」下拉只包含 `sub_parts_extensible = true` 的词性；目录中没有基础词性时给出空态提示而非报错。
- [ ] 对非基础词性调用创建细分词性接口返回稳定错误码，页面提示"该基本词性不支持细分词性"，不刷新丢失表单内容。
- [ ] V3 向导：基础词性的释义显示细分词性选择；非基础词性的释义不显示；历史 `sub_pos` 非空时仍以只读文本展示。
- [ ] 迁移在**空目录**（本地已清空）与**已有 11+19 种子**（测试服）两种库上都能成功执行，且执行两次结果一致。
- [ ] 迁移后五个基础词性以外不存在任何细分词性；若存在被引用的违规数据，迁移失败并给出可读原因。
- [ ] `pnpm --filter @tsz/api-client sync:openapi` 后契约测试通过；`pnpm typecheck` / `pnpm lint` / `pnpm test` 全绿。
- [ ] 本地 `cargo run` 后端 + admin 联调走通：新增基础/非基础词性、新增细分词性成功与被拒两条路径、向导中子词性字段显隐。

## 已决策（2026-09-06 评审拍板）

1. **六个非基础种子基本词性（介词、冠词、限定词、连词、数词、感叹词）不保留**：连同其细分词性一起由迁移下线；默认种子只剩五个基础词性 + 13 个细分词性。管理员仍可按需新增非基础词性，但不能挂细分词性。
2. **「简洁显示」本批不替换业务页面**的词性名，只做存储、管理表展示与录入。
3. **唯一性与长度上限按默认**：简洁显示 1–16 字全局唯一；英文全称 1–64 字忽略大小写唯一。
4. **测试服 tshb-test 同样清空**词条（lexicon.*）与词性数据后再上迁移，不做人工挑删。
5. **后端由本会话直接在 tsz-rust 落地**（迁移、规则、错误码、OpenAPI），前后端同批交付。
