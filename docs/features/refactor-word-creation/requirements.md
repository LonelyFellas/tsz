# 新建单词流程重构：需求说明

## 背景与目标

管理后台当前在“词库管理 → 智能词库”中通过弹窗录入 `headword`，立即创建草稿，再跳转到一个整页长表单。新的产品原型要求把“创建单词”改为有明确进度、逐步校验和英美方言联动的四步创编流程：

1. 创建新词条：所属语言、词条录入、词典检测、英美词形确认；
2. 词形与发音：基本词性、词形变化和发音；
3. 词义与例句：语法结构、多维释义、例句和关联词；
4. 预览并生效：字典预览、提交生效。

目标是在 admin 端完成一条可从智能词库列表进入、可连续走完四步、可用 mock 数据演示和测试的单词创建链路。衡量标准：验收场景中的新建单词主流程可从第 1 步走到第 4 步；刷新后仍可恢复已保存草稿；所有步骤都有明确的加载、空、校验失败和请求失败反馈；后续切换真实后端时 UI 不需要改写业务结构。

## 目标应用

- 仅 `apps/admin`。
- `apps/web` 的智能词库选词、词表创建和学习端展示不在本需求内。

## 用户与权限

- 沿用现有 admin 登录与路由门禁。
- 沿用当前智能词库的 `words.access` 可见权限；创建、保存和生效是否还需要独立写权限，待后端与权限产品定义确认。
- 无权限、登录过期和后端返回 401/403 时，沿用平台统一鉴权处理，不在页面伪装成功。

## 用户故事

### 1. 从智能词库开始创建

作为词库管理员，我在智能词库点击“创建单词”后，进入独立的新建页面，而不是弹窗。我可以看到四步进度、当前词条摘要和各内容模块的完成状态。

本轮基线仅重构“创建单词”。“创建短语”保留现有入口和旧流程，不因本需求改写；若词典检测判定输入为短语，当前向导提示管理员改走“创建短语”，不把短语静默写成单词。后续如要统一两种创建流程，应作为显式扩展范围处理。

### 2. 创建新词条与词典检测

作为词库管理员，我可以：

- 选择所属语言；首期仅支持 English / 英语，其他语言不可选或不展示；
- 输入词条并发起“词典检测”；输入会去除首尾空格，但不擅自改变大小写；
- 看到词条类型（单词或短语）、智能词库重复检测结果、内置词典匹配结果和建议词性；
- 看到检测给出的词条类型；检测为短语时不能继续单词向导，并提供返回“创建短语”的入口；是否为短语最终以检测结果为准，前端不只依据空格自行拍板；
- 若智能词库已有重复词条，看到明确冲突信息并不能继续创建重复项；
- 若内置词典匹配到英美拼写差异，自动开启“区分英美词形”，展示输入命中的方言；与原输入对应的一侧为检测基准且只读，管理员补充或确认另一侧；
- 若没有英美差异，保持统一词形；本轮不允许在没有检测依据时手工制造英美差异；
- 查看建议的基本词性，然后进入下一步；建议词性直接生成第 2 步 Tab，管理员在第 2 步增删或调整，避免第 1 步和第 2 步出现两个可写来源。

内置词典与智能词库是两个不同检测源：前者提供英美式词形、读音和建议词性；后者检查平台词库中的重复条目。

### 3. 编辑词形与发音

作为词库管理员，我可以按基本词性 Tab 分组编辑词形与读音：

- 新增、切换和删除基本词性；至少保留一个词性，同一词条不能重复添加同一基本词性；
- 每个词形变化组可配置“词形是否规则变化（是/否）”；该布尔值只作组元数据，不改变表单结构；
- 同一词性可有一个或多个“词形变化组”，用于表达 `far → farther → farthest` 与 `far → further → furthest` 等并行范式；各组可排序、增删；
- 原形在语义上每个词性/各组只有一个基准值。原形拼写只读并从第 1 步主词派生；第 1 组可编辑该词性的原形发音，后续组展示只读镜像，不允许产生彼此冲突的原形；
- 在可判断时显示“英美拼写是否有区别”；区分英美拼写时，英式和美式内容左右并列，并保持词形类型逐行对齐；
- 仅在拼写相同且产品规则允许时配置“英美音标是否有区别”；若拼写已经不同，则不再显示这项选择；
- 每组原形位于首行；其他词形可新增、删除、排序，类型可选择，拼写和读音可编辑；同组双方言行由稳定的词形槽位对齐，不能靠数组下标猜测对应关系；
- 每个词形可维护发音方式、字典音标、实际发音；真实音频未接入时，试听/生成按钮保持禁用并说明原因；
- 区分方言时支持 BrE / AmE 独立音标与实际发音；统一时仅编辑一组 common 内容。

### 4. 编辑词义与例句

作为词库管理员，我按“词义 → 语法结构 → 例句”的业务顺序录入，并可以按词性维护：

- 英式与美式语法结构，区分方言时左右并列；语法结构由人工填写，不因切换方言自动翻写；
- 语法结构的方言形状只跟随第 1 步主词模式：主词统一时只保存 `common`，主词区分时必须分别保存 BrE / AmE；不再从各词性的拼写或音标规则二次推导；
- 多个词义，支持展开/收起和排序；每个词义包含等级、语义区间、细分词性、词频、是否依赖语境；
- 多维释义：等级、释义语言/方式、释义正文及绑定语法结构；
- 多维例句：等级、英文例句、汉语译文；系统自动建立且锁定一条指向当前词条当前词义的“主关联”，管理员可选配例句中其他单词/词义的“上下文关联”；
- 近义词、反义词、派生词及其匹配词义和分值；
- 除语法结构以外，已有 BrE / AmE variant 的英语文本随方言视图即时切换且不发请求；缺少目标 variant 时只显示明确的“生成英式/美式建议”操作，管理员预览并确认后才写入。切换或生成不得覆盖未经确认的手工内容。

### 5. 预览并生效

作为词库管理员，我可以在提交前以结构化字典卡片预览完整词条，看到缺失项定位提示，返回对应步骤修改，并在校验通过后直接提交生效。提交成功后回到智能词库列表，列表出现新词条且统计同步更新。

第 4 步没有随本需求提供视觉稿；首版明确采用后台结构化只读预览，不承诺复刻学习端样式，也不臆造新的业务内容。若后续提供视觉稿，再单独调整呈现层。

## 主流程

1. 管理员在 `/words` 点击“创建单词”。
2. 系统导航到新建向导并初始化第 1 步表单，此时既不创建草稿，也不写入正式词库。
3. 管理员输入 `center` 并点击检测。
4. mock 返回：类型为单词、智能词库未重复、内置词典匹配到 `centre / center`、建议词性为名词和动词。
5. 管理员确认区分英美词形；系统用检测结果创建草稿，以建议词性初始化第 2 步 Tab，并按现有统计口径把该草稿计入累计/今日/月度创编一次。
6. 管理员完成名词、动词的词形和读音，进入第 3 步。
7. 管理员完成语法结构、释义、例句和关联词，进入第 4 步。
8. 系统展示预览和完整性检查；管理员提交生效。
9. 系统显示成功反馈，更新智能词库缓存并导航回 `/words` 列表。

## 异常与边界流程

- 词条为空、超过 200 字符或语言不支持：不发检测请求，就地提示。
- 检测请求失败：保留输入，展示可重试错误；不产生草稿。
- 用户在检测请求未完成时修改了语言或词条：过期响应不得覆盖新输入，必须重新检测。
- 未匹配内置词典：显示“无匹配”；基线方案不允许继续创建，是否开放完全人工录入仍待产品确认。
- 智能词库重复：显示已存在词条及可跳转入口，禁止继续创建；大小写和首尾空格按后端归一化规则处理。
- 检测结果与输入不一致：必须由管理员确认建议词形，不能静默替换。
- 保存失败：保留当前表单数据，可重试，不推进步骤。
- 草稿加载失败或不存在：提供重试与返回列表；不能用空数据覆盖本地未保存内容。
- 刷新/直接访问后续步骤：有草稿 ID 时恢复服务端/mock 草稿；无草稿时回到第 1 步。
- 跳步：只能进入已经完成或当前可达的步骤。草稿创建后可通过 Stepper 回到只读第 1 步查看检测基准；如需修改语言或主词，必须确认废弃当前草稿并重新检测，避免隐式清空后续内容。
- 提交校验失败：按步骤归类错误并可定位到字段；不丢失草稿。
- 本语言释义缺失或例句未关联所需词义/单词：第 3 步明确标错，第 4 步禁止发布并可跳回对应节点。
- 重复提交：按钮 loading 且禁用；服务端/mock 按幂等语义只生效一次。
- 并发更新：真实接口若返回版本冲突，提示重新加载，不能覆盖他人内容。
- 保存策略：不做逐字段自动保存；“保存草稿”和“下一步”都会保存当前步骤，“下一步”仅在保存成功后导航。带未保存修改离开页面时必须确认。
- mock 模式发布成功：同一 mock 数据源中的列表、统计和详情必须立即可读，不能只弹成功消息却在列表中找不到词条；publish 只改变状态，不让创建时已经计数的统计重复增加。

## 范围

### 本轮包含

- 智能词库“创建单词”入口改为四步向导路由。
- 四步进度头、左侧词条/完成度摘要和桌面端主表单布局。
- 第 1 至第 4 步的可用交互、校验、加载和错误态。
- 英美统一/区分模式及其联动规则。
- 新建流程使用 contract-shaped mock；真实网络请求只能经过 `@tsz/api-client`，mock 与真实层实现同一个 typed data-source 接口。
- 新 wire 类型、前端表单模型和二者映射。
- 草稿恢复、分步保存和最终提交的 mock 行为。
- 新向导草稿从列表恢复，以及新格式词条发布后的只读查看路由；V2 已发布内容的再次编辑不在本轮范围。
- 现有编辑存量词条的兼容迁移方案；不能让 `/words/:wordId/edit` 无提示失效或用旧保存逻辑覆盖新格式数据。

### 明确不包含

- 后端实现、数据库迁移、OpenAPI 实际发布。
- 内置词典算法、AI 生成质量、真实 TTS/录音/音频上传。
- 学习端字典详情改版。
- 多人实时协作编辑。
- 新语言支持。
- 对原型黄色批注框本身的 UI 复刻。
- 对智能词库列表搜索、批量删除、统计模块的整体重构。

## 数据、兼容性与外部约束

- API proposal 与 mock DTO 字段统一使用 `snake_case`；首版把该 DTO 作为前端稳定的 canonical editor contract，并通过 `AdminWordsDataSource` 隔离传输层。真实 OpenAPI 若发生变化，必须在 data source/adapter 边界映射成该 canonical contract，不能让后端字段变化扩散到步骤组件。
- mock 返回必须与提议的真实接口响应同形；禁止组件直接 import 固定样例数据。
- 草稿中的数组节点使用稳定 ID，排序不能导致关联关系断裂。
- 现有已发布词条和列表读取在迁移期继续兼容；新建向导不得破坏已有删除、筛选和统计。
- 支持当前项目定义的现代桌面浏览器。原型是宽屏后台布局；建议内容区最小宽度 1200px，较窄窗口允许横向滚动/单列降级，不要求移动端适配。
- 页面刷新必须可恢复已经成功保存的步骤；仅存在内存中的未保存输入不承诺跨刷新恢复。
- 列表行必须携带可判别的内容/编辑器版本；旧格式词条继续进旧编辑器，新向导草稿和新格式词条进入新路由。

## 性能与安全

- 输入检测只在用户点击“词典检测”或明确提交时触发，不按每次键入请求。
- 英美切换、Tab 切换和折叠不得重新请求整个词条；深层表单应避免无关区块全量重渲染。
- 单次草稿读写体积和节点上限由后端提案约束；确认前不得在 UI 与 mock 中各自硬编码不同上限，也不得静默截断用户数据。
- 所有文本按普通文本渲染；富文本标记需经过既有安全模型，不注入 HTML。
- mock 仅用于开发/测试构建，生产构建不得静默启用 mock 或伪造“已生效”。
- mock 草稿若为支持刷新而写入 `sessionStorage`，必须带 schema version、按当前管理员隔离并在登出/版本不兼容时清理；组件不得直接读写该存储。
- 不在浏览器存储管理员凭据、词典供应商密钥或后端内部错误详情。

## 可测试验收标准

1. 在智能词库点击“创建单词”进入独立四步向导，第 1 步激活，弹窗不再出现。
2. 输入 `center` 后只在点击检测时调用一次检测接口；展示单词、未重复、`centre / center` 和建议词性。
3. 检测到已有词条时不能进入第 2 步，并能看到重复原因。
4. 检测到英美差异时默认开启区分模式，并标明原输入命中的方言；命中侧只读，另一侧可确认或修正。
5. 进入第 2 步后，每个建议词性直接形成独立 Tab；词性的增删只在第 2 步发生。
6. 同一词性支持多个可排序的词形变化组；`farther/farthest` 和 `further/furthest` 能保存为两组，基准原形不会分叉。
7. 每个词形变化组的“规则变化”以“是/否”保存为布尔值；切换该值不会增删或重排词形行。
8. 当同一词形槽位的 BrE/AmE 拼写不同时，隐藏“英美音标是否有区别”并强制区分音标；拼写相同时显示“是/否”选项。
9. 词形按词性级方言规则显示；语法结构只按第 1 步主词模式显示：主词区分时 BrE/AmE 并列，主词统一时只显示 `common`。
10. 第 3 步可新增、删除、排序词义、释义、例句和三类关联词，并保持稳定 ID；释义支持中文定义、英文定义、中文整句、英文整句四种方式。每条例句自动保存一条不可删除的当前词义主关联，并可增删其他上下文关联。
11. BrE/AmE 视图切换立即展示已存 variant 且不发转换请求；缺失时只有点击“生成建议”才请求转换。语法结构不参与转换，手工目标 variant 未确认前不被覆盖。
12. 任一步保存失败时停留当前步骤并保留值；重试成功后才推进。
13. 刷新带草稿 ID 的后续步骤可恢复最后一次成功保存的数据与当前完成度。
14. 第 4 步能预览前三步数据；缺少必填项时按稳定节点定位，完整时可提交一次。
15. 提交成功使 mock 草稿转换为新格式已发布词条，返回智能词库列表后能看到状态更新；统计重新读取但不会把创建时已计数的词条再加一次。操作变成“查看”并进入 V2 只读预览，不会进入旧整树编辑器。
16. 新接口在 `@tsz/types`、`@tsz/api-client` 有 snake_case 类型和 method/path/body 契约测试；mock 与契约共享类型。
17. admin 单元/集成测试、类型检查、lint 和生产构建通过；关键向导主流程有独立的 admin 浏览器级验证。

## 待产品/后端确认

1. 后续是否把“创建短语”迁移到同一向导；本轮基线不迁移。
2. 未命中内置词典是否允许人工录入并最终生效；本轮基线禁止继续。
3. 词条重复的唯一键：语言 + 类型 + 规范化 headword，还是还包含方言。
4. 内置词典建议数据的真实供应商、覆盖率和质量要求；本轮契约基线要求返回第 2 步所需的词性、词形和音标建议。
5. 英美自动切换的准确字段范围、触发时机、转换接口/数据来源，以及手工内容冲突确认方式；当前原型文字不足以定义可实现的转换规则。
6. “词形是否规则变化”这个布尔标注具体影响哪些下游业务；本轮只存 `true/false`，不推导表单结构。
7. 词形类型是否保持现有枚举；原型中的“三单”等标签是否只改展示文案。
8. 例句上下文关联是否允许只选词条而不选具体词义；主关联已固定为当前词条当前词义。
9. 第 4 步的正式视觉稿；本轮基线为结构化预览、提交后返回列表。
10. 是否需要审核状态；本轮按原型“提交生效”理解为直接 `published`。
