# 新建单词流程重构：需求说明

## 背景与目标

管理后台当前在“词库管理 → 智能词库”中通过弹窗录入 `headword`，立即创建草稿，再跳转到一个整页长表单。新的产品原型要求把“创建单词”改为有明确进度、逐步校验和英美方言联动的四步创编流程：

1. 创建新词条：所属语言、词条录入、词典检测、英美词形确认；
2. 词形与发音：基本词性、词形变化和发音；
3. 词义与例句：语法结构、多维释义、例句和关联词；
4. 预览并生效：字典预览、提交生效。

目标是在 admin 端完成一条可从智能词库列表进入、可连续走完四步、可用 mock 数据演示和测试的单词创建链路。衡量标准：验收场景中的新建单词主流程可从第 1 步走到第 4 步；刷新后仍可恢复已保存草稿；所有步骤都有明确的加载、空、校验失败和请求失败反馈；后续切换真实后端时 UI 不需要改写业务结构。

本轮追加“系统设置 → 词性配置”：基本词性和细分词性不再由创建页面写死，而由统一配置目录提供。词条创建、编辑、列表筛选和预览都读取同一份中文展示名称；后端接口尚未落地时先使用 contract-shaped mock，真实接口提案同步写入 `tsz-rust/docs/frontend-integration.md`。

### A1 的适用范围与遗留工作

A1 在本节确定的是**产品定位**：方言不再是逐词条的检测驱动决策，而是管理员账号级的录入/展示偏好，默认英式。由此**直接成立**的结论：

- 第 3 步（英文释义、英文例句、语法结构）不再按英美分栏，各只维护一份，口径取当前管理员的偏好方言；
- 第 3 步不再有「内容方言」选择器，也不再有跨方言自动补全能力——该能力所依赖的方言转换端点在真实 OpenAPI 中从未存在。

**尚未确定**、留给**第 3 批「A1 英美区分改造」**按 feature 流程（需求 → 技术设计 → 实施）产出的：

- 偏好设置的存放位置（管理员个人设置项 / 后端持久化 / 前端本地）、生效范围与默认值下发方式；
- 第 1 步检测契约 `headwords.mode`、`source_dialect` 与双拼写检测结果的新处理方式；
- 第 2 步词形与音标是否仍保留 BrE / AmE 双栏，以及它与偏好设置的关系；
- 存量 `mode: "distinguish"` 草稿与已发布词条的迁移口径。

在第 3 批落地前，本文档中第 1、2 步的英美相关条款继续描述**现状实现**，仅标注「待 A1 改写」，本轮不擅自改写。

> **A3 的跨文档影响**：`docs/features/admin-word-content-readiness/requirements.md` 目前把词频列为词义的完成条件（「细分词性、等级、可用词频和至少一条中文释义」及其对应验收项）。该表述已被 A3 覆盖——词频缺失不得使词义判定为未完成。为避免与并行推进的其他批次冲突，本轮不改写该文档，由落地 A3 的批次同步修订。

## 目标应用

- 仅 `apps/admin`。
- `apps/web` 的智能词库选词、词表创建和学习端展示不在本需求内。

## 用户与权限

- 沿用现有 admin 登录与路由门禁。
- 沿用当前智能词库的 `words.access` 可见权限；创建、保存和生效是否还需要独立写权限，待后端与权限产品定义确认。
- 无权限、登录过期和后端返回 401/403 时，沿用平台统一鉴权处理，不在页面伪装成功。

## 用户故事

### 1. 从智能词库开始创建

作为词库管理员，我在智能词库点击“创建单词”后，进入独立的新建页面，而不是弹窗。我可以看到四步进度、当前词条摘要和各内容模块的完成状态。

### 2. 创建新词条与词典检测

作为词库管理员，我可以：

- 选择所属语言；首期仅支持 English / 英语，其他语言不可选或不展示；
- 输入词条并发起“词典检测”；输入会去除首尾空格，但不擅自改变大小写；
- 看到词条类型（单词或短语）、智能词库重复检测结果、内置词典匹配结果和建议词性；
- 看到检测给出的词条类型；检测为短语时不能继续单词向导，并提供返回“创建短语”的入口；是否为短语最终以检测结果为准，前端不只依据空格自行拍板；
- 若智能词库已有重复词条，看到明确冲突信息并不能继续创建重复项；
- 若内置词典匹配到英美拼写差异，自动开启“区分英美词形”，展示输入命中的方言；与原输入对应的一侧为检测基准且只读，管理员补充或确认另一侧；
- 若没有英美差异，保持统一词形；本轮不允许在没有检测依据时手工制造英美差异；
- 查看建议的基本词性，然后进入下一步；建议词性直接生成第 2 步 Tab，管理员在第 2 步增删或调整，避免第 1 步和第 2 步出现两个可写来源。

内置词典与智能词库是两个不同检测源：前者提供英美式词形、读音和建议词性；后者检查平台词库中的重复条目。

> **【A1 待改写 · 2026-08-19】** 上面「自动开启『区分英美词形』」「没有英美差异时保持统一词形」两条描述的是**检测驱动、逐词条决定是否区分英美**的现状实现，已被决策 A1 取代（改为管理员个人偏好设置，默认英式）。第 1 步检测契约与方言确认交互的新形态由第 3 批产出，本轮保留原文以对照现状。

### 3. 编辑词形与发音

作为词库管理员，我按基本词性分组编辑词形与读音：

- 新增、切换和删除基本词性；至少保留一个词性，同一词条不能重复添加同一基本词性；
- “添加基本词性”只读取“系统设置 → 词性配置”中维护的基本词性，不显示细分词性；
- 每个词形变化组可配置“词形是否规则变化（是/否）”；该布尔值只作组元数据，不改变表单结构；
- 同一词性可有一个或多个“词形变化组”，用于表达 `far → farther → farthest` 与 `far → further → furthest` 等并行范式；各组可排序、增删；
- 原形在语义上每个词性/各组只有一个基准值。原形拼写只读并从第 1 步主词派生；第 1 组可编辑该词性的原形发音，后续组展示只读镜像，不允许产生彼此冲突的原形；
- 在可判断时显示“英美拼写是否有区别”；区分英美拼写时，英式和美式内容左右并列，并保持词形类型逐行对齐；
- 仅在拼写相同且产品规则允许时配置“英美音标是否有区别”；若拼写已经不同，则不再显示这项选择；
- 每组原形位于首行；其他词形可新增、删除、排序，类型可选择，拼写和读音可编辑；同组双方言行由稳定的词形槽位对齐，不能靠数组下标猜测对应关系；
- 每个词形可维护发音方式、字典音标、实际发音；三者的定义、相互区别与填写规则见「词形发音字段定义（A4 · 2026-08-19 追加）」；
- 试听/生成按钮**接入真实 TTS**（决策 A2），仅在能力确实不可用时——只读态、未配置可用发音人、服务不可用或请求失败——禁用并说明原因；不保留占位提示，也不得在未真正生成时提示成功。这是语音能力在本文档中的唯一口径，验收标准 37 与之一致。
- 区分方言时支持 BrE / AmE 独立音标与实际发音；统一时仅编辑一组 common 内容。

> **【A1 待改写 · 2026-08-19】** 本节「英美拼写是否有区别」「英美音标是否有区别」「BrE / AmE 左右并列」等条款描述的是现状实现。决策 A1 把方言改为管理员个人偏好后，第 2 步是否保留双栏由第 3 批确定，本轮不改写。

### 5. 预览并生效

作为词库管理员，我可以在提交前以结构化字典卡片预览完整词条，看到缺失项定位提示，返回对应步骤修改，并在校验通过后直接提交生效。提交成功后回到智能词库列表，列表出现新词条且统计同步更新。

第 4 步没有随本需求提供视觉稿；首版明确采用后台结构化只读预览，不承诺复刻学习端样式，也不臆造新的业务内容。若后续提供视觉稿，再单独调整呈现层。

### 6. 配置基本词性与细分词性

作为超级管理员，我可以从左侧菜单进入“系统设置 → 词性配置”，统一维护词条创编使用的词性目录：

- 页面内容顶部显示“基本词性 / 细分词性”Tab；两个 Tab 是配置目录的管理视图，不代表单词/短语类型；
- 查看基本词性分页列表，列出中文名、英文名、英文缩写、创建人、创建时间和引用数量；
- 按中文名、英文名、稳定编码或英文缩写搜索；
- 新增基本词性。创建时填写不可重复的稳定编码、中文名、英文名、英文缩写和排序值；
- 修改基本词性的中文名、英文名、英文缩写和排序值；稳定编码创建后不可修改，避免现有词条引用失效；
- 切换到“细分词性”Tab 后，可按所属基本词性筛选，并在当前页面新增、修改、排序或删除细分词性；细分词性同样使用创建后不可修改的稳定编码；
- 当任意草稿、已发布单词或短语已引用某个基本词性时，不能删除该配置，只能修改展示信息；细分词性已被词义引用时同样不能删除；
- 删除未被引用的基本词性前显示二次确认，并同时删除其未被引用的细分词性；服务端/mock 仍需在提交时重新检查引用，防止并发竞态；
- 配置变更成功后，智能词库列表、筛选器和已经打开的词条页面刷新为最新中文名称；词条 wire 只保存稳定编码，不复制可漂移的展示文案。

词性配置页以管理和审计为目的，因此可以显示英文名和缩写；其他词条业务页面默认只显示配置中的中文名。首期仅超级管理员可修改全局配置，普通管理员可读取配置并用于词条创编。

内置词典建议返回稳定基本词性编码。若建议编码未出现在当前配置目录中，前端必须明确提示“词性未配置”并阻止创建草稿，不能静默丢弃或伪造一个词性。

## 词形发音字段定义（A4 · 2026-08-19 追加）

原需求只列出「发音方式、字典音标、实际发音」三个字段名，从未定义其语义——「实际发音」在成为完成词条的硬性阻断项的同时，没有人知道它该由谁按什么规则填什么。本节按决策 A4 补齐定义；A4 的结论是**保留必填，补写定义**，而不是放宽。

| 字段     | wire            | 含义                                                                                                                                               | 来源                                                                            | 必填                           |
| -------- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------ |
| 发音方式 | `style`         | 本条读音属于常规读（`normal`）、强读（`strong`）还是弱读（`weak`）。同一词形可挂多条读音，每条占一行、各有自己的方式                               | 管理员选择，默认 `normal`                                                       | 是（有默认值，实际不构成阻断） |
| 字典音标 | `dict_phonetic` | **内置词典标注的规范音标**，属于外部来源的引用形式，可能带词典排印约定（可选音 `(r)`、并列变体、音节点等）                                         | 检测命中内置词典时预填，词形变体带 `origin: "dictionary"`；未命中时由管理员录入 | 是                             |
| 实际发音 | `actual_pron`   | **本平台对该词形该条读音最终采用的音标**，是下发到学习端、供学员据以模仿的那一份；须为单一、无可选记号、可直接朗读的形式，且与本条「发音方式」一致 | 检测命中时与字典音标同值预填，管理员确认或修正                                  | 是（决策 A4 保留）             |

### 两者的区别

- 字典音标回答「**词典怎么标**」，实际发音回答「**学员按哪一份念**」。
- 二者**允许相同**——检测命中时默认就是相同的。保留两个字段是为了在词典来源可追溯（字典音标不被覆盖）的同时，让平台能给出唯一确定的教学口径（实际发音）。
- 因此「实际发音等于字典音标」不是冗余数据，而是「已确认按词典标注教」的显式表态。

### 谁按什么规则填写

- 责任人是**词库管理员本人**（创建或编辑该词条的账号），不引入额外的审校角色或权限。
- 检测命中内置词典时，管理员的动作是**确认**而非从零录入，这也是保留必填不会显著增加录入负担的前提。
- 需要让实际发音**偏离**字典音标的典型情形：
  1. 字典音标含可选音或并列变体（如 `/ˈsentə(r)/`），须收敛为单一可读形式；
  2. 本条是强读/弱读变体，实际发音按该读法填写，字典音标保持词典原值；
  3. 平台教学口径与词典标注不一致，以平台口径为准。
- 检测**未命中**内置词典时字典音标没有来源，两份都要管理员按平台教学口径自行录入。该场景与「待产品/后端确认」第 1 条绑定，见「阻塞录入可用性的待确认项（A6 · 2026-08-19）」。

### 校验口径

- 基准原形的字典音标与实际发音**两者都必须非空**才算该词性完成——是 AND，不是 OR；派生词形按同一规则。
- 校验提示文案必须与该判定一致，并指明缺失的是哪一个字段、哪一侧方言。当前实现提示「缺少字典音标**或**实际发音」与 AND 判定相反，属实现缺陷（手测报告 B2），由第 1 批修正，本节即其需求依据。

## 主流程

1. 管理员在 `/words` 点击“创建单词”。
2. 系统导航到新建向导并初始化第 1 步表单，此时既不创建草稿，也不写入正式词库。
3. 管理员输入 `center` 并点击检测。
4. mock 返回：类型为单词、智能词库未重复、内置词典匹配到 `centre / center`、建议词性为名词和动词。
5. 管理员确认区分英美词形；系统用检测结果创建草稿，以建议词性初始化第 2 步 Tab，并按现有统计口径把该草稿计入累计/今日/月度创编一次。
6. 管理员完成名词、动词的词形和读音，进入第 3 步。
7. 管理员完成语法结构、释义、例句和关联词，进入第 4 步。
8. 系统展示预览和完整性检查；管理员提交生效。
9. 系统显示成功反馈，更新智能词库缓存并导航回 `/words` 列表。

### 词性配置流程

1. 超级管理员展开左侧“系统设置”，进入“词性配置”。
2. 页面从统一数据源加载基本词性配置；mock 首次使用时预置当前 11 个基本词性及 19 个细分词性。
3. 管理员新增或修改配置；成功后目录缓存失效，所有词条页面后续读取新配置。
4. 管理员点击删除时，页面先根据引用数量禁用明显不可删除的记录；实际删除请求仍由数据源重新检查。
5. 若配置已被单词、短语或词义引用，返回明确的“已被引用，无法删除”结果并保留原记录。
6. 管理员在第 2 步打开“添加基本词性”时，只看到配置目录中尚未被当前词条使用的基本词性，并按配置排序显示中文名。

## 异常与边界流程

- 词条为空、超过 200 字符或语言不支持：不发检测请求，就地提示。
- 检测请求失败：保留输入，展示可重试错误；不产生草稿。
- 用户在检测请求未完成时修改了语言或词条：过期响应不得覆盖新输入，必须重新检测。
- 未匹配内置词典：显示“无匹配”；基线方案不允许继续创建，是否开放完全人工录入仍待产品确认。
- 智能词库重复：显示已存在词条及可跳转入口，禁止继续创建；大小写和首尾空格按后端归一化规则处理。
- 检测结果与输入不一致：必须由管理员确认建议词形，不能静默替换。
- 保存失败：保留当前表单数据，可重试，不推进步骤。
- 草稿加载失败或不存在：提供重试与返回列表；不能用空数据覆盖本地未保存内容。
- 刷新/直接访问后续步骤：有草稿 ID 时恢复服务端/mock 草稿；无草稿时回到第 1 步。
- 跳步：只能进入已经完成或当前可达的步骤。草稿创建后可通过 Stepper 回到只读第 1 步查看检测基准；如需修改语言或主词，必须确认废弃当前草稿并重新检测，避免隐式清空后续内容。
- 提交校验失败：按步骤归类错误并可定位到字段；不丢失草稿。
- 本语言释义缺失或例句未关联所需词义/单词：第 3 步明确标错，第 4 步禁止发布并可跳回对应节点。
- 重复提交：按钮 loading 且禁用；服务端/mock 按幂等语义只生效一次。
- 并发更新：真实接口若返回版本冲突，提示重新加载，不能覆盖他人内容。
- 保存策略：不做逐字段自动保存；“保存草稿”和“下一步”都会保存当前步骤，“下一步”仅在保存成功后导航。带未保存修改离开页面时必须确认。
- mock 模式发布成功：同一 mock 数据源中的列表、统计和详情必须立即可读，不能只弹成功消息却在列表中找不到词条；publish 只改变状态，不让创建时已经计数的统计重复增加。

## 数据、兼容性与外部约束

- API proposal 与 mock DTO 字段统一使用 `snake_case`；首版把该 DTO 作为前端稳定的 canonical editor contract，并通过 `AdminWordsDataSource` 隔离传输层。真实 OpenAPI 若发生变化，必须在 data source/adapter 边界映射成该 canonical contract，不能让后端字段变化扩散到步骤组件。
- mock 返回必须与提议的真实接口响应同形；禁止组件直接 import 固定样例数据。
- 草稿中的数组节点使用稳定 ID，排序不能导致关联关系断裂。
- 现有已发布词条和列表读取在迁移期继续兼容；新建向导不得破坏已有删除、筛选和统计。
- 支持当前项目定义的现代桌面浏览器。原型是宽屏后台布局；建议内容区最小宽度 1200px，较窄窗口允许横向滚动/单列降级，不要求移动端适配。
- 页面刷新必须可恢复已经成功保存的步骤；仅存在内存中的未保存输入不承诺跨刷新恢复。
- 列表行必须携带可判别的内容/编辑器版本；旧格式词条继续进旧编辑器，新向导草稿和新格式词条进入新路由。
- 基本词性和细分词性目录必须有稳定编码。词条的基本词性与词义的细分词性只保存编码；中文名、英文名、缩写和排序由目录读取。
- 默认种子需覆盖现有 `noun`、`verb` 等 11 个基本编码与 `N-COUNT`、`V-T` 等 19 个细分编码，保证存量 mock/legacy 词条可解析。
- 配置中文名、英文名和缩写不能为空；同层级编码、中文名和英文名不允许重复。比较时忽略首尾空格，英文唯一性忽略大小写。
- 词性配置加载失败时，已有词条可回退显示稳定编码并提示目录不可用，但新增基本词性、选择细分词性和确认含未知建议词性的草稿必须禁用。
- V2 语义区间使用独立的 `name_zh`、`name_en` 字段；UI 始终至少保留一个区间且所有词义都有 `sense_group_id`。名称在“保存草稿”时允许一侧暂缺，“完成并进入预览”要求两侧去除首尾空格后均为 1–200 字符。V1 存量词条继续使用既有单 `name` 契约，不在本轮自动迁移或猜测缺失译名。

33. 第 3 步默认展示第一条语义区间的“中文”和“英文”输入，不显示红色必填星号；各行仅在最左侧以圆圈数字 `① / ②` 排序，头部不显示醒目的“必填”标签。保存并刷新后两项均能恢复，词义下拉以“中文名 / English name”展示并仍只保存稳定 `sense_group_id`。任一名称缺失时可保存草稿，但不能完成第 3 步。
34. 每个词义的语义区间不可清空；新增词义默认选择第一个区间。最后一个区间不可删除；删除被引用的其他区间时，经确认把受影响词义改绑到第一个剩余区间。
35. 左侧“完成情况”显示“语义区间”及当前数量；已有 word 时至少与默认首行一致显示 `1`，并在保存后按 canonical word 更新。
36. 语法结构各行仅在最左侧使用圆圈数字 `① / ②` 排序，不显示“结构 N”；卡片头部不显示“英美文本独立维护”。多条结构通过拖动手柄排序，不再显示上下移动箭头；仅有一条或只读时禁用拖动。
37. 语法结构输入沿用上一步发音控件：左侧显示播放图标，输入框右侧显示“获取语音”和“上传语音”图标；编辑态**调用真实 TTS 生成试听**（决策 A2），仅在只读态、未配置可用发音人、服务不可用或请求失败时禁用并说明原因；任何状态下都不出现占位提示，也不得在未真正生成时提示成功。（原文「每个方言输入」随 A1 改为单份输入。）

> **作废理由：**
>
> 1. **前提不再成立**。A1 把英美区分从「检测驱动 + 逐词条决策」改为管理员的个人偏好设置（默认英式），「词义与例句」步骤不再区分英美。本节赖以成立的前提——第 3 步同时存在两份方言内容、需要来回切换并补齐缺失侧——已经不存在。
> 2. **依赖的能力从未存在**。本节 9 条验收标准全部依赖一个「方言转换端点」，而本节「约束与边界」最后一条自己写明「当前真实 Rust OpenAPI 尚无方言转换端点」。这等于写了一整套在真实后端上无法验收的需求，是本轮暴露的最典型的需求缺陷。
> 3. **实测已印证后果**。手测报告 B5 记录：从美式切到英式时缺失侧只显示空输入框，既不提示另一侧已有内容，也没有本节「用户流程」第 6 条要求的「重试补全当前方言」入口——该要求在真实数据源下根本没有落点。
>
> 本节内「开放问题与本轮推荐基线」的 4 条随之关闭，不再作为待确认项跟进。

### 背景与目标

当前英文释义和英文例句分别展示英式、美式两块内容，管理员需要逐字段处理缺失方言。新增一个第 3 步统一方言选择器，让管理员一次选择当前编辑的内容方言；切换到缺失方言时，系统自动利用另一侧已有文本批量补齐，从而减少重复操作。语法结构仍然是人工维护的固定双栏，不被统一选择器控制。

### 目标端

- 仅 admin 的 V2 单词创建向导 `/words/:wordId/wizard/meanings`。
- V1 词条编辑器、web 学习端和短语旧流程不在本次范围。

### 用户流程

1. 主词为英美区分时，第 3 步在“语义区间”卡片上方显示“内容方言：英式 / 美式”，默认选中第 1 步的 `source_dialect`。
2. 英文定义释义、英文整句释义和英文例句只展示当前选中方言的一份输入；中文释义、汉语译文、关系词、语义区间等内容不随选择器变化。
3. 切换方言时，若目标侧全部已有内容，只切换展示，不发请求，也不改变草稿 dirty 状态。
4. 若目标侧存在 `missing`，系统把所有“源侧已就绪且非空”的缺失英文释义和例句合并成一次批量转换请求；成功项直接写入目标 variant，`origin` 标记为 `converted`。
5. 批量补全期间显示当前目标方言的加载状态并暂时禁用再次切换，避免并发响应写错方言。成功后提示补全条数；部分缺失响应只写入匹配成功的项。
6. 没有可用源文本、服务不可用或请求失败时，保留所有原值并给出提示；目标输入仍允许管理员手工填写，并提供“重试补全当前方言”的入口。
7. 新增英文释义或例句时，数据仍按第 1 步源方言初始化；若当前正在查看另一方言，则该字段显示为空并可触发当前方言补全。
8. 语法结构始终同时展示英式和美式输入，继续人工分别维护；切换内容方言、自动补全和重试都不得读取、修改或提交语法结构到转换接口。

### 约束与边界

- 自动补全只处理 `EnglishTextV2`：英文定义释义、英文整句释义、英文例句。
- 自动补全只写 `state: "missing"` 的目标槽位；`ready/manual`、`ready/converted`、`ready/dictionary` 一律保留，避免静默覆盖和源文本修改后的连锁重写。
- 选择器是页面展示状态，不写入 `DraftMeaningsStepContent`，切换本身不产生未保存提示；真正写入补全结果后才标记 dirty。
- 主词为 `unified` 时不显示选择器，继续编辑单一 `common` 文本，也不请求方言转换。
- 保存与发布规则不降低：英美区分词条仍要求所有启用方言的英文释义/例句完整。
- 当前真实 Rust OpenAPI 尚无方言转换端点；真实数据源能力关闭时只能切换已有内容和手工填写，不能伪造自动补全成功。

### 验收标准

- [ ] 英美区分词条显示一个全局“英式 / 美式”选择器，统一词条不显示。
- [ ] 默认方言等于 `headwords.source_dialect`；切换不会改变主词、语法结构或各文本自身的 `source_dialect`。
- [ ] 英文释义和英文例句只显示当前方言，语法结构仍同时显示英式/美式。
- [ ] 目标方言内容完整时切换零请求；存在缺失时同一方向最多发一个批量请求。
- [ ] 批量请求不包含 grammar、中文内容、关系词或已有目标 variant。
- [ ] 成功建议按 `client_id + field_kind` 精确回填并标记 `converted`；缺失、重复或错误类型响应不会写错字段。
- [ ] 手工、词典和已转换目标文本均不被自动覆盖；失败或部分成功时未命中项原样保留且可重试/手填。
- [ ] 自动补全写入后保存草稿、刷新恢复和完成校验均保持双方言内容。
- [ ] 只读页面允许切换查看已存方言，但不发自动补全请求、不显示重试或编辑入口。

### 开放问题与本轮推荐基线

- 自动补全触发时机采用“切换到缺失方言时触发”，不在每次键入或失焦时自动请求，避免频繁调用和竞态。
- 缺失目标没有覆盖风险，因此推荐成功后直接写入，不逐字段弹确认框；任何已有目标 variant 都不自动重新生成。
- selector 推荐为页面级状态，跨所有基本词性 Tab 共用同一个当前方言，减少在不同词性间来回切换。
- 真实转换接口的质量、限流、计费和审计仍需后端确认；能力未开放前只在 contract-shaped mock 中演示自动补全。
