## 1. 执行顺序与负责人

首轮关键路径：

```text
COIN-01 数据模型
    → COIN-02 事务记账
    → COIN-03 本人查询契约          [B1a 验收]
    → COIN-04 注销后端
    → COIN-05 注销前端与兼容验证   [B1b 验收]
    → COIN-06 人工入账/冲正 API
    → COIN-07 C 端钱包 ─┐
    → COIN-08 Admin 钱包┴→ COIN-09 真实联调 [B2 验收]
```

- 当前会话负责总体协调、跨仓契约与验收；任务按后端、共享契约、Web、Admin 划分职责，不把单个页面拆成独立完整工程流程。
- COIN-01～03 已验收完成；本批验收记录见 [b1a-acceptance.md](b1a-acceptance.md)。B1b（COIN-04～05）也已完成验收，见 [b1b-acceptance.md](b1b-acceptance.md)；B2（COIN-06～09）已完成验收，见 [b2-acceptance.md](b2-acceptance.md)。
- 默认串行完成核心、生命周期与共享契约。COIN-06 的接口/类型稳定后，COIN-07/08 具备并行条件；共享的 `packages/types`、`packages/api-client` 同一时段仅一个写入者。
- 每批内部任务在该批任务分支集中完成；按仓库生成必要 PR，不为每个表、接口或页面单开一轮审查、同步和全量测试。
- 任务执行时先核对最新主线已有能力，避免把本次基线之后已合并的实现重做。后端当前本地 main 落后，仅用于本轮只读调查，实施必须从最新 `origin/main` 建独立任务 worktree。

### B1a 的完成边界

- 交付可被业务安全调用的核心和本人查询，不增加业务奖励算法、不做收款页面。
- 可以在隔离测试库直接调用服务验收，不提供临时生产发币接口，也不靠手改余额测试。
- B1b 未完成前不对真实账号开放记账，避免现有立即注销流程与新账本混用。

### B1b 的完成边界

- 延迟注销归属账号模块，钱包只提供事务能力。
- 必须同时覆盖登录、refresh、旧 access token 与敏感写入的锁后到期检查；不能只测试 worker 删除成功。
- 申请/撤销/worker 锁序统一；时间检查用锁后的数据库实际时间，不能被锁等待跨越截止时间绕过。
- 存在申请后不能回退到忽略等待期的旧后端；不因 worker 暂停重新开放账户或延长撤销期限。

### B2 的完成边界

- 首个运营可验收版本：人工发放 → 两端钱包到账 → 查询流水 → 必要时按原单纠错。
- 客服真实联系方式属于上线配置，开发可测试缺省/未配置状态；不编造联系方式，不因此阻塞核心。
- 购买核验只是人工记账依据；不在本批引入支付网关、汇率、退款、图片凭据上传或商城。
- 对外售币建议等首个真实消费路径可用后开放；本批交付不代表词表投币已经能用。

## 5. 状态与交付规则

- 状态只记录真实进展：待开工 → 开发中 → 定向验证通过 → 本批验收完成；“等前置”不代表已经启动后台任务。
- 每批交付记录：实际前后端分支/SHA、修改范围、运行过的验证与结果、未满足依赖、下一批可否开工。
- 使用从最新 `origin/main` 创建的独立任务分支/worktree；不在 main 开发，不覆盖其他任务改动。
- 实现、提交/推送、PR、合并、部署分别按当时用户授权执行；本次安排任务未执行任何外部交付或部署，也未设置定时自动执行。
