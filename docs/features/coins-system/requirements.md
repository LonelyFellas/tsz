## 1. 已确认的目标

- 先建设独立的天生币能力，再接入业务。建议作为现有 Rust 后端的独立模块，不增加独立部署服务。
- C 端用户和管理员各有钱包。C 端同账号的学生、教师身份共用一个钱包；user/admin 是不同身份域，即使手机号相同也不合并。
- C 端获取入口为：完成每日任务、邀请好友、词表获得投币、联系客服购买。
- 首期消费用途只有词表投币：付款方扣币，作者入账，不增加平台总币量。
- 后台提供人工入账页面，可面向 C 端用户或管理员，区分购买入账和人工奖励，记录原因、凭据、操作人、时间。
- Admin 自动获取规则暂未确定；持币资格与查询他人账户、人工发币权限分开。
- 最早可用闭环是：客服核实 → 后台人工入账 → 收款人的钱包余额与流水可见。
- C 端注销不立即生效：申请成功后等待连续 72 小时；有余额必须主动签署放弃余额声明，不同意则不提交申请。用户已确认等待期内可撤销，钱包暂停入账和支出，到期注销并记录余额作废流水；零余额也等待 72 小时。

## 2. 采用的方案与边界

用户已认可上一轮建议；采用以下工程方案。第 5 节区分本轮收口的默认规则和业务接入时仍需补齐的参数，不将未提供的金额或算法视为已经确定。

- 单币种、整数币，不实现小数、提现、在线支付、日常币过期、部分金额冻结、跨账户任意转账或兑换商城。注销等待期的钱包整体暂停和到期余额作废属于本次明确范围。
- 首期不需要消息队列、跨服务事务、通用规则引擎。后续同库业务通过事务内服务调用接入。
- 核心只负责“向谁记账、记多少、来源是什么、不能重复和透支”；奖励条件、金额、每日上限属于对应业务模块。
- 平台发放不需要先建立一个可透支的平台钱包。发行、扣除和转账通过操作类型区分，并可对账。
- 后台已核实购买的记录不等于在线支付订单；后台操作不能自动证明真实付款。
- 未完成的获取途径不展示可成功领取的按钮；可展示说明或未开放状态，具体文案随对应批次落地。
- 第一次接入消费前具备原子转账；不为消费页面提供可任意指定收款人的通用转账 API。

## 3. 基础行为与验收条件

1. 每个 `(owner_type, owner_id)` 最多一个钱包。旧账号初始为零，不从前端 mock 或占位余额迁移数据。
2. 账户第一次访问可以返回逻辑零余额，第一次写账或进入注销生命周期时实际开户；并发开户仍只有一行，零余额开户不伪造流水。
3. 发放、扣除、转账全部产生可追溯流水。余额与流水在同一事务提交，失败不能残留半笔操作。
4. 钱包余额不能为负。转账两边变动额之和为零，并发消费不能超出可用余额。
5. 同一幂等键、相同请求返回原结果；同键不同对象、数量或来源返回冲突。响应丢失后可安全重试。
6. 请求去重与业务去重分别保证。人工购买需稳定核验单号；同一次奖励需稳定事件编号，不能更换请求键再次发币。
7. 普通持币者只能查看自己的账。人工入账服务端实时校验权限，余额变化、流水和审计原子提交。
8. 管理端核验凭据、联系方式、内部备注不能通过个人钱包流水泄露。个人流水仅包含必要的来源说明和时间等公开投影。
9. 钱包和流水不因账号注销而级联删除。停用、注销与在途写账须串行处理；重新注册的新账号不继承旧钱包。
10. 账目修正通过关联原操作的新流水完成，不覆盖余额、不编辑或删除原流水。B2 提供原人工入账的受限全额冲正，规则见第 5 节。
11. 加载失败与真实零余额区分；切换账号清理或隔离钱包缓存，失去权限时停止展示他人账户。
12. 注销签署展示精确余额、放弃声明和 72 小时规则，确认项不能预选。提交时服务端锁账户和钱包核对余额；余额变化需重新展示并签署，不以旧页面金额授权新余额。
13. 待注销期间余额保持不变，包括后台人工入账、冲正、投币和自动奖励都不能绕过钱包暂停。撤销在期限前生效，恢复原余额，不产生作废流水；再次申请重新签署并重新计算 72 小时。
14. 到期依据服务端时间生效，不能依赖浏览器倒计时、进程内计时器或下一次登录。持久申请支持重启恢复和多实例执行；到期后不得继续登录或使用旧 token，余额作废与实际删除幂等完成。
