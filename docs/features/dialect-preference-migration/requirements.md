# 英美方言偏好化改造（A1）：需求评估

> **上游依据**：`docs/test-reports/word-creation-local-2026-08-19.md` 问题 A1 与
> `docs/features/refactor-word-creation/requirements.md`「本轮评审决策（2026-08-19）」。
> 本文是「词条创建流程重构」**第 3 批**的需求评估，只覆盖英美方言这一条线，
> 不重复描述四步向导本身。与 `refactor-word-creation/requirements.md` 冲突时，
> 方言相关条款以本文为准，其余仍以原文为准。
>
> **状态**：2026-08-19 评审通过，进入实施。实施阶段划分见 [`design.md`](./design.md)。

## 背景与目标

### 现状

当前方言是**检测驱动、逐词条决策**的：第 1 步检测出英美拼写差异就自动开启
`distinguish` 模式并要求管理员确认另一侧；第 2 步词形与音标 BrE / AmE 双栏；
第 3 步再叠一个「内容方言」选择器加跨方言自动补全。

2026-08-19 的全流程手测把代价摆了出来：三个步骤各有一套方言语义、
校验错误不指明是哪一侧、切到缺失方言只有一个空输入框、
第 3 步那套「自动补全」建立在一个平台并不具备的「跨方言内容生成」能力之上。
管理员为了录一条 `centre / center`，要做一次模式决策、填两套音标、维护两份释义与例句。

### 目标

把「英美」从**每条词条都要做的决策**降级为**管理员账号上设置一次的偏好**，
让录入者在绝大多数时间里根本不需要想起方言这回事。

具体到可衡量的结果：

- 管理员在个人设置里选一次「英式 / 美式」，默认英式，之后创建词条不再被问到方言；
- 第 3 步（词义与例句）的英文释义、英文例句、语法结构各只有一份输入；
- 第 1 步不再出现「区分英美词形」开关，也不再要求确认另一侧拼写；
- 词典客观存在的双拼写（`centre` / `center`）**不因此丢失**，查重与后续学习端展示不退化。

### 一个必须先说清楚的区分：方言有三层，A1 只动其中一层

改造过程中最容易出错的地方，是把三件不同的事都叫「方言」。本文统一按下面三层称呼，
后续所有结论都挂在这个骨架上：

| 层     | 名称         | 是什么                                                                    | 谁说了算         | A1 的处置                         |
| ------ | ------------ | ------------------------------------------------------------------------- | ---------------- | --------------------------------- |
| **L1** | 词条事实层   | `centre` 与 `center` 是同一个词的两种地区拼写；`centres` / `centers` 同理 | 内置词典（客观） | **不变**，继续记录                |
| **L2** | 管理员偏好层 | 「我按英式录入和查看」                                                    | 管理员本人       | **新增**，账号级，默认英式        |
| **L3** | 内容行文层   | 英文释义、英文例句、语法结构这些**平台自己写的文本**用哪种拼写口径        | 过去是逐词条决策 | **取消分叉**，只写一份，口径取 L2 |

A1 拍板的原话是「英美式区分改为管理员的个人偏好设置，默认英式；词义与例句不再区分英美」——
它取消的是 **L3 的分叉**，新增的是 **L2**。它**没有**、也不应当推翻 L1：
`centre` 和 `center` 是同一个词这件事是词典事实，不会因为某个管理员偏好英式就不成立。
把 L1 一并砍掉会让同一个词裂成两条词条、查重失效、学员搜 `center` 找不到 `centre`，
而且**不可逆**——丢掉的对侧拼写无法从数据里找回来。

## 目标端

- **仅 `apps/admin`**（管理后台，antd v6）。
- `apps/web` 学习端目前**完全没有消费方言数据**（全仓库 `apps/web/src` 内 `dialect`、
  `headword` 命中数均为 0），本改造不外溢到学习端。
  web 端唯一与方言相关的存量工作是 PR #134，其处置结论见技术设计文档。
- 不改 `tsz-rust` 后端。需要后端配合的部分写成提案，由用户转达。

## 用户与权限

- 沿用现有 admin 登录与 `(console)` 路由组门禁，不新增角色。
- 方言偏好是**每个管理员自己的**设置：普通管理员和超级管理员都能改自己的，
  谁也改不了别人的，也没有「平台全局默认方言」这种配置项。
- 偏好只影响**当前管理员看到什么、录入时默认写哪种口径**，
  不改变任何已保存词条的数据，也不改变其他管理员打开同一词条时的数据。

## 用户故事

### 1. 设置我的方言偏好

作为词库管理员，我在顶栏头像菜单进入「个人设置」，看到一项「英语方言偏好」，
可选「英式（BrE）」和「美式（AmE）」，默认英式。改完立即生效，
下次登录、换台电脑仍然是我选的那个。

### 2. 创建词条时不再被问英美

作为词库管理员，我在第 1 步输入 `center` 并检测。系统告诉我：
内置词典识别到这个词有英式 `centre` 和美式 `center` 两种拼写，两种都会记录在这条词条上。
我**不需要**决定"要不要区分"，也**不需要**逐字确认另一侧拼写——那是词典给的事实，不是我的判断。
词条摘要里 `centre` 排在前面并且更醒目，因为我的偏好是英式。

### 3. 录词形与发音时以我的偏好为主

作为词库管理员，我在第 2 步看到的默认是英式那一栏。
美式那一栏折叠着，标明"已填 / 待填"，需要时展开。
如果我漏填了什么，错误提示会直接告诉我"名词 · 复数 · **美式** 缺少实际发音"，
而不是让我在两栏之间猜。

### 4. 录词义与例句时只写一份

作为词库管理员，我在第 3 步看到的英文释义、英文例句、语法结构**各只有一个输入框**。
页面上没有「内容方言」选择器，没有「自动补全 N 项」按钮，也不会出现
"切过去发现是个空框"的情况。我写的英文按英式口径写，因为那是我的偏好。
点「获取语音」时，系统按我的偏好挑英式发音人。

### 5. 打开旧的英美双份词条

作为词库管理员，我打开一条老词条（它在旧版里维护了英式和美式两份释义）。
编辑器按我的偏好只展示英式那一份。在我第一次保存它之前，
系统会明确告诉我：保存后美式的那 N 条内容将不再保留。我确认后才继续。
系统不会背着我删掉任何东西。

## 五个开放问题的产品结论

第 0 批把这五项留给本批。以下是产品侧结论，技术落地方案见 `design.md`。

### Q1 · 偏好设置放在哪里、怎么生效

**结论：账号级偏好，最终形态由后端持久化在管理员档案里；后端就绪前先用浏览器本地存储过渡。**

| 项目       | 结论                                                                                                                                                                                                             |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 归属       | 管理员**个人**设置，不是平台全局配置，也不是词条属性                                                                                                                                                             |
| 取值       | `uk` / `us` 两态，无第三态、无"跟随系统"                                                                                                                                                                         |
| 默认值     | **`uk`（英式）**。从未设置过的存量管理员一律解释为 `uk`                                                                                                                                                          |
| 终态存储   | 后端持久化：`GET /admin/profile` 响应里带出，配一个写入端点。默认值由**后端**下发，前端不做第二处默认                                                                                                            |
| 过渡期存储 | 浏览器 `localStorage`，按当前管理员 ID 命名空间隔离 + schema version。**不在登出时清理**——键已按身份隔离，换账号本就读不到别人的值；清理反而会让偏好每次登出丢失，与用户故事 1「下次登录仍是我选的那个」直接矛盾 |
| 迁移顺序   | 后端字段落地后：以后端值为唯一事实源，本地值降级为离线缓存；首次读到后端值即覆盖本地                                                                                                                             |
| 入口       | 顶栏头像 Popover → 「个人设置」                                                                                                                                                                                  |
| 生效范围   | 当前管理员在 admin 内看到的全部方言相关呈现：创建向导四步、只读预览、词条摘要排序、语音发音人 locale                                                                                                             |
| 不影响     | 已保存的词条数据、其他管理员的视图、学习端                                                                                                                                                                       |

**为什么不选"平台全局配置"**：A1 明说是个人偏好。全局配置意味着一个人改了所有人跟着变，
而且和"默认英式"这句话冲突——全局配置就没有"默认"可言了。

**为什么终态不能停在纯前端本地**：换浏览器、换电脑、清缓存都会静默变回英式。
管理员会以为词条数据变了而不是自己的设置丢了，这是最难排查的一类困惑。
但作为**过渡**它是合适的：它不写任何业务数据，切换零风险，可以让前端先跑起来不等后端。

**在偏好尚未持久化到后端的过渡期，本改造不做任何依赖"所有设备一致"的功能**——
比如不做"按偏好过滤列表"这类会让人误以为数据丢失的能力。

### Q2 · 第 1 步检测契约怎么处理

检测接口仍会返回 `headwords: { mode: "distinguish", uk, us, source_dialect }`——
这是后端依据内置词典的地区证据算出来的（已核对本地库中 `colour / color` 的真实
`detection_snapshot`）。前端不改后端行为，也不该把它丢掉。

**结论：事实照收、决策取消、呈现按偏好。**

1. **`headwords` 判别联合原样保留，双拼写照原样落库**。
   这是 L1 事实层，不属于 A1 的处置范围（理由见「背景与目标」）。
2. **取消管理员的方言决策**：删掉「区分英美词形」开关，删掉"确认另一侧词形"的可写双输入框。
   检测给出对侧就直接采用，UI 降级为一行只读事实说明：
   > 内置词典识别到该词有两种地区拼写：**centre**（英式）/ **center**（美式），两者都会记录在这条词条上。
3. **主次按偏好排**：偏好侧排前、字号更大；另一侧作次要信息。
   这顺带闭合手测 **C5**（`centre` 排在 `center` 之前被误读为"主词被静默替换"）。
4. **`source_dialect` 语义不变**，仍表示"本次输入命中的是哪一侧"，
   用于追溯"管理员当时输入的是什么"；但它**不再决定任何内容口径**。
   偏好侧与 `source_dialect` 不一致（偏好英式却输入了 `center`）是完全正常的，
   不提示、不阻断、不改写输入。
5. **对侧拼写有误怎么办**：走既有的"废弃草稿、重新检测"路径。
   第 1 步不再提供自由编辑对侧拼写的入口。若实测中词典对侧出错的比例偏高，
   再单独评估是否开放"修正对侧拼写"（列入开放问题）。
6. **词条重复唯一键维持现状**（关闭 `refactor-word-creation/requirements.md`
   待确认第 2 条）：唯一键**包含方言**，即
   `(语言, 类型, 方言 scope, 归一化 headword)`。后端 `entry_headword_keys`
   已按 `uk` / `us` 两个 scope 各占一行（统一词条两行同值、区分词条两行不同值），
   正因为保留 L1 双拼写，`centre` 与 `center` 才会被判为同一条词条。
   **这条唯一键的正确性直接依赖于结论 1**——若把双拼写砍掉，查重立刻退化。

### Q3 · 第 2 步的 BrE / AmE 双栏是否保留

**结论：保留双栏的数据与能力，改成「偏好侧主导 + 对侧折叠」的呈现；不砍对侧。**

| 决定                                | 说明                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------- |
| 双栏数据保留                        | 词形拼写与音标属于 **L1 事实层**，不是行文口径                                  |
| 默认只展开偏好侧                    | 对侧折叠为一行摘要（"美式：3 项已填 / 1 项待填"＋展开按钮）                     |
| 统一词条完全无方言                  | 单拼写词条（绝大多数）连折叠区都不出现，界面上没有任何方言字样                  |
| 校验提示必须指明"哪一侧 + 哪个字段" | 闭合手测 **C4**；与第 1 批修 **B2**（"或"实为"且"）的改动同一处代码，需协调先后 |
| 「生成英式 / 美式建议」按钮保留     | 见 Q5                                                                           |
| 发布仍要求两侧完整                  | 这是**后端硬约束**（已核对），前端放宽了也发布不了                              |

**为什么不砍对侧**：`centres` / `centers`、`/ˈsentə/` / `/ˈsentɚ/` 和主词双拼写是同一类事实。
砍掉等于平台记不住"美式怎么拼、怎么读"，而这正是学习端将来要展示的内容。
更现实的一点：后端校验强制 `distinguish` 词条的每个词形槽位必须有 uk 和 us 两行、
且每行的字典音标与实际发音都非空——前端单方面砍掉对侧，词条会直接发布失败。

**遗留痛点如实记录**：对侧音标的录入负担并没有被本轮消除。
如果实际使用中它才是最大的成本，正确做法是**单独提一个后端提案**把非偏好侧的
`pronunciations` 放宽为选填，而不是在前端假装它不存在。本轮不做，列入开放问题。

### Q4 · 存量 `distinguish` 数据怎么办

**事实基础**（2026-08-19 在本地 Docker `tsz-rust-db-1` / 库 `tsz_rust` 只读查询）：

| 指标                     | 数量                                                                     |
| ------------------------ | ------------------------------------------------------------------------ |
| `lexicon.entries` 总数   | 14                                                                       |
| 其中 `mode: distinguish` | **2**（`centre / center` 已发布且有未发布修改；`colour / color` 纯草稿） |
| 其中 `mode: unified`     | 12（2 条已发布）                                                         |
| `text_variants` 方言分布 | `common` 104 / `us` 12 / `uk` 9                                          |
| `form_variants` 方言分布 | `common` 45 / `us` 9 / `uk` 9                                            |

测试服 `tshb-test` 的前端栈已于 2026-07-26 整体拆除，当前只有后端裸跑，
平台尚无生产环境。也就是说：**全平台的存量 `distinguish` 词条是个位数，且全在本地开发库里。**

**结论：不写迁移脚本，不做批量转换；改用"编辑时随手收敛"（lazy migration），且绝不静默丢数据。**

1. **`distinguish` 词条改造后仍是合法的一等公民**（L1 不变），不存在"旧格式词条"，
   因此没有"必须迁移否则打不开"的问题。列表、只读预览、发布状态都不受影响。
2. 需要收敛的只有 **L3**：存量 `distinguish` 词条里已经存在的英式 + 美式两份
   英文释义 / 英文例句 / 语法结构。
3. 打开这类词条的第 3 步时：**按偏好侧取那一份作为唯一内容**展示与编辑，
   顶部给一条一次性说明条：
   > 这条词条在旧版里维护了英式和美式两份英文内容。现在统一按你的偏好（英式）维护一份。
4. **第一次保存前必须显式确认**，把要丢弃的内容数量说清楚：

   > 保存后，这条词条的 **美式** 英文释义 2 条、英文例句 3 条、语法结构 1 条将不再保留；
   > 英式内容会成为唯一内容。确认继续？

   > **【阶段 3 修正 · 2026-08-20】** 初稿写的是「语法结构不受影响」，那是错的：
   > 语法结构保存时按偏好侧镜像写两条，非偏好侧写过的**不同**文本会被覆盖，
   > 同样是丢数据。它必须计入确认框（只在两侧文本确实不同时计入；空的、
   > 或本来就是镜像的不打扰管理员）。
   > 管理员取消则不保存、不改动任何数据。这条是硬性的——
   > `refactor-word-creation/requirements.md`「数据、兼容性与外部约束」写明"不得静默截断用户数据"。

5. **不主动触碰未被编辑的词条**：没人去编辑，它就一直保持双份，只读预览照常显示两份。
6. **已发布的 `distinguish` 词条不因本改造重新发布**、状态不变、不产生新 revision。
7. 本地开发库那两条测试数据由开发者按需自行清理，不属于产品流程，也不写进任何脚本。

### Q5 · 已落地的方言建议能力怎么办

**结论：能力保留，第 3 步的调用全部删除，第 2 步的调用全部保留。**

判定依据（已核对 `tsz-rust` 的真实实现，非推测）：
`POST /admin/lexicon/dialect-variant-suggestions` 是一个**确定性的地区拼写替换**——
它拿输入文本里的英文 token 去内置词典的地区词表里找证据，找到对应关系才做替换
（`colour` → `color`），找不到就什么都不返回。它**不生成内容**，也不会"翻写句子"。

也就是说，它回答的问题是「**同一个词在另一侧地区怎么拼**」——这正是 **L1 事实层**的问题，
恰好是第 2 步词形拼写要解决的。A1 取消的是 **L3 内容层**的方言分叉，两者不是一回事。

逐个落点的处置：

| 落点                                                                      | 处置         | 说明                                                                             |
| ------------------------------------------------------------------------- | ------------ | -------------------------------------------------------------------------------- |
| 后端 `POST /admin/lexicon/dialect-variant-suggestions`                    | **保留**     | 不提议下线；不需要任何后端改动                                                   |
| `packages/api-client/src/admin.ts` 的 `suggestDialectVariants`            | **保留**     | 请求层不变                                                                       |
| `dataSource.ts` 的 `dialectVariantSuggestions: true` 开关                 | **保留**     | 含义收窄为"词形拼写建议可用"                                                     |
| `FormsAndPronunciationStep.tsx` 的 3 处引用（第 2 步"生成英式/美式建议"） | **保留**     | 这是它真正的用武之地                                                             |
| `MeaningsAndExamplesStep.tsx` 的 4 处引用（第 3 步内容自动补全）          | **全部删除** | 连同内容方言选择器、批量补全、重试入口一并删除                                   |
| `model.ts` 中服务于第 3 步的方言批处理函数                                | **删除**     | collect / chunk / apply / count 四组                                             |

## 功能范围

### 本轮包含

- 管理员个人方言偏好：设置入口、读写、默认英式、按管理员隔离的持久化（过渡期本地）。
- 第 1 步：删除「区分英美词形」开关与对侧可写输入，改为只读事实说明；主次按偏好排序。
- 第 2 步：偏好侧主导 + 对侧折叠的呈现；校验提示指明方言侧。
- 第 3 步：删除内容方言选择器、自动补全、重试入口；英文释义、英文例句、语法结构各一份输入。
- 语音发音人按偏好选 locale（英式 → `en-GB`、美式 → `en-US`），覆盖第 2、3 步的"获取语音"。
- 存量 `distinguish` 词条的懒收敛：偏好侧展示 + 首次保存前的显式确认。
- 左栏词条摘要、完成情况、第 4 步只读预览的方言呈现同步收敛。
- mock 数据源、契约测试、e2e mock 与用例同步。
- 后端提案（偏好持久化、语法结构方言校验放宽、列表 headword 结构化）写入技术设计文档，由用户转达。

### 明确不包含

- 后端实现、数据库迁移、OpenAPI 实际发布（一律只出提案）。
- 学习端（`apps/web`）任何改动；PR #134 的代码本轮不动，只给处置结论。
- 「平台全局默认方言」这类管理配置。
- 把非偏好侧的音标改为选填（需要后端配合，本轮只记录为开放问题）。
- 第 1 步开放"手工修正对侧拼写"。
- 批量迁移脚本、存量数据清洗命令。
- 手测报告里 A2 / A3 / A4 与 B、C 两类问题——分属第 1、2、4、5 批，不在本文范围。

## 异常与边界流程

| 场景                                                     | 期望行为                                                                                       |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 偏好读取失败 / 本地存储不可用（隐私模式、配额满）        | 按默认 `uk` 工作，不阻断任何流程，不弹错误对话框；仅在开发构建里打一条 warn                    |
| 偏好写入失败                                             | 就地提示"偏好未能保存"，UI 回退到写入前的值，不留下"看着改了其实没存"的假象                    |
| 偏好在另一个标签页被改动                                 | 本轮不做跨标签页同步；当前页保持既有值，刷新后取最新。不做乐观广播，避免半途改变正在编辑的口径 |
| 检测返回 `unified`（无地区差异）                         | 全程不出现任何方言字样；偏好在这条词条上只影响语音 locale                                      |
| 检测返回 `distinguish`，但偏好侧与 `source_dialect` 不同 | 正常继续，不提示、不阻断、不改写管理员输入。摘要按偏好排序，`source_dialect` 只用于追溯        |
| 存量 `distinguish` 词条，偏好侧内容为空、对侧有内容      | 编辑器展示空输入（偏好侧就是空的），**不自动搬运**对侧文本。管理员可自行复制；不做任何隐式填充 |
| 存量 `distinguish` 词条被打开但未做任何修改              | 不弹确认框、不保存、不产生 revision。确认框只在真正触发保存时出现                              |
| 存量收敛确认框被取消                                     | 保持未保存状态、保留全部输入，不推进步骤，可再次尝试                                           |
| 语音：偏好对应 locale 没有可用发音人                     | 沿用既有"暂无可用发音人"的禁用与说明，不静默降级到另一个 locale 而不告知                       |
| 已发布词条继续编辑                                       | 与草稿同一套口径；确认框在"首次保存这条词条的新 revision"时出现一次                            |
| 只读预览（第 4 步 / 已发布详情）                         | 按偏好侧展示单份内容；存量双份词条在只读态**仍展示两份**并标注方言，因为只读不涉及丢弃         |

## 可测试验收标准

**偏好本身**

1. 顶栏头像菜单里能进入「个人设置」，看到「英语方言偏好」，两个选项，默认选中「英式」。
2. 切换到「美式」并刷新页面后仍是「美式」；退出登录再用**另一个**管理员账号登录，看到的是该账号自己的偏好（新账号为默认英式），不串号。
3. 清空浏览器存储后重新进入，偏好回到默认「英式」，且不报错、不阻断任何页面。

**第 1 步**

4. 创建向导第 1 步**不存在**任何名为「区分英美词形」的开关或复选框。
5. 检测 `center` 后，页面以只读方式说明该词有 `centre`（英式）/ `center`（美式）两种拼写；两个拼写都**不可编辑**。
6. 偏好为英式时，词条摘要中 `centre` 在前且更醒目；切换偏好为美式后重新进入，`center` 在前。
7. 创建出的草稿其 `headwords` 仍为 `{ mode: "distinguish", uk: "centre", us: "center", source_dialect: "us" }`，与检测结果一致。
8. 检测 `banana`（无地区差异）时，第 1 步全程不出现"英式""美式""方言"任何字样。

**第 2 步**

9. `distinguish` 词条的第 2 步默认展开偏好侧一栏，非偏好侧折叠并显示"已填 / 待填"计数，可展开。
10. `unified` 词条的第 2 步没有任何方言分栏或折叠区。
11. 缺少音标时，错误提示同时指明**方言侧**与**字段名**（如"名词 · 复数 · 美式 · 实际发音"），点击可定位到该输入框。
12. 「生成英式 / 美式建议」按钮仍在，点击后弹确认框展示源词形与建议词形，确认后写入，且不覆盖已有内容。

**第 3 步**

13. 第 3 步**不存在**「内容方言」选择器、「自动补全 N 项」按钮和「重试补全」入口。
14. 每条英文释义、每条英文例句、每条语法结构都只有**一个**输入框；页面上不出现"英式 / 美式"分栏标题。
15. 新建词条完成第 3 步并发布后，其英文释义与例句的 wire 为单份形态；改动偏好后重新打开，内容不变（偏好不改写已存内容）。
16. 第 3 步的「获取语音」按偏好选 locale：偏好英式时请求 `en-GB` 发音人，美式时 `en-US`。

**存量数据**

17. 打开一条存量 `distinguish` 且第 3 步有双份内容的词条，编辑器只展示偏好侧那一份，顶部有一次性说明条。
18. 首次点击"保存草稿"或"完成并进入预览"时弹出确认框，明确列出将不再保留的内容条数与方言侧；取消则不保存、数据不变。
19. 确认后保存成功，再次打开不再出现说明条与确认框。
20. 未被编辑的存量 `distinguish` 词条，在列表和只读预览里表现与改造前一致，不报错、不丢字段。

**不回归**

21. 智能词库列表的「方言」列仍能显示 `英式 / 美式`，筛选与统计不变。
22. 检测到智能词库重复时的阻断行为不变；`centre` 与 `center` 仍被判为同一条词条。
23. `pnpm test:cov`、`pnpm typecheck`、`pnpm lint`、`pnpm build` 全绿，覆盖率不低于既有门槛。
24. `packages/api-client` 契约测试与 `openapi.snapshot.json` **无需变更**即可通过（本轮不改任何已有 wire 契约）。

## 存量数据的产品处置口径（管理员会看到什么）

一句话：**旧词条照常能开、能看、能发布；只有在你主动编辑并保存它的第 3 步内容时，才会问你一次要不要收敛，问清楚了才动。**

| 时机                              | 管理员看到的                                                                |
| --------------------------------- | --------------------------------------------------------------------------- |
| 列表里看到存量 `distinguish` 词条 | 与改造前一致：方言列显示 `英式 / 美式`，状态、统计、操作都不变              |
| 打开只读预览                      | 两份英文内容都能看到，各自标注方言。只读不丢数据，所以不做任何收敛          |
| 进入第 3 步编辑                   | 只展示偏好侧一份 + 顶部一条说明："旧版维护了两份英文内容，现统一按英式维护" |
| 偏好侧那份是空的                  | 就是空输入框。系统不会把美式内容搬过来冒充英式，也不提示"另一侧有内容"      |
| 第一次点保存                      | 确认框，写明"美式英文释义 2 条、英文例句 3 条将不再保留"，可取消            |
| 确认保存后                        | 说明条与确认框消失；这条词条从此只有一份英文内容                            |
| 从头新建的词条                    | 全程没有任何双份内容的概念，也永远不会遇到这个确认框                        |
