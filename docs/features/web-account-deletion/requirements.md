# C 端账号注销需求评估

## 背景与目标

C 端已有账号注销入口和旧版验证码表单，但尚未完整对接 tsz-rust 已部署的 RFC 9457 契约，也缺少足够明确的高风险二次确认和完整会话清理。本功能让已登录用户可通过账号现有手机号或邮箱完成不可恢复的账号注销，并保证成功后客户端立即退出认证态。

## 目标端

web（C 端，Next App Router + `@tsz/ui`）。本次不改 admin。

## 用户故事 / 使用场景

- 已登录用户进入账号注销页，先看到不可恢复、数据会清除的风险说明。
- 用户只能从账号实际已绑定的手机号/邮箱中选择验证渠道；前端不提交 target 或 purpose。
- 用户申请验证码后输入六位数字验证码，再通过最终确认层明确同意永久注销。
- 请求期间不能重复发送或重复注销；失败后保留安全、可重试的状态。
- 注销成功后，用户的 access token、刷新定时器、用户缓存与认证状态被清除，并整页跳转登录页。
- 开发测试用户能看到当前测试环境固定验证码 `000000` 的合理提示；该提示不成为 API 或验证逻辑中的业务常量。

## 功能范围

### 本次范围内

- 对接 `POST /api/v1/auth/account/deletion-code`（202 空响应）。
- 对接 `DELETE /api/v1/auth/account`（204 空响应）。
- 依据当前用户资料展示可用 phone/email 渠道。
- 验证码申请、倒计时、输入校验、最终确认、请求中禁用和失败恢复。
- 按 RFC 9457 稳定 `code` 映射指定错误与通用错误。
- 成功后完整清理本地认证状态并整页跳转。
- 更新 types/api-client/OpenAPI 快照、mock、契约/组件/e2e 测试。
- 窄屏和键盘/读屏可访问性验证。

### 明确不做

- 不向后端提交联系方式 target 或 OTP purpose。
- 不在生产 UI 或生产请求中 mock 验证码。
- 不修改后端实现、验证码策略或联系方式绑定能力。
- 不 commit、push、创建 PR 或部署。

## 约束与边界

- 仅 Bearer 鉴权用户可操作；路由继续由客户端 `RouteGuard` 保护。
- 注销不可恢复，最终 DELETE 前必须有独立确认动作。
- 渠道只取当前账号已有联系方式；没有可用渠道时展示不可操作状态。
- 验证码当前测试环境固定为 `000000`，但 API 请求和表单校验只依赖“六位数字”，便于后端日后替换。
- 401 `invalid_token` 按会话失效处理；401 `invalid_account_deletion_code` 只提示验证码错误，不误清有效会话。
- 所有错误分支依据 `HttpError.code`，不得依赖可变 `detail/message`。

## 验收标准

- [ ] 仅提交 `{channel}` 申请验证码，成功接受 202 空响应。
- [ ] 仅提交 `{channel, code}` 注销账号，成功接受 204 空响应。
- [ ] 可用渠道来自当前用户 phone/email，单渠道不出现无效选项，双渠道可切换。
- [ ] 页面清晰说明注销不可恢复和数据后果，DELETE 前有最终确认。
- [ ] 验证码格式不合法、未确认、请求进行中时不能提交；重复点击只产生一次请求。
- [ ] 指定 401/409/429/503 和通用 400/422/500/未知错误均有可理解反馈并可安全重试。
- [ ] 注销成功清 access token、刷新定时器、用户/角色/onboarding 状态，停止认证态请求并整页跳转登录页。
- [ ] 开发测试提示 `000000` 与业务校验解耦，生产 API 不走 mock。
- [ ] 关键契约、组件状态与 e2e 主流程有自动化覆盖，质量门通过。
- [ ] 窄屏布局无横向溢出；交互可用键盘完成，确认层有 dialog 名称、描述和焦点管理。

## 开放问题

无阻塞开放问题。测试码提示按当前产品阶段常显为“开发测试提示”，未来后端切换真实 OTP 时可独立移除文案，不影响请求契约。
