# 关联词不存在时创建草稿并关联：需求评估

## 背景与目标

来源：2026-08-20 智能词库系统测试报告的「大功能待办」，报告里标注为**新增功能、待产品确认**，不是缺陷。

当前限制（报告实测）：在「词义与例句」里加近义词/反义词/派生词时，只能从**已发布**的词条及其词义里选。输入词库外的 `reliability`，下拉提示「未找到匹配词条」，「匹配词义」保持禁用，**没有任何办法把它存下来**。

这对录入是硬伤：关联词天然成对成群出现。录 `testability` 时想到近义词 `reliability`，但 `reliability` 还没进库——管理员只能中断当前工作，去新建 `reliability`、录完、发布，再回来接着录。一条词条的录入被另一条词条的完整生命周期卡住。

目标：**关联词不在库里时，能就地把它建成草稿并关联上**，当前词条的录入不中断。被关联的草稿之后再补录、再发布。

成功长什么样：管理员在 `testability` 的近义词里输入 `reliability`，下拉提示「词库中没有，创建草稿并关联」，点一下就建好并选中，继续录下一个关联词；`reliability` 出现在智能词库草稿列表里，之后有人接手补录。

## 目标端

**admin**（管理后台，antd v6）。web 端不涉及。

**需要后端配合，且这是本功能的前提**——当前后端在**保存草稿**时就要求关联目标必须是已发布词义，不改后端的话前端无法落地（详见技术设计文档）。**上线顺序必须后端先行**：发布接口入参带 `deny_unknown_fields`，前端先发新字段会让 publish 直接 400。

## 用户故事 / 使用场景

1. **就地创建**：管理员在近义词输入 `reliability`，词库中没有 → 下拉给出「创建草稿并关联」的入口 → 点击后创建词条草稿、自动选中其默认词义、回填到当前关联项 → 管理员继续录入，不跳页。
2. **命中重复**：管理员输入的词其实已存在（已发布或已有草稿）→ **不重复创建**，直接把已有的列出来供选择。
3. **同形确认**：要创建的词与库里已有词条同形 → 走现有的同形确认流程，确认后才创建。⚠️ 撞的若是**同词头**（ExactHeadword），当前后端策略默认关闭，确认了也建不出来——见「待产品确认」。
4. **回头补录**：管理员事后在智能词库列表看到这条新草稿，点「继续创建」进去补齐；也能从原词条的关联项直接跳过去。
5. **发布把关**：当前词条要发布时，如果它的关联目标还是未发布的草稿 → 照常发布，但**发布前一次性列清单并要求明确确认**；关联**保留在草稿里**，目标发布后回到本词条重新保存词义步、再提交生效即可带上（见决策记录 1）。

## 功能范围

**做**：

- 关联词搜索无结果时，提供「创建草稿并关联」入口。
- 创建前检查重复：已发布词条与既有草稿都要查，命中就引导选择而不是新建。
- 创建后自动选中新草稿的默认词义，回填当前关联项（词条 ID + 词义 ID 都要落实）。
- 从关联项能跳到该草稿继续补录。

**不做**：

- **不在本功能里补录被关联词的内容**。只建草稿骨架，内容由之后单独补。
- 不做批量创建、不做「一次输入多个关联词」。
- 不改关联词的类型（近义/反义/派生）与分值机制。
- 不改已发布词条的关联行为。
- **不放宽发布门**——发布仍要通过完整性检查。指向草稿的关联不进发布引用表、对外不生效、不阻断发布，但必须显式确认（决策记录 1）；这不是「关掉校验」。
- **不做「目标发布后自动补进已生效快照」**（方案 C）。本次只保证关联留在草稿里，为它留出后续增量实现的空间，见决策记录 1。

## 约束与边界

- **重复入库是硬约束**：报告明确要求「创建前检查已发布词条和既有草稿，避免重复入库」。好消息是这套机制已经存在（智能词库重复检测 + 同形确认），要复用而不是另造。
- **关系必须存明确的 ID**：报告要求「草稿关系必须保存明确的词条 ID 和词义 ID」，不能退化成自由文本。现有 wire 类型 `WordRelationV2` 的 `target_word_id` / `target_sense_id` 都是必填，天然满足。
- **当前后端不允许关联未发布词义**——保存草稿时就会报 `relation_target_unavailable`（422）。这是本功能最大的前置依赖。
- 权限不变，不引入新角色。
- 新建的草稿归属、创建人按现有规则走。

## 验收标准

- [ ] 关联词搜索无结果时，出现「创建草稿并关联」入口（而不是只有「未找到匹配词条」）。
- [ ] 点击后创建成功，当前关联项自动填上新草稿的词条与词义，无需手动再选。
- [ ] 创建过程中不离开当前页面，已录内容不丢。
- [ ] 输入的词已存在（已发布或已有草稿）时，**不新建**，列出已有项供选择。
- [ ] 与已有词条同形时走同形确认流程。
- [ ] 创建时撞上同词头且策略未开启（409 `exact_headword_creation_temporarily_disabled`）→ 给出可读说明与「去选已有词条」的出路，不是通用报错。
- [ ] 新草稿出现在智能词库草稿列表。
- [ ] 能从关联项跳到该草稿继续补录。
- [ ] 保存当前词条的词义步成功（不是 422）。
- [ ] 关联目标是草稿时，关联行**常驻**显示「草稿」标记与「去补录」入口（不是悬停才出现），且不进「完成情况」面板、不计入待修项。
- [ ] 发布时若存在指向草稿的关联，点「提交生效」后弹出确认，**逐条**列出关联类型 / 目标词 / 所在词义；确认后才发布，取消则不发布。
- [ ] 发布成功后这些关联**仍在草稿里**——重新进入词义步能看到它们，只是不进发布引用表、对外不生效。
- [ ] 目标词条被归档时按待修项处理：发布被阻断，提示指向**恢复目标词条**（而不是要求重选关联），且能从提示定位到那一行。
- [ ] 目标词义被移出目标草稿、且不在目标当前发布里时按待修项处理：发布被阻断，要求重选，且能从提示定位到那一行。
- [ ] 新草稿没有任何词性与词义时（判据是 `word.meanings.pos` 为空数组），界面明确说明「已建草稿但没能关联上」并给出补录入口，不留一条会被静默丢弃的半成品关联。

## 决策记录

原开放问题 1–4 已评估并定案（2026-08-21）。

### 决策 1（关键）：关联目标是草稿时，**显式**发布——保留、不生效、发布前逐条告知

**规则**：

> 关联**保留在草稿里**（不删、不改）；未解析的关联**不进发布引用表**（`entry_publication_sense_refs`）因而对外不生效——但仍逐字留在 `publication.snapshot` 里，后端已确认无需剔除；**发布前明确列出哪些不会生效**并要求确认；目标词条发布后，回到本词条的「词义与例句」重新保存一次，再提交生效即可带上。

即评估时的**方案 B，但做成「显式 B」**。

**理由**：

1. **方案 A（阻止发布）在放宽保存后会引入一个带环的门，而且这个环没有自救路径。** 准确地说，死锁不是今天就有——今天连保存都不允许，问题被更早的一道墙盖住了；一旦为本功能放宽保存，A 就是在原地重新砌起一道等价的墙。近义词天然互指，`testability ↔ reliability` 互为近义词是极自然的录入，此后两条词条都发不出去，管理员唯一的出路是删掉一边的关联——即销毁自己刚录的成果。
2. **A 在「本轮就要发货」的约束下，破环手段只剩 B。** 理论上 A 有两个收敛方向：B（先发、这条关联不生效）和 C（关联挂起、目标发布后自动补进快照）。C 要新的挂起模型与回填触发，工作量正是我们说「以后再加」的那一份；在本轮不做 C 的前提下，A 的破环手段只可能是 B——只是由人手动触发，且中间先让管理员撞一次墙。终点相同，不如直接做 B。
3. **A 还会把发布门从「本词条自洽」改成「依赖别人的生命周期」。** 后端对跨词条耦合本来就很谨慎：发布路径已经有一条反向耦合——`sense_has_inbound_publication_refs`（我的词义被别人的当前发布版本引用时，阻止我发布）。再加一条正向耦合，两条叠起来能绕出更长的环（A 的关联指向 B，同时 B 的发布版本又引用了 A 的词义）。
4. **C 是 B 加自动化，能后续增量实现——前提正是「关联保留在草稿里」。** 这个前提成立时，后端已有的解析代码就是天然的增量点：`resolve_meaning_references` 在发布时走 `Verify` 模式，对解析不到的关联只是不产出 `entry_publication_sense_refs` 行；要升级成 C，只需让它对「上次未解析、这次能解析」的关联做一次 canonicalize 而不是报错。所以现在做 B 不是妥协，是分期。
   - 需要说清楚的是 **C 有两档**：**C1**「目标发布后，本词条下次发布自动带上，不用人工重存词义步」——沿用现有快照机制，改动小；**C2**「目标发布即回填已生效的发布快照」——要改已生效版本，成本明显大得多。「以后再加」指的是 C1。别把 C 想成 C2 再据此判 B 是权宜之计。
5. **B 原本的缺点几乎全部来自「悄悄」，不来自「消失」。** 做成显式的就不成立了：录入时关联行上有常驻的「草稿」标记（交互设计 1），发布前有逐条清单的一次性确认（交互设计 2）。
6. **但 B 有一处缺点不是「悄悄」带来的，得单独兜**：学习端会有一段时间看到残缺的近义词，而「回来重发一次」这件事没有载体，容易永远没人做。兜底见交互设计 1 的第三态——目标发布后关联行自己变成「已发布 · 重新保存后可生效」，把待办摆回管理员眼前。这一条成本极低（同一个标记的另一个取值），但它补的正是 B 唯一的真缺口。

**用词修正（后端核验后再修一次）**：评估阶段的说法是「目标发布后重新发布本词条即可带上」，这不准确；本文档上一版据此改称「不重存直接发布会撞 `relation_target_stale` 的 422」，**这同样不对，而且实际后果更糟**。`publishing.rs:155` 有一条短路——源词条的 `revision` 与当前发布的来源 revision 相同时（即发布后没再保存过），publish 直接返回 201 `Published` 并 `return`，**位置在引用解析之前**；而 publish 全程不改 `entries.revision`。所以目标发布后，源词条若没重存过，再点「提交生效」**既不产生新发布、也不报任何错**：响应里 `status=published`、`has_unpublished_changes=false`，管理员完全看不出异常。而 `validate` 没有这条短路，于是当前是「点校验能看到问题、点提交生效却一切正常」。

正确操作不变——**先回词义步重新保存一次，再提交生效**，界面文案必须这么写。但**不能指望后端报错兜底**：这件事只能靠交互设计 1 的第三态（`resolvable`）主动摆出来，它因此从「可裁」升为**必需**。后端会调整这条短路（让它对「有已变得可解析的关联」不再静默通过），具体行为联调时对齐。

**硬依赖（已确认成立）**：**关联必须保留在草稿里。** 后端已答复：不删、也不必从发布快照里剔除（见「后端答复」第 1 条）。原先「若后端在发布时删掉未解析关联，则交互设计 1 与 2 作废」的风险**已排除**。

### 决策 2：默认词义取后端返回的第一条；候选全列出来；无词义时不硬造关联

**做法**：

- 就地创建成功后，把新草稿 `meanings.pos[*].senses[*]` **全部**装进该关联行的「匹配词义」候选（复用现有 `senseChoices` 机制），默认选中**第一条**，管理员可改选。
- 候选文案复用现有兜底 `gloss || "（无释义）"`（`MeaningsAndExamplesStep.tsx:1477`），不新造「（未补录）」之类的说法。
- **新草稿一条词义都没有时**（判据：`word.meanings.pos` 是空数组，**不是**看词典命中状态，理由见下）：仍然创建草稿（管理员的核心诉求是把这个词存进库），但**不回填关联**——`target_word_id` 与 `target_sense_id` 都不填，整行保持未选，当场说明「已建草稿，但它还没有词性与词义，补录后再回来关联」，并给出跳转入口。
- **目标不可用**：由后端在关联上给出的只读状态字段区分，且**必须分成两态**——目标词条被归档（`archived`）指引「去恢复目标词条」，目标词义被移出目标草稿且不在目标当前发布里（`detached`）才要求重选；两者都阻断发布。理由见下。

**理由**：

- **「新建草稿会带一个空的默认词义」这个前提不总成立，而且判据不是「词典有没有命中」。** 后端 `build_initial_meanings`（`service/entry.rs:157`）按 `forms.pos` 逐个建词义。词典未命中时 `forms` 取 `DraftFormsStepContent::default()`——`pos` 为空，于是 `meanings.pos` 也为空，**一条词义都没有**。**但词典命中同样可能零词义**：`map_dictionary_pos`（`service/helpers.rs:77-102`）只白名单 11 类词性，表外取值 `_ => None` **静默丢弃**；某词的 pos 全是表外值时 `forms.pos` 为空 → `meanings.pos` 为空，而 `builtin_dictionary_status` 仍是 `"matched"`，且不会被 `CatalogMismatch` 拦下（`pos_codes` 与 `part_map` 同为 0，判据恒等成立）。词典数据本身对 pos 取值零约束（导入器原样落库），换一版快照这个集合还可能变大。**所以判据只能是 `word.meanings.pos` 是不是空数组。** 而这类词（品牌名、缩写、行业术语、新造词）正是本功能最想覆盖的，这个分支必须有明确行为。
- **「默认词义」也可能不止一条**：内置词典命中多个词性时，每个词性各带一条空词义。所以要定的不只是「拿不拿默认词义」，还有「拿哪一条」。取第一条 + 全部列为候选，是最少假设的做法：既能一步到位，又不剥夺管理员改选的机会。
- **不让前端顺手替新草稿补一个词性**（那样就能拿到默认词义了）。词性要选对得懂这个词，前端只有一个字符串；选错会直接污染词库，而且这超出了「只建骨架、内容之后单独补」的范围。
- **不把关联留在「已选词条、未选词义」的半成品态**：现有 `toMeaningsWireContent`（`model.ts:735` 附近）在保存时会**过滤掉**两个 ID 没填齐的关联行。留一条半成品，保存后它就没了——那正是本功能立志要消灭的「悄悄消失」，只是换了个地方发生。
- **「目标不可用」要分成两种，处置正好相反**：**目标词条被归档**——归档完全可逆且无损（`restore` 与 `archive` 同走 `transition_lifecycle`，只把 `archived_at` 置回 NULL，而 `current_publication_id` 从不清空），恢复的一瞬间目标的发布快照原样回来、关联直接回到可解析，所以正确指引是**去恢复目标词条**，绝不能让管理员重选——那会亲手毁掉一份完好的快照。**目标词义被移出且不在目标当前发布里**——这一种才是真的必须重选。（若那条词义仍在目标的当前发布里，关联照样能发布，不算问题。）
- **为什么这两类阻断、而指向草稿不阻断**：判据是**这条数据将来会不会自己变对**。指向草稿的会（目标发布后就对了），所以只告知；另两类不会，留着一定是错的，而且各有明确的自救动作（恢复目标 / 重选），没有环，阻断是安全的。

### 决策 3：入口点一下直接建，不弹确认框；删关联项**不**连带删草稿

**做法**：

- 搜索无结果时，`notFoundContent` 由纯文案改成一行可点条目：**「创建「reliability」草稿并关联」**（回显管理员当前输入的词，不用泛指的「该词」）。
- 点击后直接走 detect → 查重 →（同形时走现有同形确认）→ createV2，**不再额外弹一层「确定要创建吗」**。
- 删除关联行时**不**连带删除刚创建的空草稿。

**理由**（不弹确认框）：

- **前面已经挡了两道**：detect 的重复检测会拦下已存在的词（引导选择而不是新建），同形命中还会走现有的同形确认流程。再加一层就是三连弹窗。
- **这不是误触路径**：要先聚焦、先输入、先搜索无结果、再点那一行，四步之后才触发。
- **代价可逆且低**：新建的是空草稿，删除有独立入口。
- **与既有做法一致**：第 1 步 `CreateEntryStep` 的「创建草稿」也是点一下直接建，没有二次确认。这里应该保持同一分寸。
- 例外仍然保留：新草稿一条词义都没有时（决策 2 的分支），创建**能**成功但关联**不能**成功，这一次必须把结果讲清楚——不是弹确认框，是给明确的结果说明。入口文案说的是主路径的事，例外路径靠明确的失败说明兜底，好过把文案稀释成谁都看不懂的中性表述。

**理由**（不连带删草稿）：

- **轻操作不能有重后果。** 删关联行的按钮是个悬停才现身的小图标、没有二次确认（`MeaningsAndExamplesStep.tsx:1496` 附近，CSS `opacity:0` 直到 hover）。让它顺带删掉另一条词条，是把一个跨词条的破坏性动作挂在最轻的手势上。
- **期间可能已经有人补录了。** 关联建出来到删掉之间可以隔很久（同一次会话、也可能是下次打开），中间任何人进去补录过，连带删就是删别人的活。要判断「它还是不是空的、是不是我建的」，等于为一个省事功能引入一套状态跟踪。
- **职责已经有地方放**：草稿删除在智能词库列表有独立入口（`deleteDraft`），那里能看到词条全貌再决定。
- **空草稿不是垃圾，是待办。** 它会出现在草稿列表等人补录；下次有人输入同一个词，detect 的重复检测会命中它并引导选择，而不是再建一条——这正是「避免重复入库」这条硬约束在替我们工作。
- 若日后空草稿确实堆积，处置应当是**列表侧的批量清理**（能看清、能多选、有确认），不是编辑器里的连带删。

### 决策 4：近义 / 反义 / 派生三类都开，不分叉

**做法**：三类关联走完全同一条路径，不为派生词做特殊处理。

**理由**：

- **「派生词更适合走词形变化」在本仓的数据模型下不成立。** 本仓的词形变化（`WordDerivedFormSlotV2`）挂在**同一条词条的某个词性**下，槽位类型是复数、过去式、比较级这类**屈折**；`reliable → reliability` 是跨词条的**构词**，forms 根本表达不了它——真按这个思路走，等于要求把两条独立词条合并成一条。
- **派生词恰恰是最需要本功能的一类。** 跨词条是它的定义特征：录 `reliability` 时想到 `reliable`，两者本来就是两条词条，「目标不在库里」的概率比近义/反义更高。
- **三类在代码里本来就同构**：`RELATION_META` 三个键、同一个 `WordRelationType`、同一套 `RelationsEditor`，后端 `relation` 就是一个字符串。分叉需要额外的条件判断与两套文案，是无理由的复杂度。
- 若产品日后认为跨词条派生应当建模成「词族 / 词根聚合」，那是一个正交的新功能，与本次的关联机制并行存在，不需要现在先分叉来给它让路。

## 后端答复（2026-08-22，已核验）

原「待后端回答」三条已由后端答复（tsz-rust `docs/features/draft-relation-targets/backend-assessment.md`，PR #48），本仓按 `main` @ `2028ffd` 复核过代码。要点：

1. **「保留在草稿里」怎么落地 → 不用剔快照，硬依赖成立。** 学习端读关联这条路径今天不存在（lexicon 路由整体挂在 `/api/v1/admin/lexicon` 下、一律 `AdminAuth` + `require_active_admin`；outbox 只写不投递），管理端的 `inbound_relations` 由 `entry_publication_sense_refs` 驱动，未解析的关联不在那张表里。所以关联既留在草稿里，也逐字留在 `publication.snapshot` 里，只是对外不生效。**决策 1 的硬依赖成立，交互设计 1 与 2 不作废。**
2. **指向草稿时 `target_headword` / `target_gloss` 填什么 → 后端回填草稿当前值。** 新建草稿的释义通常是空串；**空串与「没有快照」在库里无法区分，前端一律看 `target_state`，不得用空释义推断状态。**
3. **未解析关联的清单与确认凭证 → 服务端出**，技术设计文档提的契约形状后端接受。但 `publish` 入参带 `deny_unknown_fields`，**上线顺序必须后端先行**，否则 publish 直接 400。

核验同时纠正了本文档两处会导致实现出错的判据（决策 2 的零词义判据、决策 1 的「用词修正」），以及 `target_state` 的取值表（四态改五态）。逐条见技术设计文档「后端核验结论」，那里还留了一条**仍需后端确认**的事项（`resolved` 的判据要不要加「本词条当前发布是否已收录该关联」这一层）。

## 待产品确认

**同词头的新词条今天默认建不出来。** 新词头与现有词条撞上 ExactHeadword（同 kind 同词头，**含已归档词条**）时，`create` 走策略 `allow_new_exact_headword_entries`，而它**默认关闭**（`surface_policy.rs:20-26`：只有 `SurfaceWarningAcknowledgement` 默认开启），返回 409 `exact_headword_creation_temporarily_disabled`，**带同形确认 token 也过不去**。

这不是本功能引入的，但会直接压缩它的可用面：管理员想就地创建的关联词若与库里某条词条同词头（哪怕那条已归档），这条路走不通，只能引导他去选已有词条。需要产品确认：**是否要为本功能开启该策略**，还是接受「同词头一律引导选已有」的现状。两种前端都能做，但文案与出路不同。
