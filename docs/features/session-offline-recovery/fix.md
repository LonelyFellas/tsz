# 旧会话断网后的自动恢复

目标：页面离线后恢复联网，自动恢复会话及失败的读请求，保留当前页面和输入；不因一次网络故障要求反复重试或重新登录。明确过期、撤销、禁用仍遵守现有鉴权规则。

现场：2026-10-12，Chrome 旧后台页面 `/users`；07:12:33 的 refresh 报 `ERR_INTERNET_DISCONNECTED`，随后业务接口反复 401，列表重试不再发送 refresh。现有前端永久暂停未知轮换结果，后端旧凭据重放会撤销会话。

## 实施与兼容

- 复用现有 single-flight、generation 隔离、账号行锁与撤销规则。
- 明确离线时不发送 refresh；联网/恢复可见后自动恢复。失败读请求在会话恢复后重新请求，不自动重放写操作。
- 新 refresh 带可选 `X-Refresh-Request-Id`（随机 UUID v4）。同一次尝试在网络错误、超时和页面重载后保留该键；成功或新登录后清除。不把 access/refresh token 写入 Web Storage。
- 服务端在原子轮换事务内记录请求键哈希及后继 token 哈希。后继明文由旧高熵 token 和请求键通过域隔离 HMAC-SHA256 派生，数据库只保存哈希。
- 同键重试只返回仍有效、未撤销且未再轮换的同一后继；Cookie 已更新而响应体丢失时仍返回当前 Cookie。重试不延长会话期限，也不额外创建会话。
- 每次恢复都核验账号状态、原/后继 token 的有效性，并与安全变更使用同一账号行锁。不同键和未带键的旧凭据仍保留原重放检测。
- `HEAD /auth/refresh`、`HEAD /admin/auth/refresh` 只声明恢复能力（204、`X-Refresh-Recovery: v1`），不消费 Cookie。新前端在不确定结果重试前确认该能力；旧后端不支持时继续保护未知轮换，不盲目重放。
- 每次续接都重新探测能力，不沿用曾经成功的能力缓存；后端回退也不能让长期打开的新版标签重放旧 Cookie。
- 新后端兼容旧前端的无键请求，响应 JSON 形状不变。需先发布后端（含可回退的新增列/索引），再发布前端。回退后端前应先回退前端；已存在的无键未知轮换无法保证无感恢复，不能伪造恢复成功。

## 验收与当前阶段

1. 定时刷新遇到离线：零 refresh POST；联网后自动获得新 access token。
2. 轮换提交但整个响应丢失，离线超过旧宽限窗口：同键重试成功、同一 Cookie、仅一枚后继。
3. Cookie 已送达而 JSON 丢失、并发同键请求：不多轮换、不回退 Cookie。
4. 撤销、过期、禁用、新登录与不同键重放：不复活旧会话、不覆盖新身份。
5. 浏览器真实隔离后端验证离线→联网→读请求恢复；生产构建、契约、定向回归与最终质量门。

工作树：前端 `codex/session-offline-recovery`，后端同名分支。前端基线 `aff03c0b`、后端基线 `13c2902`，加本任务工作区差异。2026-10-12 用户已授权两仓提交、推送、开 PR，精确 CI 通过后合并，再按后端 → 前端（web → admin）部署到 tshb-test。当前阶段：本地实施与验证完成，进入独立提交审查和配套交付；PR/CI 与各组件实际部署状态持续在本会话记录。
