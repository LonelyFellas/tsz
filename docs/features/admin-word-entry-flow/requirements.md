# 优化后台添加单词流程需求评估

## 背景与目标

管理后台智能词库已能通过真实 `tsz-rust` 完成检测、分步保存、校验和发布，但以 `high`、`access` 实测时，自动建议只覆盖基本词性，词形、音标、实际发音、释义和例句多数为空；同时，词形类别不受基本词性约束、校验逐条打断、必填普通文本藏在语音编辑器中，导致录入者需要反复试错并可能产生词性与词形不匹配的脏数据。

本功能要把后台添加单词改造成“自动建议打底、人工少量确认、集中修正、发布前完整预览”的流程。固定验收基线为：

- `high`：名词、形容词、副词；确认名词复数以及形容词/副词比较级、最高级。
- `access`：名词、动词；确认名词复数以及动词第三人称单数、现在分词、过去式、过去分词。

成功标准是：当真实词典有可靠数据时，上述两个词可通过少量确认完成；词典未提供的数据明确标为待补，不以伪造数据冒充建议；任何入口均不能保存或发布词性与派生词形类型不匹配的数据。

## 目标端

本次目标端为 admin 管理后台（React Router、TanStack Query、antd v6）。不改 C 端 web 展示与学习流程。

前端 `tsz` 负责录入交互、状态隔离、完成度、客户端即时校验、错误定位和预览。自动词典内容及最终业务约束的权威性属于 sibling `tsz-rust`；前端不得硬编码 `high`、`access` 的词典内容。

## 用户故事 / 使用场景

1. 录入者输入 `high` 或 `access` 并检测后，希望先看清词典实际找到了哪些内容、哪些仍缺失，再确认创建草稿。
2. 进入词形与发音步骤后，录入者希望每个基本词性只出现合法的派生词形类型，并优先采用词典提供的拼写、音标和实际发音。
3. 在多个基本词性 Tab 间连续录入时，录入者希望当前 Tab、各 Tab 内容和未保存状态互不串扰，不因普通输入自动跳 Tab。
4. 录入词义、语法和例句时，录入者希望直接使用普通文本框；只有需要发音标注、连读、重音或 SSML 时才进入高级语音编辑。
5. 点击“完成并继续”时，录入者希望一次看到当前步骤全部待修项、各 Tab 缺失数量，并可点击任一问题定位到对应 Tab、区块和字段。
6. 到达发布前，录入者希望按词性完整预览词头、词频、词形、读音、语法、词义和例句，并看到是否仍有阻断发布的问题。
7. 保存后返回列表、刷新或恢复草稿时，录入者希望看到服务端已保存版本；未保存离开时获得明确提示。完成 `high` 后再创建 `access`，新流程必须是全新状态。

## 功能范围

### 本次范围内

- 检测结果真实度：明确区分“词典已建议”“仍需人工补充”“服务不可用”，文案与实际返回内容一致。
- 自动建议覆盖：在后端提供可靠来源的前提下，带出词头、基本词性、合法词形、词典音标、实际发音、释义、例句及可用词频；每个建议保留来源标识，用户可修改。
- 合法词形规则：
  - 名词：`plural`；默认新增为“复数”。
  - 动词：`third_person_singular`、`present_participle`、`past_tense`、`past_participle`；默认按上述顺序补齐缺失类型。
  - 形容词：`comparative`、`superlative`；默认先“比较级”，再“最高级”。
  - 副词：`comparative`、`superlative`；默认先“比较级”，再“最高级”。
  - 其他基本词性默认无派生词形；只有后端能力契约明确允许时才可添加。
- 非法组合在建议生成、手动新增、类型切换、步骤保存和最终发布各层均被拒绝；已有非法草稿须提示修复，不能静默转换或丢弃。
- 完成度与聚合校验：步骤、基本词性 Tab 和折叠区块均显示阻断项数量；一次列出全部问题，点击可定位并展开目标。
- 明确覆盖词条总词频与每个词义词频的必填、范围和格式提示。
- 普通文本优先：语法结构、英文释义、英文例句直接编辑；语音富文本/SSML 是同字段的可选高级能力，不是普通录入前置条件。
- 渐进展开：第三步默认只展开当前词性的首个核心词义；语法结构、更多释义、更多例句、近义词、反义词、派生词按需展开。带错误或已有内容的区块可自动展开。
- 多词性与跨词条状态隔离；保存、返回、刷新、恢复草稿行为清晰一致。
- 发布前关键数据全量预览与最终聚合校验。

### 明确不做

- 不在前端内置 `high`、`access` 或其他单词的词形、音标、释义、例句等词典数据。
- 不由前端猜测不规则词形、音标、释义、例句或词频。
- 不在本功能中实现或替换词典数据采集、授权和清洗系统；若数据源不足，只定义后端所需契约和分阶段落地要求。
- 不重做语音富文本编辑器、TTS、音频上传或 C 端展示。
- 不改变已发布词条的业务含义；编辑已发布词条仍沿用现有 revision、影响确认与再发布机制。

## 约束与边界

- `@tsz/types` 继续 1:1 镜像 `tsz-rust` snake_case wire；词典数据不得在 HTTP 层做命名或内容转换。
- 基本词性来自可配置 catalog，前端不能仅凭显示名称判断规则。合法词形能力应由后端契约提供并由服务端校验，前端消费同一规则做即时约束。
- 客户端校验用于即时反馈，不能代替服务端保存/发布校验；服务端应返回稳定的 `step`、`node_id`、`field`、`code` 和 `message` 以供定位。
- 自动建议只能来自可追踪、许可可用的词典/语料来源；缺失值保持缺失并明确提示。
- 切换 Tab、折叠区块和高级编辑器不能更换稳定节点 ID，不能覆盖其他 Tab 或更新期间用户刚输入的内容。
- 刷新后只恢复服务端已保存内容；浏览器内未保存内容不承诺跨刷新恢复，但离开/刷新前必须提示。
- 新建第二个词条时不得继承上一个词的检测结果、active Tab、展开状态、校验问题、幂等键或本地表单数据。
- admin 继续使用 antd v6，不引入 tailwind 或 `@tsz/ui`。

## 验收标准

### 自动建议与词形规则

- [ ] 检测 `high` 后显示名词、形容词、副词及每类实际获得/缺失的建议摘要，不再用“词典建议”笼统暗示空字段已补全。
- [ ] `high` 名词只允许复数；形容词和副词只允许比较级、最高级；建议值来自真实后端数据。
- [ ] 检测 `access` 后显示名词、动词及每类实际获得/缺失的建议摘要。
- [ ] `access` 名词只允许复数；动词只允许第三人称单数、现在分词、过去式、过去分词；建议值来自真实后端数据。
- [ ] 任一词性下拉不出现其他词性的非法类型；构造非法 wire 时服务端也拒绝保存/发布并返回可定位问题。
- [ ] 新增派生词形给出该词性正确默认值；已有合法类型已齐全时，不重复盲增，提示用户选择可重复的变体组或不再添加。
- [ ] 音标、实际发音、释义、例句和词频有建议时带出并标识来源；无建议时显示明确缺失状态，不伪造。

### 完成度、校验与定位

- [ ] 每个步骤显示完成/待修数量；词形和词义页面的每个词性 Tab 显示该 Tab 阻断项数量。
- [ ] 点击完成时一次展示当前步骤全部待修项，而不是只 toast 第一条。
- [ ] 问题列表可点击，能切换到所属词性、展开所属区块、滚动并聚焦字段；定位后问题列表仍可返回查看。
- [ ] 词条总词频和每个词义词频均有明确必填标识、范围/格式说明及缺失错误文案。
- [ ] 服务端返回多个 `field_issues` 时全部展示；未知节点/字段仍显示问题且给出可恢复提示，不造成页面崩溃。

### 普通录入与渐进展开

- [ ] 语法结构、英文释义、英文例句不打开语音编辑器即可录入、保存、刷新恢复和发布。
- [ ] 高级语音编辑可从对应普通文本字段按需打开，保存后回写同一稳定节点；取消不覆盖普通文本。
- [ ] 第三步默认只展开当前词性的首个核心词义；空的非核心关系和附加内容默认折叠。
- [ ] 包含已有内容、当前错误或用户主动展开的区块不会因切换 Tab/输入而意外折叠或展开。

### 多词性、持久化与跨词条隔离

- [ ] `high` 三个词性 Tab 连续输入时不自动跳转，内容不串 Tab；保存、返回后恢复一致。
- [ ] `access` 两个词性 Tab 连续输入时不自动跳转，内容不串 Tab；刷新后恢复最近一次已保存版本。
- [ ] 未保存返回、刷新或关闭时有确认提示；选择留下继续编辑，选择离开不把未保存内容误报为已保存。
- [ ] revision 冲突保留当前未保存内容并提示重新加载，不静默覆盖服务端新版本。
- [ ] 完成或离开 `high` 后新建 `access`，首屏与后续步骤不残留 `high` 的检测结果、Tab、问题、展开状态或内容。

### 预览与发布

- [ ] 发布前按词性预览词头、总词频、基本/派生词形、字典音标、实际发音、语法结构、词义词频、释义和例句，并标出缺失/来源。
- [ ] 最终校验一次展示所有发布阻断项并可回到相应步骤定位；校验通过的 revision 才能发布。
- [ ] `high`、`access` 均能在真实 `tsz-rust` 上完成创建、保存、刷新恢复、校验和发布，且发布后读回数据与预览一致。

## 开放问题

1. 自动建议的数据源是否已具备可商用许可，且能稳定覆盖音标、实际发音、释义、例句和词频？若不同字段来自不同 provider，需由后端团队确认来源优先级与 provenance 展示粒度。
2. “实际发音”是否允许在无独立词典字段时由规范化音标派生，还是必须来自单独数据源？默认按“必须有真实来源，不等同于直接复制词典音标”处理。
3. 多音、多词义建议是自动全部落草稿，还是先进入可勾选建议清单？建议首期落入草稿并标识来源，由用户删除/修改；若来源噪声较高则改为勾选确认。
4. 词条总词频和词义词频的词典来源、量纲映射及缺省策略需后端确认；在确认前不自动填入猜测值。
5. 其他可配置基本词性的合法词形能力由谁维护？建议纳入 catalog 的只读创编能力，由后端管理和校验，而不是前端按 code 永久硬编码。
