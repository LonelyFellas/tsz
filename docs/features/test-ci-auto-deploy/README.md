# 测试精简与 tshb-test 自动部署

目标：保留鉴权、数据、契约、关键用户路径及部署安全保障，减少低价值断言；PR 与 main 使用一致的核心验证；main 精确 CI 成功后自动发布前端制品。

自动部署已在 `af413f45` 的 main CI 后完成首次真实发布，Web 与 Admin 均已验收。后续按用户要求移除 E2E，由 AI 使用 Codex 内置浏览器对真实页面进行验收；下方精简记录保留为历史证据。

现有前端部署复用精确 CI 制品、来源检查、远端锁和事务；不构建服务器源码。`deploy/check-api-contract.mjs` 根据服务器 API manifest 对照该版本 OpenAPI，校验前端快照及运行时 schema。拟定协议让前端在事务期间持有 `/opt/tsz-cross-deploy.lock` 并检查后端的 `/opt/tsz-rust/deploy.lock`；后端在创建自己的事务锁时也须持有共享锁。两仓协议就绪前不得启用自动部署。2026-10-29 检查到 tshb-test API manifest 为 `edba6bef11c8c2610da2d5dc2a5cd87c44a36912`，两份契约通过。该契约检查本身不验证数据库迁移，仍依赖后端发布事务的验收及现有配套发布要求。

已精简：移除只固定词形拼写字重、连续边框和字体特性像素形态的 E2E；字体加载、可见性和关键流程仍保留。UPS 展开用例保留交互状态，去除图标样式断言；字段样式用例保留窄屏裁切检查，移除装饰性字号和对齐断言。取消 CI 测试中固定五个分片名称的重复断言，分片完整性仍由模块清单测试和实际执行清单校验。其余测试尚未完成逐项梳理，不应宣称全面审查完成。

验收：成功 main push CI 对应的精确版本在兼容性与凭据检查通过后自动发布；旧候选不能覆盖新版本；失败及部分发布可观察且可恢复；PR/main 的关键测试模式一致；部署安全、关键业务和权限回归保留；移除 Gitee 镜像及其运行依赖。

## 覆盖率分片与耗时

PR、main 与手动 CI 共用 packages、web、admin-1 至 admin-5 七个模块。Admin 每片仍使用一个 worker；实际执行清单和 blob 必须完整，按项目/文件检查恰好执行一次，重跑只选择每个模块的最新 attempt。

Admin 由 `scripts/ci-test-sequencer.mjs` 按历史耗时从长到短分配给当前累计负载最低的分片。`scripts/ci-test-durations.json` 记录来源 CI run 和各文件的中位总耗时，包含测试、收集、setup、环境及准备时间；它只影响分配，不定义测试集合。新文件使用历史中位值估算，删除的文件不会因历史记录而继续运行。非 Admin 与未分片运行沿用 Vitest 默认排序。

实际清单保留 `timings`：逐文件 `duration_ms`、`test_duration_ms` 和状态，缺失诊断为 null。每个测试 job 的 Actions 摘要列出最慢的十个文件；这些累计诊断不包含 runner 启动、依赖安装、覆盖率收尾等，不等于整个 job 时间。后续根据成功 main 的真实产物刷新历史数据，不使用 PR 写入的共享缓存或跳过任何用例。

比较效果时同时记录工作流关键路径、排队时间、所有 job 的总运行分钟及失败次数。当前公开仓库使用标准 runner，账单 API 返回零计费时间；总 runner 分钟仍用于比较资源开销，不能把零账单当作无开销。

## 发布就绪检查

第三批分三个独立改动交付：固定 API 目标的合并前预检、按实际受影响组件发布、过时候选提前退出。复用已有的严格契约比较、精确 main/CI 绑定、共享锁、原子切换与回退；本批不修改业务 API 或数据库。

`deploy/api-target.json` 绑定权威后端仓库的完整 commit SHA。普通 PR、main 和手动 CI 用 `pnpm ci:api-preflight` 读取该提交的公开 `docs/openapi.json`，在独立临时目录调用本 checkout 的生成器，再严格比较两份已有快照。此步骤不需要部署凭据，不改跟踪中的生成文件；目标缺失、不可取或不兼容均使 CI 失败。变更目标时须同时记录配套版本及验证依据，不使用浮动分支或把失败改成跳过。

固定目标只证明选定前后端契约兼容，不代表 API 已运行该版本。正式发布仍由 `check-api-contract.mjs` 读取服务器 API manifest，再核对真实契约；共享锁内仍确认实际 API SHA。初始固定目标为本次只读核实的已验收 API `c970d13280f5dd2b0b485cee141655f7b3216089`，无需配套后端发布。涉及 API 升级时，按既有配套发布清单核实新旧组合与发布顺序，不由预检自动发布后端。

组件选择以每端最后验收版本到候选版本的构建依赖变化为依据，共享包和配置纳入影响范围；缺少可信历史时完整发布，跳过前保留版本与制品验证。过时候选须在下载和上传前记录退出原因；已写入 stage 或进入事务的异常继续按原恢复规则处理，不包装成无写入的成功。

组件选择在完整验证候选包之后、创建远端 stage 之前执行。自动发布启用 `DEPLOY_SELECT_COMPONENTS=1`，各端分别从已验收 manifest 与当前 release 的 CI 回执取得真实基线；只读共享锁内复算制品并核对 HTTPS version、页面 200 与 API 401。源码比较包含该端 app、所有共享包、根配置、CI/构建与发布工具，只有另一已知 app 及明确非构建文档可以忽略，未知路径保守发布。比较完整 Git 树、祖先关系与删除/重命名两端；缺少历史或源对象则发布，摘要、身份、服务或锁异常则失败。同 SHA 的手动 CI 参数变化也会发布。跳过不重写任何远端 manifest，摘要分别列出候选和仍在运行的旧版本。

自动候选检查使用 `DEPLOY_AUTO_SKIP_STALE=1`，在依赖安装、SSH 配置前及每端下载/上传前核对权威 main 与最新 CI run/attempt。main 已改变或有更新 CI 时，记录 `superseded` 与精确元组后结束，后续环境准备和远端写入不再执行；它表示候选已失效，不表示已验收。查询错误、未知元数据和原 CI 未成功仍失败，不用跳过掩盖异常。创建 stage 后禁止这类成功退出，上传后 strict recheck 与原事务恢复规则继续生效；失败输出保留 stage 路径，不删除现场或自动重发。检查之间仍可能变化，此时后续严格门禁可报告失败。

工作流先 checkout 本次受信 workflow 的 `github.sha` 执行候选检查，确保早于此功能的旧候选也能被识别；通过后再确认 checkout HEAD 等于预期候选 SHA。三个身份（checkout、当前 main、事件候选）不一致不进入环境安装或发布。
