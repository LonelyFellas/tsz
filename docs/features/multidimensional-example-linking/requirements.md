# 智能词库多维例句关联需求评估

## 文档状态

- 功能标识：`multidimensional-example-linking`
- 目标端：管理后台 `apps/admin`
- 当前阶段：2026-08-30 正式前后端能力评估，等待联合评审；Mock 仅作为已验收的产品输入
- 评审门：本次更新 `requirements.md`、`design.md` 与 `test-matrix.md` 后一次性交前后端评审；未批准前不修改前端业务数据流、Rust、数据库或 OpenAPI
- 当前边界：现有 Mock 继续保持零业务写入；正式实现必须以当前 `tsz-rust` OpenAPI 和既有例句关联能力为基线，不沿用已过时的“后端完全没有关联契约”结论

## 背景与目标

当前智能词库的例句随某个具体词义录入，并能通过 `focus/context` 链接指向其他词义，但管理员无法说明“原句中的哪个位置对应哪个词条和具体词义”，也无法保存尚未建词条的单词并在未来反向认领。

一期要把例句提升为可复用的独立共享对象：一条例句正文只保存一次，管理员可以在英文原句中标记单词出现位置，为每个位置确认已发布词条和具体词义；暂时没有匹配项时保存为预关联，待目标词条和词义具备后再认领。词性和词形由智能词库数据自动解析，只有存在真实歧义时才让管理员选择。

成功后的核心结果是：

- 同一条例句可以被多个具体词义共同引用，但正文、译文和难度只有一份。
- 每个正式关联都能追溯到原句中的精确单词位置和一个具体词义。
- 未匹配位置不会丢失，未来可从目标词条侧发现并认领。
- 例句内不重复维护英式/美式配置；展示形式由词库已有方言词形和当前用户个人设置共同决定。

## 术语

- **多维例句**：产品界面的统一名称。拥有稳定例句 ID、英文原文、中文译文和 CEFR 难度；底层正文只保存一次，并可被多个具体词义引用。界面不得另设或展示“共享例句”概念。
- **原句位置**：英文原文中一次具体出现的连续单词区间；同一个拼写在一句中出现两次时是两个不同位置。
- **正式关联**：一个原句位置已经指向智能词库中的一个具体词条和一个具体词义。
- **预关联**：一个原句位置尚无可用目标词条/词义，以待关联词保存，等待未来认领。
- **认领**：管理员在目标词条具备具体词义后，为历史预关联选择目标词义并将其转为正式关联。
- **真实歧义**：管理员已经确定词条和具体词义后，词库数据仍对应多个合法词形槽位，系统不能唯一确定应绑定哪一个。
- **个人设置**：用户已有的英语方言偏好。管理后台预览使用当前管理员设置；未来学习端展示使用学习用户设置。

## 用户故事 / 使用场景

### US-1 创建并复用一条多维例句

作为词库管理员，我在一个具体词义的“多维例句”区域点击添加或编辑，希望系统打开抽屉完成英文例句、中文译文、难度和位置关联；同一句可以关联其中多个单词的具体词义，而不用复制正文。

### US-2 标注并确认已发布词义

普通关联候选只来自已发布单词；新建例句必须精确关联正在编辑的当前草稿词义作为归属，这一当前草稿例外不应把其他草稿混入候选。

作为词库管理员，我选择英文原句中的一个单词位置，希望系统搜索已发布词条并列出具体词义，我只需确认正确的词条和词义；词性与词形能唯一判断时不再重复询问。

### US-3 处理真实词形歧义

作为词库管理员，当同一拼写在已选词义所属词性下仍可能对应多个词形时，我希望只看到必要的候选差异并作一次选择，避免系统静默猜错。

### US-4 保存未匹配词

作为词库管理员，当 `Center the picture on the wall.` 中的 `on` 尚无可用词条或具体词义时，我希望把该位置保存为预关联，同时继续保存整条例句及其他已经确认的关联。

### US-5 从新词条反向认领

作为词库管理员，当以后创建 `on` 并建立具体词义时，我希望系统提示命中该词及其词形的历史预关联例句；我选择一个具体词义后，预关联转成正式关联。

### US-6 按个人方言偏好预览

作为用户，我希望系统根据我的英式/美式个人设置，从目标词条已有词形中选择展示形式；管理员不需要在例句里再录一次英美拼写。

### US-7 安全修改共享原文

作为词库管理员，我修改已经被多个词义引用的英文原文时，希望先看到影响提示，并明确重新确认所有受影响的位置，避免位置静默漂移到错误单词。

## 一期功能范围

### 1. 多维例句

- 例句具有稳定 ID，英文原文、中文译文和 CEFR 难度只保存一份。
- 主页面不新增独立例句区块；“添加例句”和点击已有英文例句均打开右侧多维例句抽屉。
- 抽屉承载英文原文、中文译文、难度、原句位置选择和关联确认；取消不产生新例句或修改已有数据。
- 同一共享例句可关联多个具体词义，例如 `center`、`picture`、`wall` 分别指向句中不同位置。
- 从某个词义移除例句时，只解除该词义与该位置的关联，不删除仍被其他词义或预关联使用的共享例句。
- 一期不提供全局批量删除共享例句的入口；无引用例句的清理策略由后端运维或后续例句库功能处理。

### 2. 单词位置标注

- 管理员在英文原文中选择一个连续、非空的单词区间。
- 位置以原文为基准，必须能区分同一句中相同拼写的不同出现位置。
- 一期只处理单个单词位置；不支持多段选择、交叉位置或短语内部成分展开。
- 同一位置一期只能有一个有效业务状态：正式关联或预关联，不能同时存在两者。

### 3. 已发布词条与具体词义匹配

- 普通关联只搜索智能词库当前已发布的词条和词义。
- 管理员必须最终确认“哪个词条 + 哪个具体词义”，仅选词条不算完成。
- 系统根据已选词义所属基本词性和词库中的实际词形数据自动解析基本词性、词形类别和稳定词形槽位。
- 唯一可解析时直接带出结果，不显示额外选择控件。
- 只有剩余多个合法词形槽位时才显示歧义选择；不允许客户端按拼写规则自行猜测。
- 无匹配、目标已下线或目标词义不可用时，不得伪造正式关联；管理员可以改选目标或保存为预关联。

### 4. 预关联

- 预关联至少保留：例句 ID、原句位置、原始选中文本、规范化待关联词、创建人和创建时间。
- 活跃预关联按“例句 ID + 原句位置 + 规范化待关联词”去重。
- 同一条例句同一位置即使整句同时被 `center`、`picture`、`wall` 等多个词义引用，也只产生一条 `on` 预关联。
- 相同待关联词出现在三条不同例句中时产生三条记录；同一句中出现两次时按两个位置产生两条记录。
- 重复点击保存、请求重试或从多个已关联词义进入同一共享例句，都不得生成重复预关联。

### 5. 反向认领

- 当新词条的词头或已录词形与活跃预关联匹配时，词条创建流程提示历史预关联数量并提供查看入口。
- 管理员逐条选择当前词条的一个具体词义后才能认领；系统不能仅按词头自动选词义。
- 认领成功后，正式关联沿用原预关联的例句 ID 和原句位置，预关联从活跃列表关闭，且不能被再次认领。
- 并发认领同一条预关联时只能有一个结果；后到请求应看到已认领结果或明确冲突，不能覆盖前一个目标。
- 一期评审推荐认领目标必须已有当前发布版本；若希望在草稿词义建立后立即认领，需在评审时确认额外的“待发布认领”生命周期，见“开放问题”。

### 6. 方言与词形显示

- 例句对象和位置关联不保存管理员手选的 `uk/us`。
- 关联保存稳定词形身份，展示时再结合目标词条已有 `common/uk/us` 词形和当前用户个人设置选择拼写。
- 管理后台预览使用当前管理员已有方言偏好；一期不新增例句内方言开关。
- 目标方言没有可用词形时保留原句文本并明确提示词库数据缺口，不按规则猜写另一种拼写。
- 学习端真正消费、出题和练习行为不在一期，但数据不得阻碍后续按学习用户偏好展示。

### 7. 原文修改规则

- 修改中文译文或 CEFR 难度不影响英文位置关联。
- 修改英文原文时保持同一个例句 ID，但这是对单份例句对象的全局修改，抽屉必须展示受影响的正式关联数和活跃预关联数并要求确认。
- 一期采用保守规则：英文原文一旦变化，所有原句位置均进入“待重新确认”，不得仅按字符串差值静默平移。
- 管理员重新选择位置并确认后才能保存新的有效关联；原有目标词条/词义可作为建议展示，但不能自动生效。
- 服务端保存时再次校验“位置截取文本 = 本次确认的原始选中文本”；旧版本或错位请求不得覆盖新原文。
- 若管理员只是想为部分词义使用不同句子，应创建新共享例句，而不是修改会影响全部引用者的原句。

### 8. 存量兼容

- 现有 `WordSentenceV2` 例句和 `focus/context` 链接必须保持可读、可发布，不因一期上线丢失正文、译文、难度或既有关联。
- 不按正文哈希自动合并存量例句；相同文本可能有不同译文、难度或编辑意图。
- 存量链接没有原句位置时以“待补位置”的兼容状态展示，不伪造位置和词形。
- 管理员补齐位置前，存量例句仍按旧行为展示；补齐后才能进入位置去重、预关联和按词形替换的新流程。

## 明确排除项

- 短语整体关联、短语内部成分展开、多段或交叉标注。
- 学习端出题、练习题模板、记忆算法和答题判定。
- 例句 TTS、录音、音频上传、音频切片或逐词音频联动。
- 独立“例句库”列表页、批量导入、全局检索和批量治理。
- 自动生成或 AI 改写例句。
- 自动猜测词义、自动确认真实歧义、客户端自行推导不存在的词形。
- 依据相同正文自动合并历史例句。

## 约束与边界

- 只有具备现有智能词库编辑权限的管理员可以创建、修改、关联或认领；具体权限 key 沿用智能词库，不在一期新增 RBAC 类别。
- 词条、词义、词形和方言事实以智能词库当前发布数据为准；前端搜索结果不是权威校验。
- 所有位置都以 Unicode 码点的半开区间 `[start, end)` 表示，不能使用 JavaScript UTF-16 下标直接上送。
- 共享例句和认领写操作需要并发保护；过期版本必须提示刷新，不能最后写入者静默覆盖。
- 活跃预关联去重必须由数据库最终兜底，不能只依赖按钮禁用或前端数组去重。
- 审计记录保存操作者、对象 ID、动作和时间，不记录完整例句正文副本。
- 所有后端错误继续使用现有 RFC 9457 Problem Details 和稳定 `code`；前端不解析错误文案做业务分支。

## 验收标准

### 正常关联

- [ ] AC-01：在词义下通过多维例句抽屉创建 `Center the picture on the wall.` 后，后端只有一个例句 ID；将 `center`、`picture`、`wall` 分别关联到三个具体词义不会复制正文。
- [ ] AC-02：管理员选择 `center` 的位置和具体词义后，如果基本词性、词形槽位唯一，界面直接显示自动识别结果且不出现词性/词形选择框。
- [ ] AC-03：同一具体词义下确有多个合法词形槽位时才出现歧义选择；未选择前不能保存为正式关联。
- [ ] AC-04：相同拼写在一句中出现两次时，可以分别关联，读取后两个位置不混淆。
- [ ] AC-05：从任意已关联词义查看该多维例句，正文、译文、难度和全部位置关联一致；页面不出现独立“共享例句”区块。

### 未匹配与去重

- [ ] AC-06：`on` 无已发布目标时可保存为预关联，同时已匹配的 `center/picture/wall` 正常保存。
- [ ] AC-07：对同一例句、同一 `on` 位置重复点击、重试请求或从三个已关联词义分别保存，活跃预关联始终只有一条。
- [ ] AC-08：三条不同例句各包含一个待关联 `on` 时，活跃预关联恰好三条。
- [ ] AC-09：同一句有两个不同位置的 `on` 时，活跃预关联恰好两条。
- [ ] AC-10：同一位置存在正式关联后不能再创建活跃预关联；认领完成后原预关联不能被第二次认领。

### 反向认领

- [ ] AC-11：目标 `on` 词条达到评审确认的可认领状态后，系统提示历史预关联，并展示原句、位置和上下文。
- [ ] AC-12：管理员必须选择 `on` 的具体词义；认领成功后该位置成为正式关联，原例句 ID 和位置不变。
- [ ] AC-13：两个管理员并发认领同一预关联时只产生一个正式目标，另一方收到可理解的已认领结果或冲突。

### 方言与原文修改

- [ ] AC-14：例句编辑区没有英式/美式重复配置；切换个人方言设置后，预览从词库既有词形选择显示值，持久化关联不增加方言字段。
- [ ] AC-15：目标方言数据缺失时不生成猜测拼写，预览保留原文并提示数据缺口。
- [ ] AC-16：只改中文译文或 CEFR 后，位置与关联保持有效。
- [ ] AC-17：修改英文原文时先显示影响数量；未经逐项重新确认不能保存错位关联。
- [ ] AC-18：携带旧例句版本或位置与截取文本不一致的请求被拒绝，刷新后能恢复当前真实状态。

### 兼容与范围

- [ ] AC-19：一期上线后，未补位置的存量 `WordSentenceV2` 仍能读取和发布，且不会被按正文自动合并。
- [ ] AC-20：管理员可把存量链接升级为有位置的正式关联；升级前后例句 ID、正文、译文和难度不丢失。
- [ ] AC-21：一期界面和接口不包含短语成分展开、学习端出题或音频联动能力。

## 评审假设

- 一期“词”指连续的单个英文单词位置；短语及其成分留到后续。
- 一个具体出现位置在一期只表达一个语义，因此只能指向一个具体词义。
- 普通新建关联只允许当前已发布目标，符合现有 `related-search` 的数据范围。
- 原文修改采用全量重新确认位置的保守策略；后续可在有充分测试后优化为安全差值重定位。
- 管理后台预览直接复用已有服务端方言偏好，不新增例句级或关联级方言配置。

## 开放问题

1. **认领生效时点**：推荐一期仅在目标词义已有当前发布版本后完成认领，以复用现有发布引用约束。若产品要求“草稿词义一建立即可认领”，后端需增加 `pending -> reserved -> linked` 生命周期，并定义草稿词义删除、换 ID 或发布失败时的回退规则。
2. **共享原文修改权限**：一期可沿用智能词库编辑权限并通过影响确认保护；是否需要进一步限制为超级管理员，需产品与运营评审。
3. **无引用例句保留期**：一期不提供全局删除；后端是永久保留、软归档还是按时间清理，需要在未来独立例句库设计中确定。

### 用户认知路径

## 2026-08-30 正式前后端能力评估切片

本节是当前正式实施评审依据；与上文 2026-08-22 旧一期模型或 2026-08-29 Mock 切片冲突时，以本节为准。旧内容保留用于追溯，不代表当前选定架构。

### 评估目标

把已通过浏览器评审的多维例句抽屉从纯前端 Mock 收敛为可正式保存、读取、修正和认领的管理后台能力，同时守住以下产品结果：

- 管理员能在一条例句的具体英文位置关联已发布词条和具体词义。
- 管理员能把连续多个单词标记为自定义短语；目标短语尚不存在时，保存为 Pending，并预填写一条可编辑词义。
- Pending 不伪装成正式关联，不自动选择词义，也不在打开抽屉或保存例句时隐式创建新词条。
- 正文、CEFR、分层译文、位置关联和目标词条事实各有唯一权威来源，不因同一例句被多个词义查看而复制或漂移。
- 管理员关闭抽屉、请求失败或遇到版本冲突时，不产生半成品目标或静默覆盖他人修改。

### 正式用户流程

1. 管理员从某个具体词义点击“添加例句”或打开已有例句，进入多维例句抽屉。
2. 管理员先确认英文原文、CEFR 和中文译文，再在英文原文中选择一个连续位置。
3. 对单个词或连续短语，系统先查询已有已发布目标：
   - 命中唯一目标词条和具体词义时，管理员确认后建立正式关联；
   - 命中多个词条或词义时，管理员必须明确选择，不自动猜测；
   - 没有可用目标时，管理员保存为 Pending。
4. 自定义短语进入 Pending 时，界面带出短语词面和一条可编辑的预填词义；管理员可以修改或清空该词义再保存草稿。
5. Pending 后续可从目标短语侧或来源例句侧进入认领流程；认领必须选择一个真实具体词义，成功后原位置转为正式关联。
6. 只改 CEFR 或译文时保留位置关联；英文正文改变时，所有受影响位置必须重新确认。
7. 保存成功后主页面展示服务端真实投影；取消/关闭不产生写入。新例句采用两阶段保存时，若例句已保存但关联失败，主页面必须显示可恢复的 unresolved 状态并让管理员重试，不能隐藏局部成功。

### 产品状态与规则

#### 正式关联

- 必须同时指向目标词条和目标具体词义。
- 目标必须是当前未归档且可引用的已发布版本。
- 系统可以展示服务端解析出的目标词头、词义、词性和词形类型，但管理员不能直接编辑这些只读事实。
- 同一方言侧的原句位置不能与另一条活跃关联重叠。

#### Pending 关联

- 必须保留来源例句、方言侧、原句连续位置、原始词面和规范化词面。
- 必须区分目标种类 `word` / `phrase`；本切片重点验收 `phrase`。
- `pending_target_headword` 必填；`pending_target_gloss` 可在草稿保存时为空，但创建新目标短语前必须补齐。
- Pending 加入“本次关联”后，管理员仍可直接编辑或清空预填词义；不要求删除关联后重新标记短语。
- 单独选择一个不存在的词时保存为 `word` Pending；连续选择多个词时保存为 `phrase` Pending，两者使用相同的词义编辑、创建目标和认领流程。
- Pending 允许来源词条继续发布，但不进入对外正式关联投影，也不会自动创建目标短语。
- 一个句子、同一方言侧、同一位置只能有一个活跃业务状态；重复保存不能产生第二条 Pending。

#### 认领与创建目标

- 认领已有短语时必须选择具体词义；仅选词条不算完成。
- 如果目标短语不存在，管理员显式选择“创建短语”后进入 V3 短语创建流程，Pending 词面和词义只作为预填建议。
- 创建流程取消、失败或尚未完成时，原 Pending 保持不变。
- 目标短语和词义达到可引用状态后，管理员再确认认领；系统不能仅因词面相同自动认领。
- 同一 Pending 并发认领只能成功一次，后到操作看到已认领结果或明确冲突。

#### 发布与展示

- 例句关联是独立于 publication snapshot 的当前 lifecycle 投影；来源词条发布不会把 linked/Pending 冻结进历史快照。
- Pending 认领后原地成为当前 linked 投影并推进 lifecycle revision；不制造无意义的 meanings 待发布变更，也不改写历史 publication。
- 英美显示继续依据目标词条已有词形和当前用户方言偏好，关联本身不新增方言偏好字段。
- 自定义短语没有可用词形时展示原句 surface，不按拼写规则生成英美变体。

### 正式功能范围

- V3 admin 新增和编辑多维例句的生产抽屉。
- 连续单词/短语范围选择、正式目标确认、Pending 词面和预填词义编辑。

## 2026-08-30 句内一键发现与草稿候选需求评估

### 背景与目标

当前管理员必须先手工选择原句中的单词或连续短语，系统才查询一个词面。真实录入时管理员并不知道词库已经覆盖哪些单词、词形或短语，需要反复点击试探，容易漏掉可复用目标。

本切片新增“一键发现已有单词/短语”：管理员点击一次后，系统以数据库当前发布词面和短语模式为权威，匹配英文例句内已有的单词、连续短语和明确登记的可分离短语动词。管理员仍可手动选择任意多个有序 token 查询，并额外查看尚未发布的草稿候选。

> 2026-08-30 首个可发布切片收缩：自动模式只承诺已发布单词和连续短语。可分离状态机保留为后续独立 pattern-authoring PR；在权威 pattern 投影上线前，管理员通过手动多段选择处理不连续短语，产品文案不得宣称自动命中可分离短语。

本节经批准实施后，取代上文历史切片中“只允许连续范围、排除多段/不连续短语”的限制；当前线上/工作区实现仍维持旧规则，直到新契约、迁移和前端同时启用。

### 内部核心复用定位

- 一键发现的算法核心必须是后端内部可复用模块，但本期对外 HTTP 契约只服务多维例句，不建设提前泛化的平台接口。
- 内部 core 输入是文本、语言/方言、目标种类和可见范围；输出是命中位置、词形证据、原形候选和具体词义摘要，不依赖 association、Pending、抽屉或保存流程。
- 例句 handler/adapter 在 core 结果之上添加 range/segment 约束和例句候选 DTO；core 本身不创建任何业务数据。
- 后续文章标注、内容导入、缺词统计和练习解析可在后端内部调用同一 core，但各自建立贴合自身权限、限额和响应形状的接口。
- 前端本期不新增全局 discovery client 或跨业务公共组件；只实现例句抽屉需要的 API client 和 UI。
- 内部 core 结果绑定 publication generation 和输入 text hash，保证不同调用方基于同一版已发布词库事实。

### 产品定义

- 一键发现查询当前发布版本中的 `word` 与 `phrase`，覆盖 V2/V3 主词头、已发布词形、短语匹配模式与可关联的具体词义。
- 自动短语匹配由数据库中的 published phrase pattern 反向匹配句子，不从句子生成任意单词组合。
- 普通短语只允许连续命中；只有数据库明确标记为 separable 的短语才允许跨过未选中的中间成分。
- 自动发现是只读建议，不自动建立关联、不自动选词义、不创建 Pending，也不触发父级保存。
- 手动模式允许管理员选择任意多个单词，可连续也可不连续；系统按原句顺序拼成一个短语，同时查询已发布结果和未归档草稿结果，两组结果必须视觉分开。
- 已发布候选可选择具体词义并建立正式关联；草稿候选只能查看或转为“待关联词条”，不得把草稿 sense UUID 直接写成正式目标。

#### 词形识别、原形返回

- 用户确认句中可以通过已发布复数、过去式、分词、英美变体或其他词形识别目标，但候选必须归并并展示所属原形。
- 查询证据保留“原句命中词形 → 所属原形 → 具体词义”，不把每个变化词形渲染成独立词条卡片。
- 原形候选身份至少由 `entry_id + pos_id + base_form_id` 确定；同一原形被多个 surface 命中时合并，并保留全部 `matches[]`。
- 直接命中原形时返回该原形；命中派生/变化词形时，依据当前 publication 的词形组 membership 解析原形。
- 一个变化词形对应多个 POS、多个 form group 或多个原形时全部返回并标记“需要选择”，不得自动取第一项。
- 短语连续/可分离 pattern 同样归并到已发布 phrase 原形，再展示该原形下的具体词义。
- 自动模式只使用当前 publication 的词形和原形映射；未发布词形修改只在手动草稿候选中可见。

#### 手动多段短语边界

- 用户确认管理员可任意选择句中多个不连续单词组成短语，重点覆盖 `turn the light off` → `turn off` 这类可分离短语动词。
- 选中单词按原句顺序组成 canonical query；不允许拖动改序，也不自动加入未选中的中间单词。
- 相邻的已选 token 可合并为一个连续 segment；不相邻 token 形成多个有序 segment。
- 匹配结果和保存数据必须保留全部 segment，不能用一个包含中间插入成分的连续外包络伪装命中。
- 中间未选中的单词仍可建立自己的关联；范围冲突只按真实 segment 交集判断。
- 手动选择形成的短语如果未命中已发布/草稿目标，可以按拼接后的词面保存为 Pending phrase。
- 自动发现与手动选择共用 `source_segments` 位置模型；区别只是 segments 由后端模式匹配产生，还是由管理员明确选择产生。

### 用户流程

#### 一键发现

1. 管理员确认英文例句后点击“一键发现已有单词/短语”。
2. 系统按 Unicode 码点切词，在一次请求中使用发布词面/短语模式索引匹配单词、连续短语和可分离短语。
3. 界面显示“扫描单词数、命中单词数、命中短语数、候选词条数”，只展开有命中的位置，不堆叠空结果。
4. 原句中命中的单词和短语 segments 获得低干扰标记；管理员点击某个命中后查看全部候选词条和具体词义。
5. 唯一命中也只做推荐，不自动建立关联；管理员明确选择具体词义后才加入“本次关联”。
6. 自动发现结果彼此或与管理员手动选择发生 segment 交集时都可查看；一旦确认其中一个关联，冲突候选标为不可同时选择并说明原因。

#### 手动选择

1. 管理员进入“标记单词/短语”后逐个切换任意 token；至少选择一个单词，选择多个时可不连续。
2. 查询结果按“已发布词义”和“草稿候选”分组。
3. 已发布结果可直接选择具体词义；同一词条存在多个词义时全部列出，不按排序自动猜测。
4. 从未发布的草稿显示词条类型、主词头、当前可读词义摘要和更新时间；没有完整词义时显示“词义尚未完成”。
5. 管理员可以打开草稿查看，或把草稿词头与选定/填写的中文词义复制为 Pending；不得把草稿当成已关联成功。
6. 已发布词条若同时有未发布更改，正式关联仍锚定当前发布版本，并额外标记“有未发布修改”。
7. 界面以 `turn … off` 形式预览非连续选择，并让管理员在查询/保存前明确确认最终短语词面。

### 数据与行为规则

- 自动单词/连续短语使用 exact normalized surface；可分离短语按数据库 pattern 的有序 literal segments、gap/slot 规则验证；不使用 contains/语义模糊命中。
- 匹配来源至少包括当前发布主词头与词形 surface；同一位置命中多个词条或多个词义时全部返回，结果按位置、片段长度、词条和词义稳定排序。
- 搜索索引可包含所有已发布词形 surface，但词义详情只在归并到少量原形候选后批量加载，禁止提前展开 `surface × POS × sense` 笛卡尔积。
- 句子最大扫描 100 个 word token；超过限制返回明确校验问题，不静默漏扫。
- 一键扫描只能发一个批量请求；禁止前端对每个单词、短语或组合循环调用现有 `related-search`。
- 相同规范化词面在句中重复出现时只查询一次数据库，但响应必须恢复到每个独立 range。
- 初始批量响应每个 range 返回前 20 个候选及真实总数；有更多候选时允许按该 range 继续加载，不能把“前 20”描述成全部结果。
- 英文正文改变后立即清空旧扫描结果并取消/忽略在途请求；不得把旧 range 套到新正文。
- 手动选择的 `source_segments` 必须按 start 递增、互不重叠、surface 与正文码点范围逐段一致；服务端重新计算拼接词面，前端拼接值不权威。
- 同一 association 内相邻 segment 规范化合并；不同 association 的任一 segment 发生交集即为冲突，中间未选择区域不参与冲突。
- 扫描和手动查询均不写业务数据；只有现有“关联已有词义/添加待关联词条/保存例句与关联”动作会进入写链路。
- 已归档词条、没有当前发布版本的词条不得出现在自动结果；手动草稿结果也排除已归档条目。

### 性能与可用性目标

- 40-token 例句、100 万 entry/约 1000 万 form alias+pattern 的固定基准环境中，服务端 P95 目标不高于 1s，端到端 P95 不高于 1.5s；纯匹配阶段 P95 目标不高于 150ms。
- UI 显示明确的扫描中、无命中、部分截断、失败重试状态；失败不清空管理员已经确认的本次关联。
- 结果区使用渐进展开，不把所有 range × sense 展开成连续大表格。
- 按钮、范围标记、候选词义、草稿状态和冲突原因有稳定可访问名称，支持键盘完成选择。

### 本切片明确不做

- 不扫描数据库未登记的任意不连续组合、语序变换、同义改写或语义相似片段。
- 不根据普通 phrase headword 猜测可分离性；只有权威 pattern 标记允许时才自动跨段命中。
- 不接 AI/向量召回，不把 contains 搜索结果混入一键自动命中。
- 不自动选择具体词义、不自动保存、不自动认领草稿目标。
- 不允许正式关联直接锚定从未发布的草稿 sense。
- 首期选用 `fst + aho-corasick + 自定义可分离短语状态机` 的内部 generation 快照；PostgreSQL 负责权威 publication、delta 和词义 hydration，不建设独立搜索服务。

### 验收标准

- [ ] AD-AC-01：点击一次后扫描 1–100 个 token 中所有数据库可匹配的单词/短语，网络层只有一个批量请求，不枚举任意子序列。
- [ ] AD-AC-02：`The office is in a central location.` 一键发现同时命中 `location` 与已发布短语 `central location`。
- [ ] AD-AC-03：同一 surface 的 V2/V3、多词条和多词义候选全部可见；没有候选的 range 不生成空卡片。
- [ ] AD-AC-04：唯一命中不会自动写入；管理员选择具体词义后才加入本次关联。
- [ ] AD-AC-05：自动/手动候选的任一 segment 发生交集时不能同时保存；segment 之间未选中的单词不被误判冲突。
- [ ] AD-AC-06：手动选择可分组看到已发布结果和未归档草稿；自动扫描永远不返回草稿。
- [ ] AD-AC-07：草稿候选只能打开查看或转 Pending，保存 payload 不包含草稿 target word/sense UUID。
- [ ] AD-AC-08：已发布词条存在未发布修改时，正式关联仍指向当前发布 sense，并显示草稿提示。
- [ ] AD-AC-09：重复词面只查询一次但每个位置都有结果；正文修改后旧结果与在途响应失效。
- [ ] AD-AC-10：100 token 边界可完成，101 token 返回稳定 422；候选超过 20 时显示总数和继续加载入口。
- [ ] AD-AC-11：扫描失败、超时或局部截断不会改变已有本次关联、父级 meanings 或保存状态。
- [ ] AD-AC-12：真实本地发布的 `location` 与 `central location` 可被同一次一键发现；手动模式还可检索指定未发布草稿。
- [ ] AD-AC-13：数据库把 `turn off` 标记为 separable 后，一键发现和手动选择都能在 `turn the light off` 中命中，并保留 `turn`/`off` 两段码点范围。
- [ ] AD-AC-16：普通不可分离短语即使 literal token 按顺序散落在句中也不能自动命中；连续出现时仍可命中。
- [ ] AD-AC-17：句中 `locations` 通过复数词形命中并只展示原形 `location`，卡片保留“命中词形：locations”。
- [ ] AD-AC-18：句中 `went` 可通过已发布词形映射命中原形 `go`；不会把 `went` 显示成独立原形。
- [ ] AD-AC-19：同一 surface 对应多个 POS/原形时全部候选可见且标为歧义，用户必须明确选择具体原形和词义。
- [ ] AD-AC-20：同一原形被多个词形证据命中时只显示一张卡片，`matches[]` 完整且刷新顺序稳定。
- [ ] AD-AC-21：内部 discovery core 不依赖 association/Pending/HTTP DTO；例句 adapter 可独立把中性结果转换为例句候选。
- [ ] AD-AC-22：相同文本、scope 和 publication generation 从两个后端测试 harness 调用 core 时，命中位置、原形候选和词义摘要一致。
- [ ] AD-AC-14：管理员可增删任意已选 token；相邻选择合并 segment，取消到零个时不发查询、不产生 Pending。
- [ ] AD-AC-15：多段短语未命中时保存为 `phrase` Pending，规范化词面来自已选 token，刷新后 segments、顺序和 gloss 不变。

### 独立深度评审后的 P0 裁决

- 自动发现与手动选择是两个明确模式：自动 token 标记只展示命中；手动 token 使用独立 `aria-pressed` 切换。切换模式不清除“本次关联”。
- 手动增删 token 期间不发请求；只有点击“查询所选词语”才发送一次 `selected_segments` 请求。
- 重叠/嵌套命中必须通过独立“发现位置”导航逐项可达，例如同时列出 `location · 单词` 与 `central location · 短语`，不能只靠 token 下划线猜测点击目标。
- 候选归并边界加入 `source_fingerprint`：同一原形在句中两个位置必须保留两组结果；只有同一位置、同一原形的多个词形证据才合并进 `matches[]`。
- 一键发现成功后，唯一词条且唯一词义的候选自动加入抽屉内“本次关联”；仍不调用 association PUT，只有管理员保存抽屉时才写库。多词条、多原形或多词义候选继续要求人工确认。
- 自动加入按“最长短语优先”解决重叠：`central location` 与 `location` 同时命中时只把前者加入本次关联。被覆盖的 `location` 仍在发现结果中展示为该短语的“成分用词”，不得生成第二条重叠 association。
- 短语详情与本次关联都展示“成分用词”；连续短语展示全部 token，可分离短语只展示实际 literal token，例如 `turn … off` 的成分用词是 `turn`、`off`，中间的 `light` 仍可独立关联。
- 人工加入仍禁止静默替换；若与本次关联相交，应说明冲突对象。
- V3 关联位置只认 `source_segments[1..20]` 一个权威；连续位置也是单 segment。`source_range` 只保留 V2 历史契约，不在 V3 同时双写。
- 手动无命中时仍返回规范化 segments/query，允许创建 Pending。草稿操作固定为“查看草稿/转为待关联词条”，并明确发布后仍需认领。
- 可访问性提升为 P0：加载/空结果/失败/截断使用 `aria-live`；所有状态和禁用原因使用中文产品文案，不暴露 resolver/pending_only 等工程枚举。
- 匹配完整性必须显式返回 `complete | overloaded`。正常分页必须知道真实 total；召回过载时不能伪装成“已返回全部”，应提示缩小范围或手动查询。

### 2026-08-30 已批准的产品边界

1. 新 discovery capability 启用后停止创建新的 publication refresh 隐式关联，只保留“一键发现 → 人工确认”；存量关联不删除、不重写。
2. 继续执行“真实 segment 不得相交”：`turn … off` 可与中间 `light` 同时关联，但不能再单独关联 `turn` 或 `off`。若未来需要短语与内部成分同时关联，必须另开需求并重新设计冲突约束。
3. “成分用词”不是独立 association，不参与例句关联计数，也不绕过真实 segment 交集约束；它持久化在短语 publication 的具体方言词形下。common、BrE、AmE 可分别配置不同的成分用词。
4. 例句命中短语时必须记录具体短语词形；展示与保存只读取该词形的成分用词，不能因为 BrE/AmE 拼写相同而复用另一侧配置。
5. “已关联词义”的成分身份与词头/释义快照必须由后端按目标 publication 校验并固化；前端提交值仅表达管理员选择，不能成为权威。BrE/AmE 已有独立成分时，切回 common 必须显式处理，禁止静默丢弃任一侧。
