# 智能词库多维例句关联需求评估

## 文档状态

- 功能标识：`multidimensional-example-linking`
- 目标端：管理后台 `apps/admin`
- 当前阶段：前端开发/mock 实现与交付评审；真实契约联调仍未开始
- 评审门：需求、技术设计与 `test-matrix.md` 已形成同一评审包；真实数据源接入仍须以后端 OpenAPI 为准
- 当前边界：本仓只实现显式开发/mock 能力，不修改 `tsz-rust` 或数据库；真实数据源继续走 legacy 例句契约，绝不提前发送草案字段

## 背景与目标

当前智能词库的例句随某个具体词义录入，并能通过 `focus/context` 链接指向其他词义，但管理员无法说明“原句中的哪个位置对应哪个词条和具体词义”，也无法保存尚未建词条的单词并在未来反向认领。

一期要把例句提升为可复用的独立共享对象：一条例句正文只保存一次，管理员可以在英文原句中标记单词出现位置，为每个位置确认已发布词条和具体词义；暂时没有匹配项时保存为预关联，待目标词条和词义具备后再认领。词性和词形由智能词库数据自动解析，只有存在真实歧义时才让管理员选择。

成功后的核心结果是：

- 同一条例句可以被多个具体词义共同引用，但正文、译文和难度只有一份。
- 每个正式关联都能追溯到原句中的精确单词位置和一个具体词义。
- 未匹配位置不会丢失，未来可从目标词条侧发现并认领。
- 例句内不重复维护英式/美式配置；展示形式由词库已有方言词形和当前用户个人设置共同决定。

## 术语

- **多维例句**：产品界面的统一名称。拥有稳定例句 ID、英文原文、中文译文和 CEFR 难度；底层正文只保存一次，并可被多个具体词义引用。界面不得另设或展示“共享例句”概念。
- **原句位置**：英文原文中一次具体出现的连续单词区间；同一个拼写在一句中出现两次时是两个不同位置。
- **正式关联**：一个原句位置已经指向智能词库中的一个具体词条和一个具体词义。
- **预关联**：一个原句位置尚无可用目标词条/词义，以待关联词保存，等待未来认领。
- **认领**：管理员在目标词条具备具体词义后，为历史预关联选择目标词义并将其转为正式关联。
- **真实歧义**：管理员已经确定词条和具体词义后，词库数据仍对应多个合法词形槽位，系统不能唯一确定应绑定哪一个。
- **个人设置**：用户已有的英语方言偏好。管理后台预览使用当前管理员设置；未来学习端展示使用学习用户设置。

## 用户故事 / 使用场景

### US-1 创建并复用一条多维例句

作为词库管理员，我在一个具体词义的“多维例句”区域点击添加或编辑，希望系统打开抽屉完成英文例句、中文译文、难度和位置关联；同一句可以关联其中多个单词的具体词义，而不用复制正文。

### US-2 标注并确认已发布词义

普通关联候选只来自已发布单词；新建例句必须精确关联正在编辑的当前草稿词义作为归属，这一当前草稿例外不应把其他草稿混入候选。

作为词库管理员，我选择英文原句中的一个单词位置，希望系统搜索已发布词条并列出具体词义，我只需确认正确的词条和词义；词性与词形能唯一判断时不再重复询问。

### US-3 处理真实词形歧义

作为词库管理员，当同一拼写在已选词义所属词性下仍可能对应多个词形时，我希望只看到必要的候选差异并作一次选择，避免系统静默猜错。

### US-4 保存未匹配词

作为词库管理员，当 `Center the picture on the wall.` 中的 `on` 尚无可用词条或具体词义时，我希望把该位置保存为预关联，同时继续保存整条例句及其他已经确认的关联。

### US-5 从新词条反向认领

作为词库管理员，当以后创建 `on` 并建立具体词义时，我希望系统提示命中该词及其词形的历史预关联例句；我选择一个具体词义后，预关联转成正式关联。

### US-6 按个人方言偏好预览

作为用户，我希望系统根据我的英式/美式个人设置，从目标词条已有词形中选择展示形式；管理员不需要在例句里再录一次英美拼写。

### US-7 安全修改共享原文

作为词库管理员，我修改已经被多个词义引用的英文原文时，希望先看到影响提示，并明确重新确认所有受影响的位置，避免位置静默漂移到错误单词。

## 一期功能范围

### 1. 多维例句

- 例句具有稳定 ID，英文原文、中文译文和 CEFR 难度只保存一份。
- 主页面不新增独立例句区块；“添加例句”和点击已有英文例句均打开右侧多维例句抽屉。
- 抽屉承载英文原文、中文译文、难度、原句位置选择和关联确认；取消不产生新例句或修改已有数据。
- 同一共享例句可关联多个具体词义，例如 `center`、`picture`、`wall` 分别指向句中不同位置。
- 从某个词义移除例句时，只解除该词义与该位置的关联，不删除仍被其他词义或预关联使用的共享例句。
- 一期不提供全局批量删除共享例句的入口；无引用例句的清理策略由后端运维或后续例句库功能处理。

### 2. 单词位置标注

- 管理员在英文原文中选择一个连续、非空的单词区间。
- 位置以原文为基准，必须能区分同一句中相同拼写的不同出现位置。
- 一期只处理单个单词位置；不支持多段选择、交叉位置或短语内部成分展开。
- 同一位置一期只能有一个有效业务状态：正式关联或预关联，不能同时存在两者。

### 3. 已发布词条与具体词义匹配

- 普通关联只搜索智能词库当前已发布的词条和词义。
- 管理员必须最终确认“哪个词条 + 哪个具体词义”，仅选词条不算完成。
- 系统根据已选词义所属基本词性和词库中的实际词形数据自动解析基本词性、词形类别和稳定词形槽位。
- 唯一可解析时直接带出结果，不显示额外选择控件。
- 只有剩余多个合法词形槽位时才显示歧义选择；不允许客户端按拼写规则自行猜测。
- 无匹配、目标已下线或目标词义不可用时，不得伪造正式关联；管理员可以改选目标或保存为预关联。

### 4. 预关联

- 预关联至少保留：例句 ID、原句位置、原始选中文本、规范化待关联词、创建人和创建时间。
- 活跃预关联按“例句 ID + 原句位置 + 规范化待关联词”去重。
- 同一条例句同一位置即使整句同时被 `center`、`picture`、`wall` 等多个词义引用，也只产生一条 `on` 预关联。
- 相同待关联词出现在三条不同例句中时产生三条记录；同一句中出现两次时按两个位置产生两条记录。
- 重复点击保存、请求重试或从多个已关联词义进入同一共享例句，都不得生成重复预关联。

### 5. 反向认领

- 当新词条的词头或已录词形与活跃预关联匹配时，词条创建流程提示历史预关联数量并提供查看入口。
- 管理员逐条选择当前词条的一个具体词义后才能认领；系统不能仅按词头自动选词义。
- 认领成功后，正式关联沿用原预关联的例句 ID 和原句位置，预关联从活跃列表关闭，且不能被再次认领。
- 并发认领同一条预关联时只能有一个结果；后到请求应看到已认领结果或明确冲突，不能覆盖前一个目标。
- 一期评审推荐认领目标必须已有当前发布版本；若希望在草稿词义建立后立即认领，需在评审时确认额外的“待发布认领”生命周期，见“开放问题”。

### 6. 方言与词形显示

- 例句对象和位置关联不保存管理员手选的 `uk/us`。
- 关联保存稳定词形身份，展示时再结合目标词条已有 `common/uk/us` 词形和当前用户个人设置选择拼写。
- 管理后台预览使用当前管理员已有方言偏好；一期不新增例句内方言开关。
- 目标方言没有可用词形时保留原句文本并明确提示词库数据缺口，不按规则猜写另一种拼写。
- 学习端真正消费、出题和练习行为不在一期，但数据不得阻碍后续按学习用户偏好展示。

### 7. 原文修改规则

- 修改中文译文或 CEFR 难度不影响英文位置关联。
- 修改英文原文时保持同一个例句 ID，但这是对单份例句对象的全局修改，抽屉必须展示受影响的正式关联数和活跃预关联数并要求确认。
- 一期采用保守规则：英文原文一旦变化，所有原句位置均进入“待重新确认”，不得仅按字符串差值静默平移。
- 管理员重新选择位置并确认后才能保存新的有效关联；原有目标词条/词义可作为建议展示，但不能自动生效。
- 服务端保存时再次校验“位置截取文本 = 本次确认的原始选中文本”；旧版本或错位请求不得覆盖新原文。
- 若管理员只是想为部分词义使用不同句子，应创建新共享例句，而不是修改会影响全部引用者的原句。

### 8. 存量兼容

- 现有 `WordSentenceV2` 例句和 `focus/context` 链接必须保持可读、可发布，不因一期上线丢失正文、译文、难度或既有关联。
- 不按正文哈希自动合并存量例句；相同文本可能有不同译文、难度或编辑意图。
- 存量链接没有原句位置时以“待补位置”的兼容状态展示，不伪造位置和词形。
- 管理员补齐位置前，存量例句仍按旧行为展示；补齐后才能进入位置去重、预关联和按词形替换的新流程。

## 明确排除项

- 短语整体关联、短语内部成分展开、多段或交叉标注。
- 学习端出题、练习题模板、记忆算法和答题判定。
- 例句 TTS、录音、音频上传、音频切片或逐词音频联动。
- 独立“例句库”列表页、批量导入、全局检索和批量治理。
- 自动生成或 AI 改写例句。
- 自动猜测词义、自动确认真实歧义、客户端自行推导不存在的词形。
- 依据相同正文自动合并历史例句。

## 约束与边界

- 只有具备现有智能词库编辑权限的管理员可以创建、修改、关联或认领；具体权限 key 沿用智能词库，不在一期新增 RBAC 类别。
- 词条、词义、词形和方言事实以智能词库当前发布数据为准；前端搜索结果不是权威校验。
- 所有位置都以 Unicode 码点的半开区间 `[start, end)` 表示，不能使用 JavaScript UTF-16 下标直接上送。
- 共享例句和认领写操作需要并发保护；过期版本必须提示刷新，不能最后写入者静默覆盖。
- 活跃预关联去重必须由数据库最终兜底，不能只依赖按钮禁用或前端数组去重。
- 审计记录保存操作者、对象 ID、动作和时间，不记录完整例句正文副本。
- 所有后端错误继续使用现有 RFC 9457 Problem Details 和稳定 `code`；前端不解析错误文案做业务分支。

## 验收标准

### 正常关联

- [ ] AC-01：在词义下通过多维例句抽屉创建 `Center the picture on the wall.` 后，后端只有一个例句 ID；将 `center`、`picture`、`wall` 分别关联到三个具体词义不会复制正文。
- [ ] AC-02：管理员选择 `center` 的位置和具体词义后，如果基本词性、词形槽位唯一，界面直接显示自动识别结果且不出现词性/词形选择框。
- [ ] AC-03：同一具体词义下确有多个合法词形槽位时才出现歧义选择；未选择前不能保存为正式关联。
- [ ] AC-04：相同拼写在一句中出现两次时，可以分别关联，读取后两个位置不混淆。
- [ ] AC-05：从任意已关联词义查看该多维例句，正文、译文、难度和全部位置关联一致；页面不出现独立“共享例句”区块。

### 未匹配与去重

- [ ] AC-06：`on` 无已发布目标时可保存为预关联，同时已匹配的 `center/picture/wall` 正常保存。
- [ ] AC-07：对同一例句、同一 `on` 位置重复点击、重试请求或从三个已关联词义分别保存，活跃预关联始终只有一条。
- [ ] AC-08：三条不同例句各包含一个待关联 `on` 时，活跃预关联恰好三条。
- [ ] AC-09：同一句有两个不同位置的 `on` 时，活跃预关联恰好两条。
- [ ] AC-10：同一位置存在正式关联后不能再创建活跃预关联；认领完成后原预关联不能被第二次认领。

### 反向认领

- [ ] AC-11：目标 `on` 词条达到评审确认的可认领状态后，系统提示历史预关联，并展示原句、位置和上下文。
- [ ] AC-12：管理员必须选择 `on` 的具体词义；认领成功后该位置成为正式关联，原例句 ID 和位置不变。
- [ ] AC-13：两个管理员并发认领同一预关联时只产生一个正式目标，另一方收到可理解的已认领结果或冲突。

### 方言与原文修改

- [ ] AC-14：例句编辑区没有英式/美式重复配置；切换个人方言设置后，预览从词库既有词形选择显示值，持久化关联不增加方言字段。
- [ ] AC-15：目标方言数据缺失时不生成猜测拼写，预览保留原文并提示数据缺口。
- [ ] AC-16：只改中文译文或 CEFR 后，位置与关联保持有效。
- [ ] AC-17：修改英文原文时先显示影响数量；未经逐项重新确认不能保存错位关联。
- [ ] AC-18：携带旧例句版本或位置与截取文本不一致的请求被拒绝，刷新后能恢复当前真实状态。

### 兼容与范围

- [ ] AC-19：一期上线后，未补位置的存量 `WordSentenceV2` 仍能读取和发布，且不会被按正文自动合并。
- [ ] AC-20：管理员可把存量链接升级为有位置的正式关联；升级前后例句 ID、正文、译文和难度不丢失。
- [ ] AC-21：一期界面和接口不包含短语成分展开、学习端出题或音频联动能力。

## 评审假设

- 一期“词”指连续的单个英文单词位置；短语及其成分留到后续。
- 一个具体出现位置在一期只表达一个语义，因此只能指向一个具体词义。
- 普通新建关联只允许当前已发布目标，符合现有 `related-search` 的数据范围。
- 原文修改采用全量重新确认位置的保守策略；后续可在有充分测试后优化为安全差值重定位。
- 管理后台预览直接复用已有服务端方言偏好，不新增例句级或关联级方言配置。

## 开放问题

1. **认领生效时点**：推荐一期仅在目标词义已有当前发布版本后完成认领，以复用现有发布引用约束。若产品要求“草稿词义一建立即可认领”，后端需增加 `pending -> reserved -> linked` 生命周期，并定义草稿词义删除、换 ID 或发布失败时的回退规则。
2. **共享原文修改权限**：一期可沿用智能词库编辑权限并通过影响确认保护；是否需要进一步限制为超级管理员，需产品与运营评审。
3. **无引用例句保留期**：一期不提供全局删除；后端是永久保留、软归档还是按时间清理，需要在未来独立例句库设计中确定。
