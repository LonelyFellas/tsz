# 共享例句录音保存修复

## 问题与范围

真实验收中，上传 WAV 成功，但共享例句点击完成返回 HTTP 422 / `invalid request body`。前端向 `RichTextVariantV3` 提交 `audio_assets`，后端严格 DTO 未声明该字段；前端严格运行时 schema 也尚不能读取它。

修复沿用资产登记和语音编辑器：后端接受并按资产登记校正元数据，保存/重读保留录音，独立发布及恢复历史草稿维护引用。共享例句使用独立的草稿/发布引用表；回收同时检查词条与例句，旧发布中的录音不会因草稿移除而被删除。资产不可跨词条/例句占用，归属校验和回收通过同一资产行锁串行，数据库触发器补充约束。

`RichTextVariantV3` 同时用于词条英文内容，相关保存、发布引用遍历一并覆盖，避免接受了字段却丢掉引用。前端仅同步 wire/runtime 契约、修正文档注释和补充回归；不重做 UI。

## 验收

- 带已登记录音的共享例句创建，独立 GET/刷新重开、编辑保存后字段完整；客户端伪造的展示元数据不生效。
- 拒绝不存在、他人私有、正在回收、重复、超量和被其他内容占用的资产；失败不留下例句或引用。
- 发布后移除草稿录音，历史快照和对象仍保留；恢复历史版本重新建立草稿引用。
- `sentences.read_published` 只能取得当前公开例句的音频 URL，不能读取草稿或仅存在于历史版本的音频。
- 新建/编辑 UI 保存失败保留输入与音频，重试不丢资产；前端严格契约继续拒绝未知字段。

本地真实回归：在本任务隔离的 Postgres/Redis 与管理员账号上，实际 API 创建含录音例句返回 200；页面读取后修改译文并保存返回 200，刷新重开仍显示同一音频，真实 OSS 试听完成；页面独立发布成功，数据库同时保留草稿与发布引用。

本地 Origin 的 OSS 直传预检被现有 bucket CORS 拒绝（403 / `PreflightMissingAllowOriginHeader`），未改 bucket 或浏览器安全策略。音频通过真实上传许可、专属前缀 PUT 和 confirm 准备为 fixture，因此这次浏览器证据覆盖保存/读取/试听/发布，不将其写成浏览器直传通过。临时对象全部版本与专属本地数据在验证后清理。
