# 管理后台词性配置真实后端对接需求评估

## 背景与目标

管理后台已经具备“系统设置 → 词性配置”页面，以及基本词性、细分词性的目录读取和管理界面。但 tshb-test 当前把单词功能和词性配置一起切到了浏览器 mock，因此管理员在页面里的增删改不会进入 tsz-rust，其他词库页面读取到的也不是真实目录。

tsz-rust 现已在 `docs/openapi.json` 和 `docs/frontend-integration.md` §7 落地全部 9 个词性接口。本功能要把 admin 的词性目录与配置管理真实接到 tsz-rust，并让 tshb-test 在“单词接口仍为 mock”的过渡期中单独启用真实词性数据源。

成功标准是：管理员在 tshb-test 维护词性后，刷新页面仍能从服务端读回；智能词库所有目录消费位置读取同一份真实 catalog；并发修改、引用保护和错误提示遵循后端稳定契约，而不是继续依赖浏览器内存或 sessionStorage。

## 目标端

- 目标端为管理后台 `apps/admin`。
- 不改 `apps/web`，不修改 tsz-rust 实现或数据库。

## 用户故事 / 使用场景

### 1. 读取真实词性目录

作为已登录管理员，我进入智能词库的列表、编辑器或新建向导时，页面从 tsz-rust 读取完整基本/细分词性目录。目录加载成功后，筛选项、词性标签、基本词性选择和细分词性选择都使用服务端当前配置；目录加载失败时保留现有降级行为：历史内容以稳定编码显示，并禁用依赖目录的新增选择。

### 2. 管理真实基本词性

作为超级管理员，我进入“系统设置 → 词性配置”，可以分页、搜索、新建和修改基本词性，也可以删除未被服务端真实数据引用的基本词性。操作成功后，管理列表和 catalog 同时刷新；页面重载后结果仍存在。

### 3. 管理真实细分词性

作为超级管理员，我可以按基本词性查看、新建、修改和删除细分词性。新配置进入真实 catalog 后，智能词库中的相应选择项无需发新版即可读取；删除被引用的配置时，服务端拒绝操作，页面保留当前数据并给出明确提示。

### 4. 处理并发修改

作为超级管理员，当我基于旧 revision 修改或删除配置，而另一名管理员已经更新过同一记录时，服务端返回 `revision_conflict`。页面提示刷新后重试，并重新拉取最新列表，不能覆盖或删除他人刚保存的版本。

### 5. 过渡期混合数据源

作为测试环境使用者，我仍可使用尚未落地真实后端的单词创编 mock，但词性目录和词性配置必须来自真实后端。由真实 catalog 选择的词性编码不得被浏览器 mock 保存逻辑误判为未知编码。

此模式下，tsz-rust 的 `usage_count` 和删除保护只反映服务端真实词条/发布引用，不包含当前浏览器 sessionStorage 中的 mock 单词或草稿；mock 数据不是服务端事实来源，不能阻止真实配置删除。

## 功能范围

### 本次包含

- 真实读取完整词性目录，并完成基本词性列表、新建、修改、删除和细分词性列表、新建、修改、删除。
- 对齐服务端当前的数据字段、审计信息、分页、并发版本和错误响应约定。
- 删除操作必须携带当前记录版本，避免误删他人刚修改的配置。
- 词性相关已知错误码映射为稳定、可恢复的中文提示。
- 单词数据与词性数据可独立选择 mock/真实来源；tshb-test 保持单词 mock、词性真实，生产默认真实。
- 真实目录继续供智能词库列表、旧版编辑器和 V2 新建向导的所有现有消费位置共用。
- 保留本地离线词性 mock，并使其并发版本和稳定错误表现与真实服务一致。
- 补齐自动化测试和有登录态的真实联调清单。

### 明确不包含

- 不实现或修改 tsz-rust 路由、服务、数据库表、种子和数据迁移。
- 不把尚未落地的单词列表、检测、创编、保存、发布等接口切到真实后端。
- 不把浏览器 mock 单词同步到服务端，也不让服务端引用计数感知 sessionStorage。
- 不为跨管理员变更增加主动轮询或实时推送；首期沿用现有缓存时效和本机写入后刷新机制。
- 不改变稳定词性编码；已创建配置的 `code` 仍不可修改。
- 不直接部署生产环境；本功能合入 main 后按现有 deploy 流程发布 tshb-test。

## 约束与边界

- catalog 权限为任意有效 admin Bearer；管理列表及全部写操作只允许 `super_admin`。页面菜单和路由继续保持超级管理员门禁，后端仍是最终权限边界。
- 前后端字段保持现有 snake_case 契约，不增加命名转换层。
- 基本词性编码满足 `^[a-z][a-z0-9_]{0,31}$`；细分词性编码满足 `^[A-Z][A-Z0-9_-]{0,31}$`；创建后不可修改。
- 名称、缩写、排序、唯一性、trim 和分页规则以 `tsz-rust/docs/frontend-integration.md` §7 为准；前端校验只用于即时反馈，不能替代服务端校验。
- 修改和删除都使用服务端返回的最新 `revision`；删除缺失或非法 revision 不得发出。
- 错误分支读取 RFC 9457 的稳定 `code`、`field`、`meta`，不得匹配可变的 `detail` 文案。
- 写入成功后，设置页和所有词库页面使用的目录都要刷新；前端保留服务端同排序值记录的相对顺序，不自行以名称重排。
- mock 能力只能用于本地开发或明确的测试构建，普通生产构建禁止携带 mock。
- admin 继续使用 antd v6，不引入 tailwind 或 `@tsz/ui`。

## 验收标准

- [ ] 所有词性读取与管理操作都受 tsz-rust 当前公开契约校验，不再被标记为待落地接口。
- [ ] 任意有效管理员可通过现有词库页面读取真实 catalog；普通管理员仍不能进入或调用配置管理 CRUD。
- [ ] 超级管理员能从真实服务端分页和搜索基本词性，分页参数与响应信封符合契约。
- [ ] 新建基本词性成功返回 201；刷新浏览器后配置仍存在，并出现在 catalog 和相关业务选择项中。
- [ ] 修改基本词性与细分词性携带当前 `base_revision`，成功后读取到递增 revision 和最新展示字段。
- [ ] 删除基本词性与细分词性都在 query 中携带当前 `base_revision`，成功处理 204 空响应。
- [ ] 过期 revision 返回 409 时不覆盖/删除记录，页面显示“配置已被其他管理员修改”并刷新数据。
- [ ] 被真实词条引用的基本/细分词性返回对应 `*_in_use` 时不能删除，页面展示可理解提示；`meta.usage_count` 缺失时也不会报错。
- [ ] 基本冲突、细分冲突、404、字段错误、401/403 和 500 均不会被当作成功，已有表单输入和页面数据不丢失。
- [ ] tshb-test 明确保持单词 mock、关闭词性 mock；词性管理请求实际到达 tsz-rust。
- [ ] 本地开发可继续显式启用词性 mock；词性 mock 的 DELETE 同样校验 revision，错误码与真实契约一致。
- [ ] 在“单词 mock + 词性真实”模式下，智能词库所有目录消费者展示真实 catalog；从真实目录选择的有效编码可走完 mock 保存流程。
- [ ] 真实服务端引用数不包含浏览器 mock 单词的过渡期限制在评估与验收说明中可追溯，不伪造服务端 usage_count。
- [ ] 项目规定的类型、代码规范、测试与覆盖率质量门全部通过。
- [ ] 登录 tshb-test 后完成 catalog、基本/细分 CRUD、刷新持久化、冲突/引用保护和业务页面联动手测。

## 开放问题（本评估采用的默认方案）

1. **真实 catalog 是否同时供全部智能词库页面使用？** 默认是。配置管理和业务选择必须共用同一真实目录，不能只让设置页真实、词库页面继续读 mock。
2. **测试环境中的 mock 单词是否参与真实引用计数？** 默认否。浏览器 mock 不上传服务端；后端 `usage_count` 和删除保护只代表真实持久化数据。
3. **是否本次就发布生产？** 默认否。先完成代码、契约测试和真实联调，合入 main 后发布 tshb-test；生产按后续明确指令执行。
4. **本地开发是否彻底删除词性 mock？** 默认保留，但用独立开关控制，并同步真实接口的 revision 与错误契约，避免失去离线开发能力。
