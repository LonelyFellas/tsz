# 智能词库垃圾桶清理 需求评估

## 背景与目标

智能词库的「垃圾桶」是词条的归档态（`status = archived`）。目前它**只进不出**：

- 词条可以「移入垃圾桶」（单条 + 批量），也可以「恢 复」；
- 但**没有任何永久清理入口**——归档词条会无限期堆积在库里。

后端数据模型对此是有意为之：已发布词条不物理删除（`tsz-rust/docs/word-data-model.md:1046`），
归档只写 `archived_at`，且**不释放** catalog 引用（同文档 `:1054`）。也就是说归档在设计上
就是终点站，既没有 purge 端点，也没有保留期自动清理。

问题在于，垃圾桶里其实混着两类性质完全不同的数据：

1. **从未发布过的草稿**——建错了、重复了、试验性质的条目。它们从未对学习端可见，
   没有发布历史，没有入站引用。这类数据留着纯属占地方，还会持续占用词头（headword），
   挡住后续同名词条的创建。
2. **发布过的词条**——有发布历史、可能被其他词条的词义引用、catalog 引用未释放。
   这类数据的删除是不可逆的历史销毁。

目标：让管理员能**安全地**清理第 1 类数据（支持批量），同时明确第 2 类的边界与代价，
不把两者混为一谈。

**成功长什么样**：管理员在垃圾桶里勾选若干条误建的草稿，一次操作永久移除，
词头随之释放；对不该删的条目，系统明确拒绝并说清原因，绝不出现"删了一半"的中间态。

## 目标端

**admin**（管理后台，antd v6）。落点是智能词库列表页
`apps/admin/src/features/dictionary/SmartDictionary.tsx`。web 端不涉及。

## 用户故事 / 使用场景

**主流程**

- 管理员在智能词库切到「垃圾桶」筛选，看到归档词条列表；
- 勾选若干条确认是误建的草稿，点「永久删除」；
- 二次确认弹窗说清后果（不可恢复、释放词头、影响条数）；
- 确认后执行，成功后列表刷新、统计更新，给出结果提示。

**关键分支**

- 勾选中混入了「发布过」的词条 → 系统在提交前就拦下，说明哪些不能删、为什么；
- 提交时词条已被他人改动（revision 冲突）→ 明确提示"已变化，请刷新重试"，不静默吞掉；
- 提交时后端判定不可删（有发布历史 / 被其他草稿引用）→ 逐条回报原因；
- 部分成功 / 部分失败 → 必须让管理员看清哪些删了、哪些没删。

**反向场景（要防的）**

- 管理员误点批量删除，把还有用的词条清掉 → 需二次确认 + 明确的影响面展示；
- 想"一键清空垃圾桶"→ 本次**不提供**（见下方范围）。

## 功能范围

**做**

- 垃圾桶列表行增加「永久删除」入口（单条）；
- 支持**选中行批量**永久删除，交互与量级对齐现有「移入垃圾桶 / 恢 复」批量（上限 100 条）；
- 删除前的可删性判定与提示：区分"从未发布的草稿"与"发布过的词条"；
- 二次确认，说清不可逆与影响条数；
- 结果反馈：成功条数、失败条数与原因；
- 沿用现有的混选保护思路（垃圾桶与正常词条不同批处理）。

**不做**

- **不做「一键清空垃圾桶」**——全量清空需要分页拉取全部归档词条，耗时长、失败恢复复杂、
  误操作代价极高，收益不成正比；
- **不做保留期自动清理**（如"归档 30 天后自动删除"）——属于后端策略，且需要产品先定保留期；
- **不实现后端**——本仓库只管前端，后端能力缺口写进技术设计的「后端对接建议」，由用户转达；
- 不改动现有归档 / 恢复的行为。

## 约束与边界

**权限（已定稿）**

- 沿用智能词库现有的管理员鉴权（`@tsz/shared/auth` 内核，`(console)` 路由组门禁）。
- **普通管理员（`role = admin`）只能永久删除自己创建的词条**；
- **超级管理员（`role = super_admin`）不受此限制**，可删除任意可删词条。
- 该规则**必须由后端强制校验**。前端的按钮置灰/隐藏只是体验优化，不构成权限——
  否则普通管理员绕过 UI 直接调 API 就能删他人词条。见 design.md §4.4。
- 前端判定所需：当前管理员身份取自 `useAuthStore` 的 `profile`（含 `id` 与 `role`，
  门禁保证受保护页内必有值）；词条创建人需要与之比对的 **UUID**。
  **当前缺口**：列表行 `AdminWordListItem` 只有 `created_by_name`（姓名字符串），
  没有创建人 UUID —— 姓名比对会因重名误判，必须请后端补 `created_by`。见 design.md §4.3。

**数据规则（来自后端契约，`tsz-rust/docs/openapi.json`）**

- 永久删除端点为 `DELETE /admin/lexicon/entries/{id}`（`operationId: delete_draft`），
  语义是「**从未发布的草稿**已永久删除并释放词头」（204）；
- 必须携带乐观锁 `base_revision` + `base_lifecycle_revision`（`DeleteDraftInput`，两者都必填）；
- 后端在这些情况下拒绝：
  - `409` — revision 冲突，或**词条已有发布历史 / 被其他草稿引用**
  - `404` — 词条不存在
  - `422` — `base_revision` 取值非法
- **该端点是单条的，后端没有批量删除端点**。

**关键不确定性（阻塞方案选型）**
后端 OpenAPI 的 409 描述**没有提到 archived**，但前端 mock
（`apps/admin/src/features/dictionary/mock/adminWordsMock.ts:4345`）对
`status === "archived"` 一律抛 `409 entry_not_deletable`。
两者对"归档态的未发布草稿能不能直接删"给出了不同答案，这一条直接决定实现路径，
必须向后端确认或实测。详见 design.md。

**兼容性 / 一致性**

- 类型走 `@tsz/types`（snake_case wire，1:1 镜像后端）；请求走 `@tsz/api-client`；
- admin UI 用 antd v6，禁止 tailwind / `@tsz/ui`；
- 删除是终止性操作，需遵循项目既有的乐观锁 + 幂等键约定。

**性能**

- 批量上限 100 条，与现有 archive-batch / restore-batch 一致；
- 若最终走"前端循环单条删除"的过渡方案，需控制并发，避免打爆后端。

## 验收标准

- [ ] 垃圾桶列表中，「从未发布」的归档词条行显示「永久删除」入口；
- [ ] 「发布过」的归档词条行不提供永久删除，或提供但明确置灰并说明原因；
- [ ] 普通管理员只在**自己创建**的词条行看到可用的「永久删除」；他人创建的置灰并说明原因；
- [ ] 超管在所有可删词条行都能永久删除，不受创建人限制；
- [ ] 普通管理员批量选择中混入他人创建的词条时，提交前拦截并列出具体条目；
- [ ] 后端返回 403（越权删他人词条）时，前端给出明确提示而非笼统失败；
- [ ] 单条永久删除成功后：该行从列表消失，词头被释放（可用同名重新创建）；
- [ ] 支持勾选多条批量永久删除，上限 100 条，超出时明确提示；
- [ ] 批量选择中混入不可删条目时，提交前拦截并列出具体条目；
- [ ] 执行前有二次确认，文案说明「不可恢复」与「影响 N 条」；
- [ ] revision 冲突（他人已改动）时给出可操作的提示，并刷新列表；
- [ ] 后端拒绝（有发布历史 / 被引用）时，逐条回报原因，不出现笼统的"操作失败"；
- [ ] 部分成功时，结果提示明确区分成功与失败条数；
- [ ] 删除后列表、统计（stats）缓存正确失效并刷新；
- [ ] 重复点击 / 双击不会发出两次写请求（沿用 `runLifecycleCommandOnce` 锁）；
- [ ] 单测覆盖达 admin 90% 门槛，含成功、冲突、拒绝、部分失败各分支。

## 开放问题

1. **【阻塞】归档态的未发布草稿，后端到底允不允许直接删？**
   后端 OpenAPI 未提 archived，前端 mock 拒绝。需要向后端确认，或在测试服实测一次。
   答案决定实现是「直接删」还是「先恢复再删」两步（后者非原子，有风险）。
2. **要不要请后端加批量删除端点？**
   现有 `archive-batch` / `restore-batch` 是原子的（要么全成、要么全不动）。
   永久删除若只能前端循环，就拿不到这个原子性保证。建议请后端加，见 design 的对接建议。
3. ~~**权限门槛**~~ **已定稿（2026-08-31）**：普通管理员限本人创建，超管不受限。
   衍生出两个**新的后端依赖**：列表行需补 `created_by`（UUID），
   且后端需强制校验创建人归属。见 design.md §4.3 / §4.4。
4. **「发布过的归档词条」这条线要不要做？**
   需要后端提供「显式清理 publication + 级联释放 catalog 引用」的受审计能力，
   数据模型里明确写的是"未来"。倾向本期不做，但需用户确认。
5. **判定「从未发布」的依据是否可靠？**
   列表行的 `published_revision` 缺省代表未发布，但类型注释写的是
   "V2 当前线上 publication 的源 revision；**legacy**/未发布行缺省"——
   legacy 行也会缺省，可能误判。需确认是否有更可靠的判据。
6. **垃圾桶当前积压量有多少？**
   决定「单条先行、批量等后端」是否够用：几十条量级单条足够；
   若已积压数百条且后端排期远，才需要考虑前端循环的过渡批量（非原子，有风险）。
