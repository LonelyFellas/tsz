# 垃圾桶与引用可见性 · 总方案

> 汇总 2026-08-31 对话中确定的全部需求，作为后续施工的唯一依据。
> 已完成部分标注提交号；未完成部分按批次推进。

## 0. 目标

让管理员能**安全地清理垃圾桶**，并且在动手之前就知道**这条词条能不能删、被谁引用**。

拆成两个独立价值：

1. **清理能力**——垃圾桶从"只进不出"变成可清理（✅ 已完成）
2. **引用可见性**——被引用情况在点击前可见，而不是撞错误才知道（进行中）

## 2. 已定的决策

| 决策点                       | 结论                                                     | 理由                                                                                   |
| ---------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 垃圾桶菜单位置               | **词库管理 → 垃圾桶**，独立菜单项 + 独立列表页           | 清理是与创编不同的任务语境                                                             |
| 垃圾桶页权限                 | **复用 `words.access`**                                  | 零后端改动；删除本身已有「本人/超管」归属校验作二级保护。将来需单独授权再加 key        |
| 智能词库的「垃圾桶」状态筛选 | **保留**                                                 | 有深链依赖（如重复检测跳转定位归档词条），去掉会断                                     |
| 引用计数口径                 | 按**引用方词条去重**、**含草稿引用**、**第一版不拆类型** | 去重贴合"几个词条依赖我"；不含草稿会出现「0 引用却删不掉」；拆类型的价值被下钻明细覆盖 |
| 「被谁引用」                 | **第一版给前 5 条 preview**，不做完整分页                | 后端已有 `total + previews[≤5] + truncated` 模式可照抄                                 |
| 500 缺陷                     | **纳入，且排在计数之前**                                 | 又小又急，且它把口径定下来供计数复用                                                   |

## 3. 引用来源全景（6 类）

由 `information_schema` 全量筛出，非人工回忆。详见
[entry-reference-count/assessment.md](../entry-reference-count/assessment.md)。

| #   | 来源                                                 | 语义                   | 删除检查  | DB 外键  |
| --- | ---------------------------------------------------- | ---------------------- | --------- | -------- |
| 1   | `relations.target_entry_id`                          | 近义/反义/派生词       | ✅        | RESTRICT |
| 2   | `relations.prebound_target_entry_id`                 | 关联词预绑定待物化     | ✅        | RESTRICT |
| 3   | `sentence_links.target_entry_id`                     | 例句 focus/context     | ✅        | ❌ 无    |
| 4   | `entry_publication_sense_refs.target_entry_id`       | 发布内容词义引用       | ✅        | RESTRICT |
| 5   | `sentence_associations.target_entry_id`              | 例句关联待认领         | 🔨 A 批补 | RESTRICT |
| 6   | `v3_phrase_variant_component_usages.target_entry_id` | **短语把单词作为成分** | 🔨 A 批补 | RESTRICT |

**核心不变量**：计数口径 ≡ 删除拦截口径。两处各写一套 SQL 必然漂移，
会产生「显示 0 引用却删不掉」——比不显示更糟。因此 A 批先把口径定死，B 批复用。

## 4. 施工批次

### 批次 A —— 修 500 缺陷（后端，小）

**问题**：第 5、6 类不在删除检查里，会撞 DB 外键；而 `map_entry_write_error`
未映射这些约束名，落到 `Database(error)` → 管理员看到 **500 而非 409**。
（数据不会坏，RESTRICT 拦住了；坏的是体验与可诊断性。）

- [x] `delete_never_published_entry` 的入站检查补第 5、6 类
- [x] `map_entry_write_error` 补齐 7 个遗漏约束名（含未来兜底）
- [x] 测试：被例句关联引用的词条删除返回 409（第 6 类因 shape_check 必然已发布、
      先被 publication 判定拦下，构造不出对照组，补进检查仅作防御）

真机联调验证：造 `vacationsource --近义词--> holidaytarget` 后，
垃圾桶列表 `holidaytarget` 引用列显示 1、永久删除置灰、
点开显示「被以下内容引用：vacationsource · 关联词」；
后端 DELETE 返回 409——计数与拦截口径一致。

**性能要点**（已实测执行计划）：第 1 类必须直接用
`relations.target_entry_id`，不要 JOIN `nodes` 取 `entry_id`——JOIN 写法退化为
`Seq Scan`，直接用则走 `lexicon_relations_target_idx`。其余各类均有可用索引。

## 5. 验收标准

- [ ] 被任一类引用的词条，删除返回 **409 且文案说明原因**，绝不出现 500
- [ ] 垃圾桶在「词库管理」下有独立入口，页面只做清理相关操作
- [ ] 列表显示引用数；`>0` 时删除入口置灰并说明
- [ ] 点击引用数能看到引用方（至少前 5 条）
- [ ] **计数为 0 的词条一定能删**（口径一致性，最关键的不变量）
- [ ] 智能词库原有筛选、深链、批量归档/恢复行为不受影响

## 6. 风险

| 风险                                        | 应对                                         |
| ------------------------------------------- | -------------------------------------------- |
| 计数口径与删除拦截漂移 → 「0 引用却删不掉」 | 两者共用同一套聚合实现，A 批先定口径         |
| 列表逐行子查询性能退化                      | 批量聚合 + 真实数据量下测 P95                |
| 第 3 类无 DB 外键，仅靠应用层               | 该路检查不得削弱；改动时保留测试             |
| 独立页与原状态筛选重复维护                  | 列表渲染逻辑复用同一组件，仅入口与操作集不同 |
