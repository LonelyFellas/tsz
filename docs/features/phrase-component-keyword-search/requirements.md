# 成分用词候选支持关键字搜索 需求评估

## 背景与目标

短语词义步的「成分用词」卡片（2026-09-02 上线，见 `docs/features/phrase-component-usages/`）
让管理员把短语里的每个单词关联到智能词库的已发布词条。当前候选**只按词面严格匹配**：
点中 `give`，后端拿 `normalized_surface = 'give'` 去查，只有词面正好是 `give` 的词条进候选。

实测反馈（2026-09-03）：在 `give me` 里点 `give`，候选只有 2 条；而在智能词库列表用关键字
`give` 搜，能看到 7 条。两者口径不同——列表是 `ILIKE '%give%'` 的包含匹配，候选是等值匹配。
管理员的心智模型是列表那一套，看到 2 条会以为漏了。

更实际的问题是**够不着**：后端允许短语做成分目标（最多套一层，见
`tsz-rust/src/lexicon/service/v3.rs` 的 `validate_phrase_components`），但按词面等值匹配，
在 `give me` 里永远选不到 `give up`——除非管理员能自己想起并输入完整词面。

目标：让管理员在成分用词卡片里能用关键字找到目标词条，口径与智能词库列表一致。

成功的样子：管理员点短语中的一个词，既能立刻看到按词面命中的候选，也能在记不清、或想关联到
别的词条时输入关键字继续找，找到后照旧勾选词形与词义完成关联。

## 目标端

admin（管理后台，antd v6）。web 端无此功能。

后端为 tsz-rust，需要新增能力（详见 design.md）。

## 用户故事 / 使用场景

**主流程**：管理员在编辑短语 `give me` 的词义步，点击成分用词卡片里的 `give`，弹层默认展示按
词面命中的候选（两条 `give` 词条）。他想把这个词关联到短语 `give up`，于是在弹层的搜索框输入
`give`，列表扩展为所有词面包含 `give` 的已发布词条，选中 `give up`，再逐层选词形与词义，
勾选后关闭弹层，角标 +1。

**分支一（记不清拼写）**：短语里的词是 `harbour`，管理员想关联到 `harbor` 那条美式词条，
输入 `harb` 就能搜到。

**分支二（关键字无结果）**：输入 `zzz`，弹层显示空状态，提示没有匹配的已发布词条，
已有关联不受影响。

**分支三（结果过多）**：输入 `e` 这类过短或过宽的关键字，需要有下限与条数上限，
不能把整库拉进弹层。

## 功能范围

做：

- 成分用词弹层内新增关键字搜索输入，按关键字检索**已发布**词条，返回与现有候选同构的数据
  （词条 → 词形 → 词义三层，含成分关联所需的全部 id）。
- 关键字口径与智能词库列表一致：对词面做包含匹配，大小写不敏感。
- 搜索结果与「按词面命中」的候选在同一个级联面板里呈现，命中行的既有标识保留。
- 结果分页或条数上限，避免一次拉取过多。

不做：

- 不改成分关联的数据形状与保存链路（`component_usages` 的字段不变）。
- 不支持把草稿作为成分目标（成分关联要存 `target_publication_id`，草稿没有发布快照）。
- 不做按释义搜索、不做拼写纠错/近似匹配。
- 不动句中目标发现（`V3SentenceTargetDiscovery`）那条链路。
- 不改成分关联的层级限制（短语套短语仍只允许一层，由后端保证）。

## 约束与边界

- **只能选已发布词条**。后端 `validate_phrase_components` 用 `target_publication_id` 反查
  `entry_publications`，查不到即 `invalid_phrase_component`。归档词条同样排除。
- **候选必须自带成分关联所需的全部 id**：`pos_id`、`base_form_id`、`form_id`、`variant_id`、
  `sense_id`、`dialect`、`form_type`，以及词形可搭配的 `base_form_ids`。智能词库列表的关键字
  端点只返回词条摘要，给不出这些，所以不能直接复用。
- **`base_form_ids` 必须由后端给**。2026-09-02 的 #88 才把它从前端推导改为后端下发
  （前端拿不到同组原形信息），本次不得走回头路。
- **成分关联的 `literal` 是短语里的那个词**。关键字搜索只改「找哪个目标」，不改「这条关联挂在
  哪个词上」，所以搜索必须发生在「已经点中某个词」的上下文里，不能取消点词交互。
- 每个词形变体的成分关联上限 100 条，后端校验。
- 关键字搜索是管理端低频操作，但 `ILIKE '%q%'` 用不上现有 btree 索引，需要考虑下限字符数与
  结果上限（详见 design.md 风险段）。

## 验收标准

- [ ] 在短语词义步点击任一成分词，弹层内出现关键字搜索输入。
- [ ] 不输入关键字时，弹层展示的候选与现在一致（按词面命中，命中行有颜色标识）。
- [ ] 输入关键字后，结果覆盖智能词库列表用同一关键字能搜到的**已发布**词条。
- [ ] 搜索结果里的词条可以逐层展开到词形与词义，勾选后写入 `component_usages`，
      字段与现在一致。
- [ ] 选中一个「词面不等于该成分词」的目标（如在 `give me` 里把 `give` 关联到 `give up`），
      保存成功，不出现 400 `invalid_phrase_component`。
- [ ] 关键字无结果时显示空状态，不清空已有关联。
- [ ] 关键字过短（低于约定下限）时不发请求或给出提示。
- [ ] 结果超过上限时有明确的截断提示或分页。
- [ ] 草稿词条不出现在结果里。
- [ ] 归档词条不出现在结果里。
- [ ] 已有关联在重新打开弹层时仍正确回显为勾中。

## 开放问题

1. **搜索框与现有候选的关系**：是「默认按词面命中，搜索框用于扩展」，还是「一进来就是空的
   搜索框，全靠输入」？前者信息更多、少一次输入；后者更简单。本文档按前者写验收标准。
2. **关键字下限**：建议至少 2 个字符才发请求。需要确认。
3. **结果上限与分页**：一次返回多少条、是否要「加载更多」。建议先做上限 + 截断提示，
   不做分页。
4. **是否允许关联到另一个短语**：后端允许（最多一层），产品上是否鼓励？如果不鼓励，
   搜索结果应过滤掉 `kind = phrase`。
5. **搜索是否要覆盖屈折词形**：`surface_sources` 里存了全部词形词面，搜 `gives` 能命中
   `give` 词条。确认这是期望行为。
6. 是否需要在结果里显示词条的首条释义以区分同形异义词（当前第一列只有词面，
   两条 `give` 肉眼无法区分）。
