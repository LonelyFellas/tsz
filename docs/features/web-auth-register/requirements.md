# C 端手机号注册接口对接需求

## 背景与目标

后端注册入口已从 `POST /api/v1/user/register` 迁移到
`POST /api/v1/auth/register`，并改为手机号验证码注册、注册成功即颁发登录会话。
当前 Web 注册页仍支持邮箱、没有验证码输入，并在注册后额外调用登录接口。

目标是让 Web 注册页与新契约一致：用户通过手机号取得注册验证码，提交手机号、密码和验证码后直接进入已登录状态。可量化目标是注册主流程不再调用 `/auth/login`，所有前端注册契约测试指向 `/auth/register`。

## 目标应用

- Web（C 端）
- 不涉及 Admin

## 用户故事与流程

### 主流程

1. 用户输入合法中国大陆手机号。
2. 用户点击“获取验证码”，前端请求注册用途验证码并开始 60 秒倒计时。
3. 用户输入验证码和合法密码。
4. 前端提交 `{ phone, password, code }`。
5. 后端返回用户与 access token，并通过 HttpOnly cookie 下发 refresh token。
6. 前端保存 access token、写入用户状态，再按现有规则进入 onboarding 或首页。

### 错误流程

- 手机号非法：本地提示，不允许发码或提交。
- 验证码格式非法：本地提示，不允许提交。
- 发码频繁（429）：提示稍后重试，保留当前输入。
- 验证码错误或过期（401）：提示“验证码无效或已过期”。
- 手机号已注册（409）：提示直接登录。
- 网络或服务异常：展示兜底提示，恢复按钮可操作状态。

## 范围

### 包含

- 注册页当前只允许手机号注册；保留禁用的邮箱 Tab，并明确展示“未开放”。
- 增加验证码输入、发码按钮和倒计时。
- API client 注册路径、请求类型和响应类型对齐后端。
- 注册成功直接复用现有会话持久化和跳转逻辑。
- 更新 API client、组件和 OpenAPI 契约测试。

### 不包含

- 邮箱注册与邮件验证码。
- 修改登录页的邮箱验证码登录能力。
- 用户协议、图形验证码、邀请码或推广归因。
- 后端实现、短信供应商配置和 onboarding 后端能力。
- 改变现有“密码提交前统一转大写”的产品规则。

## 约束

- 注册接口是公开端点，不携带遗留 access token。
- refresh token 仅由 HttpOnly cookie 管理，不读取响应体中的 refresh token。
- 手机号、密码、验证码不得写入日志、URL 或持久化存储。
- 发码和提交按钮必须有独立在途状态，避免重复请求。
- 保持现有移动端布局、主题和键盘提交行为。

## 验收标准

- [ ] 页面展示手机号、验证码和密码字段；邮箱入口显示“未开放”且不可操作。
- [ ] 合法手机号可请求 `purpose=register` 的验证码，成功后显示 60 秒倒计时。
- [ ] 只有手机号、验证码、密码均合法时才允许提交。
- [ ] 注册请求为 `POST /auth/register`，body 精确为 `{ phone, password, code }`。
- [ ] 注册成功不再调用 `/auth/login`，直接建立会话并按 onboarding 状态跳转。
- [ ] 401、409、429 和未知错误均有明确反馈。
- [ ] API client 契约测试、注册组件测试、类型检查通过。

## 后端契约状态

1. `/otp/send` 的公开 `purpose` 枚举已包含 `register`，发码对接已解除阻断。
2. OpenAPI 声明注册成功为 201；前端请求层按任意 2xx 成功响应解析，不额外耦合具体成功状态。
