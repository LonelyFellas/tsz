# Smart Lexicon V3 基本词性未填计数与发布问题汇总：需求评估

## 背景与目标

V3 录入需要同时解决两种不同反馈：

1. 编辑时，管理员需要在每个基本词性 Tab 上看到本地未填进度，知道哪一类内容还没补齐。
2. 点击“检查发布条件”或“发布”后，需要完整消费后端 issues，按基本词性/步骤/问题类型汇总真实数量，并能跳到精确字段。

当前 main 没有 POS 本地计数；发布页把去重后的文案数当成问题数，并在向导多处重复平铺相同警告。旧 worktree 已验证“29 条重复发音文案、服务端实际 39 issues”会造成错误总数和警告墙。

## 目标端

- admin V3 forms、meanings、preview 和 wizard layout。
- 后端继续提供权威 `V3DraftValidationIssue[]`；本需求原则上不改变 API 和数据库。

## 两类状态的产品边界

### 本地未填计数

- 来自当前本地 draft，输入时立即重算。
- 是进度提示，不是后端校验结果，不显示字段红色错误。
- 计数单位应稳定、可解释，不能把一个 form 的三个空字段算成三个 Tab 徽标问题。

### 发布问题

- 只在用户点击“检查发布条件”或“发布”后，用服务端响应更新。
- 显示服务端原始 issues 总数，不按文案去重后计数。
- 按基本词性聚合；无法归属 POS 的问题按步骤兜底；同时显示问题 code/类型数量和影响范围。
- “去填写”使用现有 `navigateToV3Issue` 激活步骤、POS、group/form/variant/pronunciation 或 meanings 字段。
- 最近一次发布问题在输入、跨步骤和普通保存时保持，不主动重算或清除；下一次检查/发布响应才更新或清空。

## 用户故事

1. 管理员在 Step 2 补齐某个词性的拼写和发音；Tab 徽标立即从 2 降到 1，再降到 0，但字段不因本地计数自动标红。
2. 管理员在 Step 3 补语法、细分词性、词频、中文释义和双语例句；对应 POS 徽标实时变化。
3. 管理员点击检查后看到“总计 39 项”，再看到各 POS/步骤分布和问题类型数量，而不是 29 条同文案警告。
4. 管理员点击某一组“去填写”，进入第一个真实 issue 对应步骤、POS 和字段。
5. 管理员修改被标红字段；旧检查结果仍提示需要重新检查。再次检查成功后才清除字段错误和汇总。

## 功能范围

### 本次做

- Step 2 / Step 3 POS Tab 添加本地未填徽标，0 时不显示。
- 定义并测试稳定的本地计数单位。
- preview 显示真实 issue 总数、POS/步骤分组、问题类型和影响范围。
- 删除 layout 级逐条 `待完成项` 警告墙，preview 成为发布问题汇总唯一入口。
- 将最近一次发布 issues 映射到发音方式/词典音标/实际发音、细分词性、词频、释义内容、语法结构等已有控件。
- 保持已知但无法精确定位到字段的 issue 的通用兜底和步骤级导航；运行时未知合同继续 fail closed。
- 严格区分普通 save/complete validation 与 publication check/publish issues 状态。

### 本次不做

- 不在输入时调用后端 validate。
- 不用本地计数决定 complete/publish，也不替代 Rust rules。
- 不隐藏、合并或删除服务端原始 issues；UI 只聚合展示。
- 不改变后端 validation code、发布门或数据库。
- 不重新实现多维例句；句子相关 issue 只复用现有节点/导航合同。
- 不把所有后端错误都强行映射到字段；无法定位时保留可读汇总和步骤导航。

## 建议的本地计数口径

### Step 2

- 一个无成员 form group 计 1。
- 一个 concrete form 只要任一地区变体缺拼写、没有发音或任一发音缺 style/dict phonetic/actual pron，整体计 1。
- 一个 form 即使多个字段为空也只计 1；不在本地徽标统计重复、非法枚举等非“未填”问题。

### Step 3

- 整个 POS 没有 grammar structure 计 1；每个含空 variant 文本的 grammar structure 计 1。
- 整个 POS 没有 sense 计 1。
- 每个 sense 分别统计：缺/失效 sense group、缺 sub POS、缺 frequency、没有中文释义，各 1。
- 每条英/中内容不完整的 sentence 计 1。
- 枚举非法、范围非法、关系目标失效等不是本地“未填”，只由发布 issues 表达。

## 验收标准

- [ ] Step 2/3 每个基本词性显示独立徽标，填写/删除后立即按当前本地 draft 重算。
- [ ] 0 不显示；删除按钮位置和 Tab 可点击区域不被徽标破坏。
- [ ] 本地计数变化不会生成后端 issue、字段红框或网络请求。
- [ ] 发布摘要总数等于服务端 `issues.length`，不会等于去重文案数。
- [ ] 摘要至少包含总览、基本词性或步骤兜底、问题类型/数量和影响范围。
- [ ] 同一种发音问题出现 29 次时，文案只展示一次但数量仍为 29；总数仍包含其他问题。
- [ ] 每个分组只有明确的“去填写”，定位该组首个真实 issue。
- [ ] `pos_id` 缺失但 ancestor/node 能归属 meanings POS 时仍正确分组；完全无法归属时回退 forms/meanings 步骤。
- [ ] 字段错误仅来自最近一次检查/发布；输入、普通保存、complete 尝试不更新或清除该状态。
- [ ] 下一次检查/发布返回新 issues 时整体替换；返回 valid 时清空摘要和字段错误。
- [ ] Rust 发布校验、真实 issue 数和发布阻断行为不变。

## 待评审开放问题

### O1：确认本地计数单位

建议采用上面的“form/group/grammar/sense missing dimension/sentence”口径。它与服务端 issue 数故意不同：徽标回答“还有多少块内容没填”，发布摘要回答“服务端发现多少条具体问题”。需要产品确认该差异可接受。

### O2：POS 卡是否展示步骤子计数

建议 POS 卡显示总数，并列出 `词形与发音 n / 词义与例句 m`；无法归属 POS 的 issue 单列步骤卡。旧实现只有 POS 总数和全局类型分布，本次正式需求出现“按词性/步骤”，建议补上步骤子计数。

### O3：最近一次检查结果的过期提示

建议普通编辑后保留红框和简短提示“修改后请重新检查”，不自动加时间戳或 revision 标签。若需要显示“基于第 N 版检查”，可后续增强，不应阻塞本次状态边界修复。
