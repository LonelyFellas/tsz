## 建议拆分与实施顺序

三项应保持三个独立 PR/评审切片，不与多维例句功能重新捆绑：

1. 先做切片 2。它是前端专用小改动，可先消除 V3 draft 的残余导航门禁。
2. 再做切片 3。它会触及 V3 wizard、layout 和相关测试，基于切片 2 的最终导航语义实施可减少冲突。
3. 最后做切片 1。它需要数据库 expand/backfill/harden、后端兼容阶段、前端切换和最终契约收紧，发布链最长。

切片 1 的后端兼容发布可以与前两个前端切片并行准备，但不得把旧的必填 `headwords` 合同直接部署到仍在运行的旧前端。

## 共同硬边界

- `completed_steps` 是服务端完成事实，`max_reachable_step` 是“继续创建”默认落点，都不是 draft 页面访问权限。
- `intent="save"` 只放宽内容完整性，不放宽 JSON 形状、稳定 ID、引用、内容上限、并发 revision 和存储安全。
- `intent="complete"`、发布检查和发布保持 Rust 校验权威；前端不得用本地计数替代服务端 issues。
- 发布字段错误只来自最近一次“检查发布条件/发布”；输入、普通保存或跨步骤导航不主动重算、更新或清除。
- 所有新迁移编号必须晚于最新 `main` 的迁移序列；不得复用原始 worktree 中回填到历史时段的迁移文件名。
- 后续业务实施开始前，三套需求、设计、开放问题和测试矩阵需要一次性评审确认。
