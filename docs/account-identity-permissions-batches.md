### 已核实的关键问题

1. **邮箱账号模型已具备，不应重做。** `migrations/20260709075649_create_users.up.sql` 允许 phone/email 至少一个非空，并有 `users_email_key ON users(lower(email)) WHERE email IS NOT NULL`。`src/platform/model.rs` 的 Email 解析统一 trim／小写；`UserProfile` 的 phone/email 可选。仅按建议的邮箱注册范围，预计无需数据库迁移。
2. **不能直接暴露现有通用 register 服务。** `src/user/service.rs` 的 `register(RegisterInput)` 虽接受邮箱，但不负责 OTP 验证和完整的注册会话事务。HTTP 注册目前用 `register_verified_phone_in`，它硬编码 phone=Some、email=None。邮箱路径应扩展这条已验证联系方式的事务链，不另走“先建用户、再登录”的非原子路径。
3. **密码差异已从实现确认，不只是注释。** web `validate.ts:26` 要求 11–20 位字母数字，`RegisterForm.tsx` 与 `LoginForm.tsx:118` 都转大写；后端 `Password::parse` 要求至少 8 个 Unicode 字符、最多 72 字节，不限制字母数字，hash/verify 不转大写。因此通过 API 创建的混合大小写密码并不保证能从当前 web 密码登录。不能只放宽前端长度或删除转大写，否则可能改变存量用户行为；登录也不应重新执行新注册密码策略。
4. **未注册提示不能依赖不存在的返回消息。** 前端验证码错误表含 `user not found`，后端 `find_active_by_identifier` 对不存在账号返回 `InvalidCredentials`，最终消息为 `invalid credentials`。建议在失败态统一提供“尚未注册？去注册”的对应入口，保留后端防枚举行为，不要求服务端区分账号不存在和密码错误。
5. **OTP 验收必须分层。** 发码端已经接受 phone/email 二选一和 Register/Login 用途，现有冷却、日限、验证码有效期及尝试次数控制可复用；但 `src/otp/sender.rs` 唯一实现是 Mock，固定 `000000` 且只记录 mock 发送事件。短信与邮件都没有真实送达实现。`isCode` 允许 4–8 位，而登录 DTO 声明六位，建议本批表单收敛到六位，不顺手更改第三批页面行为。
6. **已有设计不是本批禁令。** `docs/features/web-auth-register/` 的邮箱“不包含”只代表旧阶段范围；第二批 #77 明确需要邮箱注册。第一批暂缓的角色下发和第三批绑定／解绑、换绑、找回密码不纳入本轮实现。

### 评估阶段建议方案（实施以授权及最终设计为准）

- **注册请求**：扩展现有 `POST /api/v1/auth/register`，支持 `{ phone, password, code }` 或 `{ email, password, code }`，非空联系方式恰好一个；两者都给、都不给或格式错误均拒绝。保留原手机号请求形状，不新增重复的登录接口，不允许客户端决定初始角色。
- **注册编排**：归一化联系方式 → 密码格式校验 → 验证同联系方式的 Register OTP → hash → 同事务创建用户、student 角色和 refresh session → 返回现有 `LoginResponse` 与 cookie。保留唯一约束和事务回滚；邮箱冲突的错误字段不能沿用当前 `map_register_error` 中固定的 `phone`。
- **前端入口**：扩展 `RegisterForm` 支持手机／邮箱；海外入口按待确认口径默认邮箱，复用组件。切换方式或联系方式清空旧验证码、错误与前端倒计时；在途操作锁定相关输入。发码和提交使用同一个归一化值，不把密码、验证码或联系方式写入 URL／持久化存储。
- **会话恢复**：继续复用 `persistSession`、`completeAuthentication`、GuestGuard 和安全回跳。注册／登录成功但 me 请求失败，只重试资料加载，不能重复注册或再次消费验证码。
- **错误与引导**：六位验证码预检；重复账号引导对应密码登录；验证码错误／过期、429、503、停用账号分别显示可行动提示。密码登录保留统一凭据错误，附注册入口而非新增账号存在性探测。
- **改动边界**：前端集中在 `RegisterForm`、`LoginForm`、注册路由、`packages/api-client/src/endpoints.ts` 及对应测试／OpenAPI 快照；必要 wire 类型放入 `@tsz/types`。后端集中在 `src/auth/handler.rs`、`src/user/service.rs`、注册集成测试和 OpenAPI；只有确认真实发码范围后才扩展 OTP provider，不重写 store／token 内核。
- **发布顺序**：后端先增加兼容现有手机号请求的邮箱注册能力，生成 OpenAPI；前端指定实际 `OPENAPI_SOURCE` 同步快照再开放邮箱入口。现有响应不变时，旧前端仍可工作；前端上线后不能把后端单独回退到仅手机号版本，应先撤回新入口或两端配套回退。若密码规则改变，另需存量兼容与回退设计，不能假定简单回滚安全。
