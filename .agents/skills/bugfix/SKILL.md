# bugfix —— 先复现，再修复

把“本地稳定复现”设为修改业务代码前的硬门禁。先证明问题存在并建立可重复的失败基线，再修根因；不能靠阅读代码后的猜测直接改实现。

## 与其他 Skill 的分工

- `bugfix`：建立现场证据、复现失败、定位根因、完成最小修复和回归验证。
- `test`：需要系统扩展测试覆盖时，先设计用例矩阵，再补分层测试。
- `ship`：用户明确要求提交、推送或开 PR 后才进入发布流程。
- `deploy`：只部署已经合入 `main` 且 CI 全绿的前端代码。

Bug 修复默认不需要 `feature` 的需求和技术评估流程；如果排查后发现实际需要新增成型能力，停止并转交 `feature`。

## 阶段 0：确认边界并保全现场

1. 明确现象、预期、发生环境、影响范围和已知操作步骤。
2. 分别检查相关仓库的分支、HEAD、`git status` 和已有未提交改动；用户改动一律保留。
3. tsz 联合问题同时检查：
   - 前端：当前 `tsz` 工作区。
   - 后端：`/Users/darwish/Dev/tsz-core/tsz-rust`。
   - 权威接口：后端 `docs/openapi.json`，以及前端 `packages/api-client/src/openapi.snapshot.json`、`@tsz/types` 和真实调用链。
4. 未经用户明确授权，不提交、不推送、不部署，不清理或覆盖现场。

## 阶段 1：建立可证伪的复现目标

在改业务代码前写清四项：

```text
前置条件：版本、配置、账号/权限、数据状态
操作或命令：可重复执行的最短步骤
预期结果：正确行为
实际结果：Bug 的可观察输出
```

复现必须命中用户报告的核心异常，不要求机械复制生产环境的全部外围条件。可以用更低层、确定性更强的方式证明同一条因果链。

## 阶段 2：本地复现门禁

按最接近根因且成本最低的顺序选择复现方式，可组合使用：

1. 运行已有的失败测试或精确覆盖该链路的测试。
2. 新增只表达现状的回归测试，使其在修复前稳定失败。
3. 直接调用 service、API 或纯函数，保存原始输入输出。
4. 启动本地前后端，按真实 UI 操作步骤复现。
5. 对环境相关问题，使用与现场等价的数据、配置和版本复现。

复现阶段允许：

- 添加测试、fixture 或一次性诊断脚本。
- 增加临时日志或只读探针，但交付前必须移除。
- 使用现有健康的本地数据库、Redis、mock 或测试容器。

复现阶段禁止：

- 修改生产业务逻辑、契约或数据结构来试探是否“可能修好”。
- 把静态代码推断、已有绿色测试或与现象不一致的模拟当成复现成功。
- 为了得到预期失败而篡改无关数据或降低断言。

### 复现通过条件

必须同时满足：

- 至少连续两次得到相同核心异常，或由确定性自动化测试稳定证明。
- 记录了执行命令/步骤和关键原始输出。
- 能说明本地异常与现场现象为何属于同一条因果链。

达到条件后，明确向用户报告“本地已复现”，才进入修复。

### 无法复现时

不得修改业务代码。继续只读排查：

1. 对比现场与本地的精确 commit、部署 SHA、配置开关、API 响应和数据形状。
2. 检查缓存、权限、时序、浏览器、数据库和第三方依赖差异。
3. 尝试缩小缺失条件，但不臆造线上数据。
4. 仍无法复现时，报告已排除项、证据缺口和获得下一份证据的最小动作，等待用户决定。

## 阶段 3：定位根因

从复现入口沿真实调用链追踪到权威来源：

- 前端：UI → state/query → data source → api-client → wire types → OpenAPI/mock。
- 后端：handler → DTO → service → repository/外部依赖 → 数据约束。
- 联合问题：对齐请求、响应、枚举、可选性、状态码、生命周期和版本。

区分根因、放大因素和表面症状。修复点应落在拥有该规则的权威层，避免只在 UI 隐藏错误或在前端硬编码后端规则。

## 阶段 4：实施最小修复

1. 先保留能够证明旧行为失败的回归测试。
2. 只修改根因所需代码；同步所有受影响的 wire 类型、OpenAPI、fixture 和 mock。
3. 保持混合版本兼容：服务端变更考虑旧客户端，前端对未来未知 wire 值保留安全兜底。
4. 不顺手重构无关模块；发现独立问题时单独记录。

若修复会造成破坏性迁移、改变公开契约或明显扩大范围，暂停并向用户确认。

## 阶段 5：沿同一路径回归

修复完成后必须先重跑阶段 2 的同一复现路径，证明：

- 相同前置条件和输入下，原异常消失。
- 实际结果变为阶段 1 定义的预期结果。
- 回归测试不是通过删除断言、弱化输入或绕过失败分支而变绿。

然后按风险运行相称质量门：目标测试 → 相关包测试/typecheck/lint → 必要的集成或 e2e。跨前后端契约变更还要重新导出后端 OpenAPI、同步前端快照并运行契约测试。

## 交付格式

简洁报告：

1. **复现证据**：命令/步骤、失败结果、重复性。
2. **根因**：权威层及错误机制。
3. **修复**：前后端分别改了什么，兼容策略是什么。
4. **验证**：同路径前后对比和质量门结果。
5. **工作区状态**：修改文件范围，以及是否暂存、提交、推送或部署。

没有复现成功时，不得使用“已修复”或同义表述。

## 红线

- 未本地复现，不改业务代码。
- 不用猜测代替原始请求、响应、日志或可执行测试。
- 不把 mock 自洽当成前后端契约正确；涉及 API 必查权威 OpenAPI 和真实后端实现。
- 不绕过 hooks、测试或覆盖率门槛。
- 不覆盖用户未提交改动，不对 `main` 直接提交或推送。
- 未经明确授权，不提交、不推送、不部署。
