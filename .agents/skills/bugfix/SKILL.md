# Bug：先复现，再修复

## 范围与基线

根据用户现象检查相关仓库，不机械检查所有服务。跨前后端问题同时核对两仓 checkout、SHA、脏改动、部署版本、配置和数据条件。
读取各仓项目约定；接口依据 tsz-rust 的 `docs/openapi.json`、实际实现、前端快照及调用链。
路径从当前 workspace/相关仓库定位，不硬编码某台机器的绝对目录。

修复请求授权必要的本地诊断、测试与最小代码修改；提交、推送、部署和真实数据变更按用户已给出的范围判断。
保留用户改动与现场；日志不暴露凭据。Bug 默认不走新功能评估；确实需要新增能力时先说明范围变化。

## 1. 建立失败基线

先记录四项：前置条件、最短操作/命令、预期结果、实际异常。
选择成本最低且能证明同一因果链的方法：已有测试、新回归测试、函数/API 调用、等价本地配置，必要时再走 UI。
确定性失败测试可直接作为基线；时序问题保留多次运行证据，不能用机械次数代替稳定性判断。
复现命中用户的核心异常后，保存关键输出并告知用户，再改业务逻辑。

允许添加诊断测试、fixture、临时探针；不以修改业务逻辑试运气，不把已有绿色测试或静态猜测称为已复现。
本地 UI 验收采用仓库规定的启动方式；web 使用生产构建与 `next start`。

## 2. 无法复现时继续取证

暂不改业务代码。对比精确版本、原始 API、权限、缓存、数据形状与时序，缩小缺失条件。
能独立完成的只读调查继续做；只有无法取得的环境信息或必要授权才问用户。
报告已排除项、证据缺口与最小下一步，不把不确定原因包装成修复完成。

## 3. 定位并最小修复

沿实际调用链找到规则的所属层：前端 UI/state/api-client/wire，后端 handler/DTO/service/repository/数据约束。
区分根因和表面症状；保留失败回归证据，只修改根因及其直接调用点。
涉及 API 时同步必要的 OpenAPI、类型、fixture 与 mock，并检查旧客户端/服务端兼容性；
响应新增字段也要检查前端是否严格拒绝未知字段，不预设发布顺序。
破坏性迁移、公开行为改变或额外系统修改超出原请求时，先说明具体方案再确认。

## 4. 沿原路径回归

先用相同输入和前置条件重跑失败路径，证明结果恢复预期，再运行受影响包、契约与必要的集成检查。
需要补测设计时使用 [test](../test/SKILL.md)，复用已经写清的复现清单。
全量门在接近完成时统一安排；紧接已授权 ship 时让其 hooks 承接覆盖的检查。不得弱化断言、降低门槛或绕过 hooks。

交付复现证据、根因、最小修复、同路径验证和各仓工作区状态。
用户已要求交付/部署时再进入对应仓库的 ship/deploy；不自动扩大任务。
