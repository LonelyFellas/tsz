# 新功能：先评估，再实施

## 范围与依据

- 先读当前 checkout 的项目约定与相关真实代码。前端契约以 `tsz-rust/docs/openapi.json`、`docs/frontend-integration.md` 和前端快照为依据；历史 tsz-go 文档只作参考。
- 用户目标涉及前后端时，可以读取相关后端实现定位接口行为，并在已授权范围内联动修改；进入另一仓库先读它的约定、分支和脏状态。纯前端任务不顺带扩大为后端重写。
- 提交、推送、PR、合并、部署按用户原请求逐项判断；实现完成不自动触发交付或部署。

## 1. 建立依赖与基线

1. 查看分支、工作区、相关现有功能与测试，先把工作分成「已在主线、可直接复用、小改动、新工作、阻塞」。跨仓只画一份依赖图，共享文件集中处理。
2. 已有本任务分支就复用。新任务先 fetch，前端以 `origin/main` 为基线，后端遵循自己的分支模型；默认使用 `codex/<slug>`。不覆盖用户改动，不抢占其他 worktree；需要隔离时创建新 worktree。
3. slug、目标端能从上下文推断就直接采用并说明。只有影响产品行为或验收的缺失信息才提问；等待时继续不依赖答案的调查。
4. 估计剩余关键路径，不为已经完成的能力重复估时。超出估计 50% 时在安全点说明原因、修订路径和最小下一步。

## 2. 连续完成两份评估

在 `docs/features/<slug>/` 写入或更新：

| 文件              | 必须说清的内容                                                                                |
| ----------------- | --------------------------------------------------------------------------------------------- |
| `requirements.md` | 用户与目标、目标端、主流程及关键异常、范围、约束、可验证验收标准、未决问题                    |
| `design.md`       | 现有能力与依赖、选定方案、具体文件/接口影响、数据与状态流、兼容与发布顺序、风险验证、回退限制 |

按功能复杂度展开，不填与任务无关的模板。跨仓文档集中在任务主仓，另一仓引用即可。
接口未实现时标明缺口；mock 只能证明前端行为，不能算真实联调完成。

## 3. 评估确认

两份文档都完成后一起展示。没有确认过方案时，请用户确认会影响实现的需求、范围与技术选择，再写实现或测试代码。
本会话已有明确方案批准或用户明确要求按既定方案直接实现时，沿用授权，不重复询问；补齐必要记录后继续。
常规实现细节自行处理；只有新增范围、破坏性契约或重大取舍超出授权时才再次确认。
需要停下时，链接本文件并引用实际触发的规则，说明尚缺的决定。

## 4. 实施与验收

按依赖顺序修改必要的类型、请求、共享逻辑和页面；后端变化在对应仓库处理。
测试策略使用 [test](../test/SKILL.md)，可以先写回归测试或边实现边验证，不必等所有实现完成才测试。

保持 snake_case wire、鉴权内核和 web/admin UI 分工，具体约定读项目文件，不在技能里维护第二份。
迭代只跑受影响检查；完成时统一安排一次仓库要求的全量门。紧接已授权 ship 时由原生 hooks 承接其覆盖的检查，不手工重复跑。
web 真实验收使用生产构建与 `next start`。

交付实际结果、验证证据和未就绪依赖。仅在用户已要求提交/推送/PR 时进入 [ship](../ship/SKILL.md)。
