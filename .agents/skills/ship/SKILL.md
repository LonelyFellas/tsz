# 前端交付

## 1. 范围与授权

- 先核对原请求、分支、完整 diff、已有提交、remotes、PR 与用户未提交改动。明确本次要提交的文件和交付终点。
- 「提交并推送」「开 PR」「ship」已授权其必要的提交/推送/PR 步骤，不在每一步重复确认；「仅提交」不包含推送，「仅审查」不包含提交。合并和部署需要各自的授权。
- 仅审查时只读取并交付发现与验证局限，不自动修改文件，也不进入提交阶段；下文的修复动作仅适用于已授权修复或交付的任务。
- 没有交付授权时，先完成自检、修复、验证与拟用提交说明，再一次性请求缺少的授权。需要停下时链接本文件并引用触发规则。
- fetch 后以 `origin/main` 作为前端 PR 基线；默认新分支 `codex/<slug>`。不在 main 提交/推送，不覆盖用户改动，不重写已发布历史。
- 已有本任务分支/PR 就复用；若旧 PR 已合并，核对剩余差异后为本次工作建立新分支。无关本地 main 的分叉不阻断可安全隔离的任务。

## 2. 定向自检

检查当前 diff 与直接调用链，只报告实际相关的结论：

| 变化         | 检查重点                                                  |
| ------------ | --------------------------------------------------------- |
| 业务逻辑     | 行为、边界、异常、权限、竞态与高价值回归证据              |
| 共享层/API   | 复用边界、wire 契约、下游调用点与混合版本兼容             |
| 页面/组件    | 请求瀑布、长列表、包体和交互性能；SEO 只检查公开 web 页面 |
| 鉴权/IO/部署 | 会话、输入、敏感信息、重定向、配置与失败路径              |

修复本次范围内的确定问题，风格/重构建议不扩大任务。测试不足时参考 [test](../test/SKILL.md)。
API/开关变化需要后端配套交付时，定位已安装的 `contract-sync`，读取其 `references/paired-release.md`，在现有 PR 中说明两仓版本、兼容性与发布顺序。若技能不可用，仍须查清这些依赖；此步骤不自动授权后端交付或部署。
迭代只跑受影响测试；已完成的同状态检查直接复用。最终 typecheck 与 `test:cov` 交给正常 pre-push，不在自检阶段重复全量运行。
本地 e2e 按实际风险或用户要求执行，其余留给 CI。纯文档改动做格式、链接、行为规则检查，不额外跑运行时套件。

## 3. 提交

确认目标完成、`git diff --check` 通过，只暂存本次文件并检查 staged diff。
使用 conventional commit，署名按当前工具/用户约定，不硬编码历史模型名。
正常提交，让 pre-commit 和 commit-msg 执行；hook 改写的文件必须纳入最终审查。
保留无关脏改动，不要求为提交清空整个工作区；有混合 hunk 时精确暂存或使用隔离 checkout。

## 4. 一次独立 pre-push 审查

1. 提交后固定 `review_base_sha`（本次 origin/main 的完整 SHA）与 `review_sha`（HEAD），审查完整待推送范围。
2. 使用可调用的独立审查工具；没有时，本技能要求创建一个新的只读 reviewer 子代理。传入原始目标、两端 SHA、项目规则和已完成的验证，不传入自审结论。
3. reviewer 只读提交对象及直接受影响调用链；脏工作区使用隔离 checkout，不能把未提交代码当被审提交。报告有文件/行号证据的正确性、安全、契约、数据、并发、性能及测试缺口。
4. P0–P2 或其他实质正确性/安全问题阻断推送；误报用证据排除。风格建议不阻断，也不派额外 reviewer 逐条核实。
5. 修复后记录旧/新 SHA，重跑受影响检查，由同一 reviewer 复查 `old_sha..new_sha` 和原问题。不变部分沿用初审证据，最终结论必须覆盖当前 SHA。只有范围扩大或初审假设失效才重做全范围审查。
6. 不让 reviewer 重跑已提供结果的全量测试、build、lint 或 typecheck。停滞时检查真实任务状态并收敛范围；没有可用独立 reviewer 就报告阻塞，不用自审替代。

## 5. 推送与 PR

正常 `git push -u origin <branch>`，绝不使用 `--no-verify`、`LEFTHOOK=0` 或其他跳过 hooks/CI 的方式。
失败先读真实输出区分 hooks、网络、认证和镜像问题；修复如产生新提交，补齐第 4 步增量审查再重推。
不默认 force push；多 push URL 的结果分别报告，镜像失败不能当成 GitHub 成功，也不盲目改远程配置。

按授权创建或更新以 main 为 base 的 PR，正文写清问题、结果、测试与审查证据。多行正文用结构化参数或 `--body-file`。
返回 SHA、reviewer 结论、hooks/CI 状态和 PR 链接。工具或认证受阻时保留已完成结果，准确说明停在哪一步；合并仍需 CI 全绿与用户授权。
