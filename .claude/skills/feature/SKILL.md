# feature —— 新功能开发工作流（评估先行）

从头做一个成型功能时，按「**分支 → 需求评估 → 技术评估 →（一次性评审确定）→ 代码动工**」推进：**动代码之前，先把需求和技术方案想清楚、写成文档、经过评审**。

**为什么先评估**：直接开写代码返工成本最高——需求理解偏了、影响范围没摸清，往往推倒重来。评估阶段是纯思考 + 文档，**改文档比改代码便宜得多**，是用便宜的前期对齐换掉昂贵的后期返工。文档还随 PR 进库，评审留痕、可追溯。

**这个 skill 的重心是评估（阶段 1、2）**。评估方案一经确定，就进入「代码动工」——写测试和写实现都是动代码，同属动工阶段：实现按项目约定走，**测试交给 test skill** 承接 design 里的测试策略，本 skill 不细管怎么写。

**确认机制（一次性评审）**：阶段 0 可与用户确认 `<slug>`（及目标端若不明）；**确认后阶段 1、2 连续做完、不逐步打断**——各自把文档写好、记录到位，中间不停下等用户逐个确认。**两份文档（`requirements.md` + `design.md`）都产出后，再一次性交给用户评审**。这是动代码之前唯一的评审门：改文档只花几分钟，是便宜的纠偏；但一次性给，不打断用户节奏。评审有问题就改文档、再复审，通过后才进阶段 3 动代码。

## 适用与边界

- **用于成型的新功能**：有独立需求、跨多个文件/接口的那种。一行 bugfix、改文案、调样式**不必**走流程，直接改。
- **评估要吃透本项目（前端）**：技术评估不是泛泛而谈，必须先读懂 `tsz` 里**相关的真实代码、架构、约定**，再落方案。
- **后端只对接文档，不碰后端实现**：
  - **共享对接文档**（主依据）：以 `tsz` 仓为工作目录时，`../docs/` 即与 `tsz`、`tsz-go` 同级的共享对接文档仓（见 `../docs/README.md` 清单）。
  - **契约文件可读**：`../docs/` 引用的 `../tsz-go/docs/` 下**契约类文件**（如 `openapi.yaml`、`api.md`、模块 design 文档）可以读，用于核对字段与接口；**禁止**读改 `tsz-go` 的 Go 实现代码（handler/service/repository 等），不产出后端 diff、不碰数据库。
  - **缺口处理**：现有文档不够、或需新接口/字段变更时，在 `design.md` 写清**后端对接建议**，由用户转达后端团队。
- **衔接 `/ship`**：动工完成、自测通过后，走 `/ship`（审查 → 提交 → 推送 → PR），本 skill 不重复那段。

## 阶段 0 —— 切分支

先把地基摆正，别在 `main` 上动土：

1. 确认工作区干净（`git status`），且本地 `main` 与远端同步：`git fetch origin`，基于 `origin/main` 切。
2. **与用户确认 `<slug>`**（功能的 kebab-case 短描述，如 `admin-reset-password`）——这是开做前**唯一允许的单点确认**；目标端（web / admin / 双端）若用户未说明，在此一并确认。`<slug>` 同时是分支名和文档目录名，一串到底方便关联。
3. 切分支：`git switch -c feat/<slug> origin/main`。
4. 建文档目录 `docs/features/<slug>/`，两份评估文档都放这。

> 红线：绝不在 `main` 上直接开发；PR 走 `main`（见 CLAUDE.md 质量门）。

## 阶段 1 —— 需求评估

产出 `docs/features/<slug>/requirements.md`，把「要做成什么」讲清楚。**这一步不谈技术实现**，只谈需求本身，避免过早陷入细节而没对齐目标。功能常始于用户一句话——把它展开成完整需求，拿不准的进「开放问题」。

模板：

```markdown
# <功能名> 需求评估

## 背景与目标
为什么要做、解决谁的什么问题、成功长什么样。

## 目标端
web（学员/教师，`@tsz/ui`）/ admin（管理后台，antd v6）/ 双端 —— 明确本次改动落在哪个 app。

## 用户故事 / 使用场景
以「谁 - 在什么情况下 - 想做什么 - 得到什么」描述主流程与关键分支。

## 功能范围
- 做什么（本次范围内）
- 明确不做什么（划走边界，防止范围蔓延）

## 约束与边界
权限/角色、数据规则、兼容性、性能/安全要求、依赖的外部系统或接口。

## 验收标准
可勾选的清单——每条都应能被一次操作或检查验证。

## 开放问题
还没定的点，需要用户或后端拍板的。
```

写好即进阶段 2，**不在此暂停**（评审留到评估全部做完后一次性进行）。

## 阶段 2 —— 技术评估

需求写完后，产出 `docs/features/<slug>/design.md`。核心是两块：**代码影响范围**和**技术方案**。

**先做功课再落笔**——用搜索/读码摸清 `tsz` 现有结构（相关的 `@tsz/types`、`@tsz/shared`、`@tsz/api-client`、页面/路由等），基于本项目真实代码设计，别凭空画。**涉及后端时**，先读 `../docs/` 对接文档；字段细节以对接文档为准，必要时对照 `../tsz-go/docs/` 契约文件，**不读 Go 实现代码**。

模板：

```markdown
# <功能名> 技术设计文档

## 方案概述
选定的技术路线，一段话讲清怎么做。若有备选方案，说明为何不选。

## 代码影响范围
逐项列出**要新增/修改的文件、包、接口**（纯前端功能可略去后端段）：
- 前端 tsz：哪些 app/package、哪些文件、哪些组件/store/路由
- 类型与数据：`@tsz/types` 的 wire 变更（snake_case，1:1 镜像后端契约）

## 后端对接（如需）
依据 `../docs/` 已有文档说明如何对接；引用具体文档路径。
- 使用的接口、字段、鉴权方式、错误码（以对接文档为准）
- **对接缺口 / 后端建议**（需用户转达后端）：缺什么接口、建议的请求/响应形状、字段变更、状态码约定等——写清楚供后端评估，**本 skill 不实现后端**

## 复用与约定
复用优先级（逻辑→@tsz/shared，类型→@tsz/types，请求→@tsz/api-client）；
鉴权走 @tsz/shared/auth 内核；web→@tsz/ui、admin→antd v6。命中哪些硬约定。

## 数据流 / 时序
关键交互的请求-响应、状态流转；前后端调用链（以对接文档契约为准）。

## 测试策略（概览）
打算怎么测——单测测什么、集成测什么、要不要 e2e/手测。此处只列策略方向，
具体测试代码在「代码动工」阶段用 test skill 落地。

## 风险与回滚
可能踩的坑、对现有功能的影响、出问题怎么回退。
```

## 一次性评审（评估门）

两份文档（`requirements.md` + `design.md`）都产出后，**在此统一交给用户评审**——这是动代码之前唯一的确认点。汇报时把两份文档一起给出，重点让用户确认：需求没跑偏、目标端正确、技术方案的「代码影响范围」没漏、路线认可；若含「后端对接建议」，一并确认是否转达后端。**用户确认后，才进阶段 3 动代码。**

## 阶段 3 —— 代码动工

评估通过后才动代码。目标：把 `design.md` 落成**前端实现**，守住项目约定。

**推荐落地顺序**（自下而上，避免类型/接口与 UI 脱节）：

1. `@tsz/types` — wire 类型与后端契约对齐
2. `@tsz/api-client` — 请求封装
3. `@tsz/shared` — 可复用逻辑、鉴权薄壳
4. 目标 app（web / admin）— 页面、组件、store、路由
5. **测试** — 核心逻辑稳定后，按 design 测试策略调用 **test skill** 补单测/集成/e2e
6. **联调** — 接口已有时走真实联调；后端未就绪时先用 mock/stub 保 UI 与状态流，接口落地后再替换

动工要点：

- 严守硬约定（CLAUDE.md）：类型 snake_case wire、复用优先级、鉴权内核薄壳、web/admin UI 分叉、antd v6 注意点、主题 class 水合坑等。
- 本地验收：`pnpm test`（或 `test:cov`）、`pnpm typecheck`、`pnpm lint`；**web 用 `pnpm build` + `next start`，不要 `next dev`**。
- **联调后端**：按 `../docs/` 对接文档与已实现的接口联调；测试服用 SSH 隧道（8080 到后端）——**不在本仓改 `tsz-go`、不碰数据库**。
- 实现中若发现方案有误——回阶段 2 更新 `design.md` 再继续，别让文档和代码脱节。

完成并自测通过后，走 **`/ship`** 开 PR。评估文档（requirements.md + design.md）随分支一起进 PR，供评审。

**联调稳定后（可选）**：若本次功能引入了新的前后端契约且 `../docs/` 尚无对应文档，可在 PR 描述或评审时提醒用户：是否需要向共享对接文档仓补充/更新 integration 文档（独立 git 仓，不由本 skill 直接提交）。

## 红线

- **不跳评估**：两份评估文档做完、经用户一次性评审通过，才动代码。
- **不在 `main` 直接做**；**不绕过 lefthook**（`LEFTHOOK=0`、`--no-verify` 一律禁止）；不 `force` push。
- **不碰后端实现**：不读改 `tsz-go` Go 源码、不产出后端 diff、不碰数据库；对接以 `../docs/` 为主、`../tsz-go/docs/` 契约文件为辅；缺口写「后端对接建议」由用户转达。
